== Auth and the MCP surface

* **Static bearer tokens, not OAuth.** The SDK supports JWKS and introspection, but neither was
  worth standing up an identity provider for a handful of operators. Cost accepted: these tokens
  do not expire, so a leaked one is good until revoked. Moving to OAuth later replaces
  `Auth.verifier` alone; scopes and tools do not change. (`mcp/src/.../access/Auth.scala`)
* **`Main` refuses to start without `MCP_TOKENS`/tokens configured.** The SDK silently ignores
  `requireScopes` declarations when no `.auth(...)` is configured, so an unauthenticated server
  looks exactly like a scoped one from outside while every tool sits open. "Guessing 'open' on a
  missing environment variable is not a failure mode worth having."
* **Tokens moved out of `MCP_TOKENS` (an env var) into the `mcp_tokens` table**, hashed
  (SHA-256, unsalted, no work factor — right here because `mint` generates 256 bits of entropy, so
  there is no dictionary to attack and nothing a slow hash would buy), issued from each other with
  `create_token`. `MCP_ADMIN_TOKEN` seeds the first row and nothing else reads it, so rotating it
  is a restart. Reason: the env var made adding an operator a redeploy and reading the list an
  `ecs describe-task-definition`; a credential that takes a redeploy to issue is one people share
  instead. Rejected alternative: keeping both — two answers to "who may write" that would drift.
* **The admin token is seeded from an env var rather than generated**, because a generated token
  would have to be shown somewhere, and the only channel at startup is CloudWatch — "the last
  place a credential holding every scope belongs." It also doubles as the recovery path: this
  database is known to lose data (see `incidents.adoc`), and a seeded admin means recovery is a
  restart; a generated one would lock every operator out on each loss.
* **No scopes table.** Legal values are a Scala enum; a row per scope would let the database hold
  combinations the code cannot express. Comma-separated on the token row to match the format
  `MCP_TOKENS` used, so the set is readable in a dump without a join.
* **`Grant` is a Scala enum with `snake_case` identifiers** (`i18n_write`, not `i18n:write`)
  because a colon is not a legal identifier — the same trade already made for `QuestionType`'s
  wire tags: "a schema that lies about what it accepts is worse than an ugly name."
* **`tokens:write` is delegable** like any other scope rather than being the one indelegable one.
  Delegation attenuates — passing it along never widens what a chain can reach, only who may
  extend it — so making it indelegable would route every new operator through whoever holds the
  admin token, the bottleneck the database move was meant to remove.
* **Scopes split finer than "read vs. write."** `identity:write` is separate from `content:write`
  because the email, profiling and location surveys are deployment-wide — one of each exists for
  every portal at once, picked by category with no location filter — so a single write scope would
  make adding an option to one's own advertiser survey and rewriting the identification flow the
  same permission. Rejected alternative: one tool per survey operation, declaring `content:write`
  and quietly demanding `identity:write` once it saw the category — "that reads better at the call
  site and makes `tools/list` lie: a tool would publish one requirement and enforce another."
  `infra:deploy`/`infra:destroy` split the same way because destroying loses something (the slug's
  assets) that deploying does not.
* **RFC 8707 audience binding is enforced unconditionally.** With static tokens there is no issuer
  to bind anything, but the server states which resource it is (`MCP_RESOURCE_URI`) and mints a
  matching audience anyway; the check still rejects a token replayed against a different
  deployment, "which is the part worth keeping."
* **The OAuth metadata issuer points at the server's own origin, not a sentinel hostname.**
  `https://captal.invalid/static-tokens` was meant to say "there is no authorization server to
  send anyone to." It instead cost a real DNS lookup that never resolves (measured at 10,011 ms
  before the resolver gives up); see `incidents.adoc` for the full chain this broke.
  `OauthMetadata` publishes `grant_types_supported: []` deliberately — with no grants declared,
  RFC 8414 does not require authorization/token endpoints, so omitting both is consistent rather
  than missing, and "it beats the 404 it replaces: a 404 says 'nothing here, perhaps try again',
  this says 'there is no flow, stop looking.'"
* **Skills are served through MCP Resources, then re-exposed as tools.** First choice: Resources,
  because `McpDispatchMethod` was a closed enum in the SDK and `skills/list`/`skills/get` (then
  experimental JSON-RPC methods) could not be registered without patching it. Superseded by
  zio-http-mcp 0.10.0's `McpExtensions` registry, but the deeper reason `read_skill` exists as a
  *tool* (not only a `skill://` resource) persists: resources are application-driven — the spec
  permits but does not require a host to hand them to the model — and the sessions these operators
  actually use (Claude Desktop, bridged sessions) forward tools and not resources, and possibly not
  `instructions` either. "Nineteen hundred lines of procedure sat behind a door with no handle on
  its side." The same reasoning produced `get_location_readiness`, `list_videos`,
  `list_pending_uploads`, `get_i18n_schema` and `get_css_schema` as tools replacing `captal://`
  resource listings. Resources stay for hosts that do read them; nothing server-side depends on
  them.
* **Reads carry `readOnlyHint`; visibility is default-deny.** A host should not present a lookup
  as an action needing approval. Every tool is `Model`-visible unless named otherwise, and
  `confirm_video_upload` is the only tool a rendered MCP App page may call — the rationale being
  that a tool with nothing declared is callable by both the model and any App the host renders, so
  without `visibleTo(Model)` the UniFi credentials form (whose whole purpose is keeping an API
  token out of the conversation) could call `create_token`. "The restriction becomes a decision
  rather than an omission."
* **`captal://` is one resource hierarchy, not a scheme per entity**, because `readDirectory`
  (SEP-2640) makes a hierarchy navigable; flat per-entity schemes would lose the containment
  `list_surveys` had to rebuild by hand. (Superseded in practice by the tools-not-resources move
  above, but the hierarchy shape is still how the remaining resources are addressed.)
* **Onboarding is a *prompt*, not a tool chain, and is explicitly not a transaction.** Nothing in
  MCP models a sequence — tools are individual capabilities, the agent is the orchestrator — and a
  prompt's `get` returns messages, so it executes nothing and asks for no consent; it is also
  user-initiated (unlike a `skill://` an agent may never fetch) and stateful, naming the step
  you're on. Every tool writes on the spot and a half-finished location is "not invalid, only
  unfinished," so `Readiness` is shared by the resource and the prompt deliberately — a second
  implementation of "what is missing" would drift and disagree in front of the operator.
* **MCP Apps (server-rendered pages in a sandboxed iframe)** exist for two things the protocol
  cannot carry: "JSON-RPC cannot carry an mp4 and a tool call cannot carry a secret." Every
  `tools/call` is recorded by the host and replayed into the model's context on later turns, which
  is not where a UniFi API token belongs, and an upload page needs to PUT a video file nowhere a
  tool argument can go.
* **The upload/UniFi App pages are Scala.js modules, not server-built string literals.** The two
  bugs that cost the first MCP-UI migration a full session were a `postMessage` envelope no host
  reads and a missing `ui/message` — "a string literal cannot be wrong about those loudly." The
  Bridge protocol is on `js.Promise`, not `scala.concurrent.Future`: Future, its ExecutionContext
  and the collections around them were the bulk of what a probe bundle carried (6.4 KB for a
  barely-touching-stdlib probe vs. 152 KB for the real app), while the host already has promises.
* **Tool naming is `verb_noun` throughout** ("consistency in the tool list is what lets a caller
  pick without guessing") — `i18n_status` was renamed to `get_i18n_status` for this alone.
* **Edit tools deliberately exclude some fields.** `update_question` cannot change a question's
  type or options (the type decides which rules and options are representable at all);
  `update_video` cannot change the location (the S3 key carries the slug and the survey hangs off
  the video, so that means a new video, not an edit). The file is replaced by `replace_video_file`,
  which keeps the video's id: the id is what the survey's answers and every guest's view history
  point at, so a new video would have started those over. See "Video files" under Data model.
* **`create_location` still sits under `content:write`, and the code says that's wrong**: "a
  translator holding `content:write` should not be able to stand up a portal." Tracked in
  `pending.adoc`.

== Wire format and schema rendering

* **Publish the schema the decoder actually enforces.** The SDK derives both the published
  document and the decoder from one `Schema[A]`, but its `JsonSchemaGen` reads only `@description`
  and ignores `@discriminatorName`, `@caseName` and `@rejectExtraFields` — so those were enforced
  at runtime and invisible in the document a caller reads. `create_advertiser_video` published
  seven question variants of which only four were distinguishable; "two operators' agents stopped
  there, both guessing at the field name, both wrong." Fixed by shadowing the SDK's `McpInput`
  given with `McpSchema`, which renders through zio-http's own OpenAPI generator — already on the
  classpath — honouring all three annotations. Rejected alternative: continuing to patch the
  generated JSON per tool (`tagEnums`, `patchOneOf`, `addConst`, a positional zip of case ids
  against the `oneOf`) — this had already drifted once (case order vs. `oneOf` order silently
  disagreeing) and was "twice forgotten at a call site." Measured non-regression across all 21
  tools when the generator swapped: 7 question variants went from 4 to 7 distinguishable, wrongly
  `required` fields with defaults became optional, 11 hand-written descriptions survived, 11
  generated "a list of TextIn"-style descriptions (which leaked Scala identifiers to operators)
  were dropped, 9 tools were byte-identical.
* **Discriminator field on the wire is `kind`, never `type` or `format`.** Both of the latter are
  JSON Schema keywords, and zio-http already emits `"format": "int32"` on integers — a property by
  either name would sit beside a keyword spelled the same, "the trap `create_question` already has
  with `required`."
* **Illegal question shapes are unrepresentable in the schema**, not merely rejected by a
  validator: what varies by question type lives in a discriminated `question`/`answer` field, so
  an input question's schema has no `options` property to even pass. `@rejectExtraFields` closes
  the remaining gap — without it, a field a variant doesn't have was silently dropped by the
  decoder and the entity created without it.
* **Descriptions are annotations on our own types, derived into the schema, never
  post-processed.** A test pins 137/137 output and 123/137 input property coverage, with the
  schema-synthesised `questionType` discriminator as the sole exemption (there's no Scala field to
  annotate). Before this, coverage was 31/137 inputs and 3/98 outputs — "which left the agent to
  guess what came back from its own call."
* **One codec owns the survey tree: `platform.surveySchemas`.** Previously the rule-config JSON in
  `question_rules.rule_config` and `answers.answer_value` was written three uncoordinated ways —
  the API served it through circe, `SurveyRepositoryQuill` read it back through circe decoders,
  and the MCP backoffice wrote the same column with string interpolation
  (`s"""{"type":"$kind","value":$v}"""`) agreeing with the other two by nobody's enforcement — plus
  a fourth rendering in test fixtures. `decodeRules` discards anything it cannot parse via
  `.toOption`, so a disagreement never raised; it just stopped enforcing the rule, silently, which
  looks identical to the rule having passed. **The survey tree format is a database format, not
  only a wire format** — this is why the single-definition fix had to live in `platform`, reached
  by both `api` and `mcp`, rather than in the wire layer alone.
* **zio-http's `Endpoint` replaced tapir, module by module.** What tapir gave was an endpoint
  described as a value; zio-http's `Endpoint` gives the same thing, and the server was already
  running on zio-http underneath, interpreted into it by `ZioHttpInterpreter`. The deeper reason
  this was more than a rename: a tapir `Schema` *documents* a shape circe has already decided —
  an undocumented type could take `Schema.anyObject` for free, and eight of them did — while a
  zio-http/zio-schema `Schema` *is* the codec. Moving a type to the derived shape is a format
  decision, not paperwork.
* **`endpoints/` was replaced by `messages/`, cross-compiled, with route descriptions staying in
  `api`.** Nothing in `client` ever imported an endpoint, only the request/response types — the
  module was making the browser pay bundle budget for a description it never read (0 of 188
  output modules mentioned tapir at the time it was measured).
* **`Schema[Phase]` is hand-written; `ApiError` and `VideoResponse` are derived.** A derived enum
  schema would write the variant name as an object key (`{"Welcome":{}}`), but the browser decodes
  `Phase` as a plain string via `Decoder.decodeString.map(fromDbString)` — so `Phase` needs the
  hand-written exception. `ApiError` could move to the fully-derived shape because *both* of its
  sides moved together (see the `ApiError` entry in `incidents.adoc`). `VideoResponse`'s old circe
  pair flattened the payload under a `type` key beside the payload's own fields
  (`{...NextVideo fields...,"type":"video"}`); zio-schema cannot describe that "merge a nested
  object's fields into the parent's, plus a discriminator" shape, so this was the one response that
  had to *change* shape (`{"Video":{"data":{...}}}`), safe only because nothing read the old bytes
  directly — both sides decode to the enum and match on it.
* **The `CodecConfig` used to build the server routes, `HttpApp.codecConfig`
  (`ignoreEmptyCollections = false`), is read by the test suite too (`TestHelpers`,
  `WireContractSuite`) rather than the test asserting against a separately-constructed config.**
  See the `ignoreEmptyCollections` incident below for why this one setting needed its own rule.

== Data model

* **Soft delete everywhere, never a hard delete, and the filter on read is the half that counts.**
  `answers.question_id` references `questions`, so retiring must not break history;
  `set_question_active` retires and reports how many answers a retired question still resolves
  for. V20 added `is_active` to `questions`, `question_options`, `question_rules` and
  `localized_texts` — "the filter is the half that matters: a column no query consults is a soft
  delete that deletes nothing." `findAnsweredQuestionsByUserQuery` deliberately does *not* filter
  on `is_active`, because it feeds the event log and "retiring a question must not rewrite the
  record of what a user answered." `isSurveyCompleteQuery` has to filter `is_active` on *both*
  sides of its comparison — filtering only the question count let deactivating an already-answered
  question close the survey by itself.
* **Video status is one column with a CHECK (`pending`/`active`/`retired`), not two booleans.**
  V21 replaced an `is_active` flag that could only express two of the three real states (created
  but never uploaded, and retired, were both `is_active = 0`). Two flags would leave a fourth
  combination that cannot happen and nothing to stop it; one CHECK-constrained column makes the
  impossible state unrepresentable. `video_url` stays `NOT NULL` because it's where the S3 key
  lives (`AssetStore.keyOf` parses the URL and nothing else stores the key) — the server picks the
  key (`<slug>/videos/<videoId>.<ext>`) at creation, before any file exists, so the column can stay
  non-null from the start.
* **Validation lives in Scala; the affected-row check (`Writes.expectOne`) is the only other line
  of defence.** `advertisers` has no unique constraint of any kind, and a CHECK violation is
  dropped by rqlite as silently as any other rejected statement (see `incidents.adoc`'s rqlite/JDBC
  section) — so "validating in Scala and checking the count afterwards is the whole safety model."
  Where rqlite *does* enforce uniqueness (`locations.slug`), the Scala pre-check still "earns its
  place on diagnosis, not integrity": disable it, and the duplicate row still stays out, only the
  error message degrades to "the database rejected it silently" instead of naming the clashing
  location.
* **Stylesheets and icons stay on S3, not the database.** Keeps the portal's render path untouched
  and the asset edge-cached; the accepted cost is that a write must also invalidate CloudFront,
  something the old CLI never did for `captal video add`. `s3:ListBucket` was *originally*
  deliberately withheld from the IAM policy — every key is derived from a slug the database
  already confirmed, so a bug in key construction should fail loudly on a missing object rather
  than quietly finding a neighbour's — but this has since lapsed: `copyBundle` and
  `destroy_location` both need to list a prefix, so the live policy grants it. `docs/mcp-iam.adoc`
  still states the old absence; see the legacy-docs judgement in this tree's `readme.adoc`
  companion report.
* **The video storage key is derived from the video id, never the uploaded file name — and later
  the key drops the extension entirely.** The old CLI used the raw file name, so two advertisers
  uploading `promo.mp4` silently overwrote each other. Later: S3 addresses objects by key and
  browsers play them by *stored content type*, not by path, and measurement showed the presigned
  signature does not need to bind the content type (`SignedHeaders=host` without one vs.
  `SignedHeaders=content-type;host` with). So the extension left the tool entirely; what S3 records
  is whatever the browser sends, checked once, honestly, at `confirm_video_upload` by reading the
  object's *actual* stored type back — the first moment the type is a fact rather than a claim.
* **A scriptable SVG icon is refused outright, not sanitised.** "Stripping tags from markup nobody
  asked for invites the question of what else was quietly changed." The object is served from the
  portal's own origin, so an SVG with a `<script>` or an `on*` handler, opened directly rather than
  through the `<img>` tag the SPA uses, renders as a document where the script runs.
* **Wire vocabulary and the stored column are deliberately decoupled.** `question_type` keeps its
  lowercase, underscore-separated tag in SQLite (`CHECK (question_type IN ('radio', …))`) while the
  MCP-facing schema capitalises case names (`Radio`, `Select`) — `flatten` maps explicitly between
  them, so one side's cosmetic convention never forces a migration on the other. V22 then aligned
  the *video type* values for a different reason: `publicidad`/`propaganda` (the DB's literal
  values) had disagreed with the column's own name (`last_promo_video_id`) since V5, and that one
  genuinely needed fixing, not decoupling.
* **Promos rotate per user and location, by fewest views** (`findNextPromo` in
  `VideoRepositoryQuill`, 2026-10-30). The rotation used to be a cursor on the session row,
  `sessions.last_promo_video_id`: a new session always started from the first promo, and nearly every
  guest of a captive portal is a new session, so a second promo was almost never served. Now: the
  session's location's promo this user has watched fewest times in `video_views`, ties by
  `(priority, created_at)`. Rejected: "the one after the last watched", because it needs the latest
  view, and views are stamped from the ZIO clock — frozen in the suites and equal on ties — so the
  order was not deterministic; counting is. Its cost, accepted: a promo added later is served to a
  returning user until it has caught up with the others. The cursor's column stays, unused: SQLite
  refuses `DROP COLUMN` on a column with a foreign key (`REFERENCES advertiser_videos(id)`, V4), and
  removing it means rebuilding `sessions`.
* **IDs are random UUIDs, not deterministic `uuid5`-from-a-seed.** The deterministic scheme existed
  so re-applying the same YAML was an upsert rather than a duplicate; with explicit CRUD through
  the MCP tools that purpose is gone, so `IdGenerator`'s old role (implicit guardian of every
  entity's natural key) had to move into explicit Scala checks before each write — which is what
  `create_advertiser`'s name check and `create_location`'s slug check are for.
* **`users` has no `location_id`; everything else does.** A user is identified once and recognised
  across every location's portal via the cross-location `captal_user` cookie; sessions, surveys,
  advertiser videos and localized texts are all scoped.
* **A device is its fingerprint, and identity is resolved in `core`** (V27, 2026-10-30).
  `devices.id` was a hash of the User-Agent, so every phone of one model and browser version was
  one "device", and a laptop could be a new one by switching browsers. It is now found by the
  fingerprint UniFi's redirect carries: the click id of the link shortener in front of the portal,
  which tracks devices, and the client MAC. Which one a match compares is configuration
  (`DEVICE_MATCHING`, `ByClickId` by default). The MAC validates itself — access is granted to
  it, so claiming another authorizes somebody else — and is there for when that matters more.
  ** *Matched in the database, decided in `core`.* `Matching` is an inline method on a concrete
     policy object, so the repository splices it into its `filter` and Quill compiles it to a
     `WHERE`. Calling it through the trait does not compile, so a runtime choice is a `match` in the
     repository, one static query per branch. A `match` inside `core` handing the policy to a
     lambda was tried and does not compile: the lambda parameter is typed as the trait.
  ** *Who an email belongs to is `core`'s to say.* `UserPersistenceHandler` used to look the email
     up and swap the session to the existing user, after `core` had already emitted its events with
     a fresh id — so the email answer was stored under a user that was never created, which is
     also why a returning user answering it again never hit the unique index on
     `(user_id, question_id)`. Now `AnswerEmailHandler` asks `UserRepository.findIdByEmail`: a new
     email emits `UserCreated` and its answer; a known one emits `UserRecognized` alone, because
     the answer is the one they gave the first time. `SessionPhaseHandler` moves the session on
     for `UserRecognized` as for an answer.
  ** *Linked each time, trusted per pair.* `DeviceLinked` is emitted whenever a user is identified
     on a device, and `answers` and `video_views` record the device. What a user has done on a
     device is what earns them trust there, so typing someone else's email on your own laptop
     starts at nothing. Both survive the sessions being cleaned up, which the history in
     `sessions` would not.
* **An error is a way out, and a client error costs time** (V28, 2026-10-30). Something breaking
  must not leave a guest without internet. A server error is the server's own record, so its id
  opens a way out at once. A client error cannot be told real from invented: on a phone or tablet
  there is no leaving the page, but on a laptop DevTools can `fetch` from the page itself, with
  its cookie and origin. So it is not judged, it is made slower than going through the flow, and
  fast for whoever has shown they would have gone through it.
  ** *CAPTCHA rejected.* AWS WAF's, or any other, checks that a human is on our page, and someone
     with DevTools open is exactly that. A token redeemed with a CAPTCHA was considered; it stops a
     headless client, not the console of the real page, and the error screen is not a route that
     could require having reached it.
  ** *Validating the message or the stack format against the engine rejected.* Libraries throw
     their own messages, engines and versions word and print them differently, and a guest's
     unusual browser would be punished for it. Checking the message against the phase the session
     is in was also dropped: it is not a superficial check.
  ** *What is checked can only contradict.* A frame from the console, a bundle version the location
     does not serve, a line or column outside the published file: each is something a real error of
     our bundle cannot produce, and multiplies the wait by ten. The same error reported by another
     device in a week divides it by ten. One device, not two: the first version asked for two, but
     the device is the link shortener's `click_id`, which a guest cannot mint, and what the product
     asked for was that it had happened to someone else (2026-10-31).
  ** *The same error is the same name at the same place, not the same message.* The first version
     hashed the message, every frame and the file's full URL, so one error split by engine
     wording, by the path that led to it and by location. It is now the bundle version, the
     error's `name` — fixed by the standard for every engine — and the file name, line and column
     of the first frame of ours, matched exactly. Similarity search over embeddings of the message
     was considered and rejected: a fuzzy match makes the signal that cuts the wait easier to
     fake, the same error in two engines' words is less alike than two different errors in one
     engine's, and a model call per report would sit on an endpoint anyone can call.
  ** *The column as reported, no source map.* Mapping it through a source map would merge an
     error whose column two engines report slightly differently. Left out on purpose: such an
     error is counted per engine, which finds fewer recurrences but never invents one.
  ** *Trust with diminishing returns.* The wait falls as `(1 + n)^-weight` in what was done on this
     device, and grows with the square of recent recoveries. Much history brings it near zero, no
     single answer is worth much, and a guest at `Welcome` with nothing waits the full five
     minutes. History is answers and views, not sessions, because sessions will be cleaned up.
  ** *Effort weighs by kind, the email least* (2026-10-31). The first version counted every answer
     alike and halved the wait per completed phase, so a returning guest typing their email again
     had halved it with one field. Now a video weighs most, its survey's answer less, a profiling
     or location answer less still, and the email almost nothing: answering it again and again is
     what clearing cookies looks like, while profiling answers pile up only over real returning
     visits. In this visit, being identified takes the wait to 1:30 and watching the video to 0:45,
     the numbers the product chose.
  ** *An error that turns out recurrent shortens the wait of those already waiting* (2026-10-31).
     An error a deploy introduces reaches someone first, and that guest, with no history, would
     wait five minutes for a bug of ours. The waiting page asks every ten seconds rather than being
     pushed to: a poll survives the captive-portal browser sleeping and needs nothing between the
     edge and the API, and the waits are minutes. The shortening is a tenth of the wait offered,
     counted from when the error happened, never longer, and the redeem applies it too.
  ** *The final phases are unrecoverable.* In `Ready`, `Recovered` or `Authorized` the error is in
     granting access itself, which a way out would only repeat; the guest is told so and given the
     error's id for staff.
  ** *The way out is a static page, not a view* (2026-10-31). A view is part of the bundle, and the
     bundle can be what failed. `error.html` has its own inline script, learns why it was opened
     from its fragment, and keeps the offer there so a reload resumes the countdown rather than
     reporting the error again. Its copy is fixed in Spanish and English, as the maintenance
     page's: it cannot count on the server for translations.
  ** *Not every error is a way out.* A lost connection, and a part of the bundle that does not
     arrive, have nothing to judge: the guest is offered a retry, and nothing is reported. Checking
     the edge for a missing object, which would make the second verifiable, is left for later. An
     error the window reports only interrupts the flow when its stack names this origin, so an
     extension's, or one typed into the console, does not.
  ** *The wait over, the page redeems on its own.* A tap first was considered; it protects nothing,
     since the redeem endpoint can be called directly.
* **Access expires for the session, not for a user** (2026-10-31). `AccessExpired` was a user
  event, emitted only when `findAuthorizedUser` found a user with an email on the session. Every
  path to `Authorized` used to require identification, so the two coincided, until a way out of an
  error authorized sessions that never gave an email: the scheduler skipped them. The controller
  still dropped the authorization on the `timeLimitMinutes` the grant carries, but the session stayed
  `Authorized` until `/api/status` happened to reset it, the client was not disconnected, and no
  expiry was recorded. Nothing that reacts to the
  event used the user — UniFi revokes the session's MAC, the reset is the session's row — so the
  event moved to `core.access`, with the user optional, and `ExpireAccessHandler` asks the session:
  `Authorized`, and past its own `accessExpiresAt`. The second condition is new, and is what keeps a
  late job from ending an access granted again since.
* **A way out lands in `Recovered`, and only `finish` grants access** (2026-10-31). The redeem used
  to set `Ready` and authorize at once. When the controller failed, or there was none, the session
  stayed at `Ready` with no user, and the client's `ReadyView` called `finish`, which needs one:
  `UserNotIdentified`, the error view, and around again. A phase of its own says where the session
  came from, and lets `finish` require a user from `Ready` and none from `Recovered`. Granting is
  `AccessGranted` in `core.access`, the session's like the expiry: one event the controller acts
  on, so the redeem does no authorizing and retrying is `finish` either way. `UserFinishedProcess`
  stays, from `Ready` only, for what the user watched and answered.
* **A serialisation bug between browser and server is the server's to prove** (2026-10-31). The
  client cannot be believed about one, but it does not have to be: the browser's decoders are
  `messages`, which compiles for the JVM, so the server reads each response the way the browser
  will before sending it, and one it cannot read is its own error, with an immediate way out. The
  other direction cannot happen by construction: property tests show every request the client can
  build is one the server reads, so an unreadable request is not ours and gives no way out.
  ** *Decodes, not equal.* The check asks what the browser asks. Comparing the decoded value with
     the original was rejected: a harmless difference would send a guest out of the flow.
  ** *Not where there is no session.* Health, locales and i18n are not checked: an error recorded
     without a session cannot be left through, and the browser's own report covers them.
  ** *The JVM stands in for the browser.* The decoders run on the JVM in the check and in the
     suites; where Scala.js differs, the gap stays open (see `pending.adoc`).
* **Video files: one row and one key per file, deleted when no playback of it is open** (V25,
  2026-10-30). A replaced file first overwrote the object under the same key and took the video
  out of rotation while it uploaded. A guest's player fetches a video in ranges for as long as it
  plays, so the ranges after an overwrite came from the new file, and out of rotation meant minutes
  without that promo for a large file. Now each file has its own key and row, the newest confirmed
  is current, and the old object goes once no playback of it is open.
  ** *Counting, not time.* Deleting a superseded file after a fixed delay was rejected as risky —
     it can delete a file someone is still playing. The count fails the other way: a guest whose
     end never arrives (the captive-portal browser closed, the phone left the WiFi) leaves a file
     kept too long, never one deleted too soon.
  ** *Playbacks expire, after the file's length plus ten minutes.* Without it, one page dying
     without `pagehide` kept a file for ever. A fixed ten minutes was rejected: a long video, or a
     paused one, would lose its playback and its replaced file with it. Closed, not deleted
     (`expired = 1`), so how often pages die without saying so stays countable. One timer per
     playback, started from the change data capture insert, was chosen over a periodic sweep;
     timers live in memory, so startup starts one for every playback still open.
  ** *A row per playback, not a counter on the file.* A counter decremented twice — the beacon and
     the watched report both arriving — reaches zero with someone still watching. Ending an ended
     playback changes nothing, and a playback left open is visible and can be closed by hand. A
     websocket heartbeat would know who is still watching, at a cost not worth it here.
  ** *Ended by the page.* `pagehide` with `sendBeacon`, the one request a page being torn down can
     still make; it fires on a reload as on a close, so the page keeps the playback in
     `sessionStorage` marked released and a reload starts a new one. A playback held but not
     released is a page that died without `pagehide`, which plays without counting twice.
  ** *Started before the first byte, and only on the current file, in one statement.* Mounting the
     `<video>` starts the download, so the start is posted first. The insert itself checks the file
     is current, and the delete marks a file only while it is not current and has no open playback;
     a check followed by a write would leave a window, and the rqlite driver's transactions batch
     writes, not reads. The same deferral is why `PlaybackHandler` runs after the commit.
  ** *Told by rqlite's change data capture.* A playback ending is what frees a file, and only the
     database sees every one. CDC is configured on rqlited at startup, not registered by the
     backoffice; retries are bounded so a relay that is down cannot fill rqlite's disk, and the
     backoffice runs a pass at startup, on every confirm and on every gap in the feed for what it
     did not hear about.

== The change data capture relay

* **A relay of its own between rqlite and the services that react to changes** (2026-10-31).
  rqlite 10.6.1 takes one CDC endpoint and one `table_filter` per node: `-cdc-config` is a single
  string flag, and the node runs one `cdc.Service`. The second consumer (the API, to shorten
  recovery waits when an error recurs) could not be added to rqlite. Rejected: having the
  backoffice, which received the posts, forward them to the API — it couples the API to the
  backoffice being up and makes the backoffice a broker it is not. Rejected: ZeroMQ — ZIO has no
  official binding (only `zio2-zmq` 0.0.x, from unit-finance/zio-raft) and it would still need a
  process to own the socket. The relay is internal (no route on the ALB), fans out to every
  subscriber, and leaves filtering per subscriber for later.
* **gRPC, one server-streaming method** (`ChangeFeed.Subscribe`), at the user's direction: one
  service exposing one method that returns a stream of events. Generated with Mill's ScalaPB
  contrib module and zio-grpc 0.6.4 (`ScalaPBC` loads `scalapb.zio_grpc.ZioCodeGenerator` through
  `--custom-gen`; `CustomGen("--zio_out", true)` keeps it in the flat package, without which it
  writes to `...protocol.cdc` and nothing compiles).
* **Change sets travel as the JSON rqlite posted** (`ChangeSet.json`), not as protobuf rows: the
  relay reinterprets nothing and a subscriber reads tables and columns as it would from rqlite.
  Only the Raft `index` is lifted out, since it orders, deduplicates and resumes.
* **Deduplicated and resumed by Raft index; a `Gap` when that cannot be honoured.** rqlite
  delivers at least once without ordering guarantees, so the relay publishes an index only above
  the last one and sorts each post. A bounded buffer (`CDC_BUFFER`, 1000) replays what a
  reconnecting subscriber missed; beyond it, or across a relay restart (told by `instance`), the
  subscriber gets a `Gap` and rebuilds from the database. Persisting the buffer was rejected: a gap
  is already handled by every subscriber, and a restart of the relay is rare.
* **Not zio-grpc's `ScopedServer`.** Its release calls `shutdown` and `awaitTermination`, which
  waits for every call to end, and a subscription never ends: the relay never stopped and the test
  that replaces it hung. The relay builds grpc-java's server itself and releases it with
  `shutdownNow`.
* **One relay task.** rqlite's leader posts to the address `cdc.<namespace>` resolves to, and a
  subscriber follows the one it resolved; two tasks would split the posts from the subscriptions.
* **Locally the relay runs on the host**, as the devenv process `cdc` beside the backoffice, as the
  backoffice itself does; LocalStack's rqlite reaches it through `host.docker.internal`.

== Client and bundle

* **`secondsRemaining` (an `Int`), not an absolute `accessExpiresAt` instant, drives the client
  countdown.** "A captive-portal client has had no internet yet and may not have synced NTP," so no
  absolute time is trusted client-side. `accessExpiresAt` was removed from `StatusResponse`
  entirely once this held — the session still stores the instant server-side; only the redundant
  wire copy went, and with it `Instant`'s decoder, the last thing holding `java.time` in the
  bundle.
* **`IsoDate` replaces `LocalDate.parse` on the three date codecs.** Gives up tolerance for date
  formats the wire never sends — the wire is ours at both ends, and `<input type="date">` is
  specified to produce exactly one format.
* **`js.Promise` with a hand-written 15-line `Promises` (`map`/`flatMap`), not
  `scala.concurrent.Future`, for client HTTP.** `dom.fetch` already returns a `js.Promise`; wrapping
  it in `Future` pulled in an executor, a `CopyOnWriteArrayList` and an `AtomicReference` — thread
  -coordination machinery for a runtime with exactly one thread.
* **Route splitting (one JS chunk per view) was adopted knowing the full-funnel cost.** A guest who
  walks the entire funnel downloads *more* total bytes (228,785 vs. 202,952, about 13%) than
  before, because every view now carries its own decoder chunk instead of one shared one. Accepted
  because "the first paint is spent staring at a blank screen deciding whether the WiFi works,
  while the rest arrive while reading a question or watching a video" — and the *API client* had
  to be grouped by the view that calls it first (one `ApiClient` reachable from every view made
  every route and every response decoder eager, moving only 13%→23% of the bundle behind the route
  boundary once decoders were split by view too).
* **Nothing in the published bundle is pre-gzipped any more.** A browser loading an ES module
  imports chunks by the exact path the linker wrote, so a file cannot be renamed to `.gz`.
  CloudFront compresses on the fly (brotli, `compress = true` already the CloudFront default)
  instead, and `publishS3` enumerates whatever the build produced rather than naming four fixed
  files.
* **Vite/Rollup replaced esbuild+terser for the client bundle**, measured slightly better
  (1,854 bytes better on first paint, 7,621 on the full session) and folding the eager half into
  one chunk instead of two; needed at all because per-route code splitting makes Scala.js emit
  more than one module, and Google's Closure Compiler — the thing that actually mangles names for
  size — refuses to run on more than one module. `@scala-js/vite-plugin-scalajs` is deliberately
  *not* used: it wires `sbt` into Vite's dev server, and Mill has already produced the linked
  output by the time this runs.
* **`allowBigIntsForLongs` instead of Scala.js's default 64-bit emulation**, trading arithmetic
  speed (BigInt is slower in a hot loop) for 3,578 bytes — accepted because nothing left in the
  client has a hot loop once the countdown moved to `Int`.
* **One Scala.js linker run for every page `client` serves** (the portal, both MCP App pages, the
  paused page) rather than one run per public module. The cost is known and was measured before
  deciding: a linker run's runtime is sized by the *entire* program and every public module
  imports it statically (not deferrable — the entry instantiates something deriving from
  `Object`), so the two MCP App pages' shared runtime grew from 16,810 bytes gzip standalone to
  91,045 inside the merged run; first download of the upload page went from 10,839 to 94,899 bytes
  gzip. Translated to load time: **+70 ms at 10 Mbps, +408 ms at 1.6 Mbps.** What's bought: the
  paused page reuses the portal's `Layout` without copying it, and there's one Vite configuration
  instead of three. If this is revisited, the thing to re-measure is not chunk boundaries — Rollup
  re-chunks by reachability regardless of linker-level module granularity — it's whether the
  shared-runtime cost (driven by one shared base class, `java.lang.Object`) can shrink at all.
* **`modulepreload` hints are always derived from the built artifact, never from a hand-written or
  server-compiled list.** Chunk names carry a content hash, so a list goes stale on the very next
  publish — "a preload with a hash nobody imports is worse than none, because the browser
  downloads a chunk it will not use." Two implementations exist because two different things
  render the HTML: the portal and paused page are rendered by the *build*, so `preloadLinks` reads
  the entry's real imports at build time; the MCP App pages are rendered by the *server* per
  request, so `AssetStore.scriptPreloads` reads the published entry from S3 and parses its imports
  at request time — and answers empty, not an error, if it can't read it. Both exclude dynamic
  `import()` deliberately, or the portal would eagerly preload every view on first paint, undoing
  the whole point of route splitting. Measured: removes one round trip from the critical path
  (the app mounts 143 ms sooner at 100 ms RTT).
* **The CDN always exists; there is no flag to run without CloudFront.** `AssetStore` invalidates
  unconditionally in every environment, and the distribution is a startup requirement like the
  assets bucket. The previous `cdnEnabled` flag — born because LocalStack Community answered
  CloudFront with a 501 — survived the move to LocalStack Pro (which does serve CloudFront)
  unnoticed and, by construction, guaranteed `createInvalidation`, the poll to `Completed`, and the
  ordering in `pause_location` that depends on the wait actually waiting were *never exercised by
  anything* until they reached production AWS. General lesson recorded for reuse: **a flag
  justified by a missing capability has to be revisited the moment the capability arrives** — this
  one didn't get revisited for an entire LocalStack tier bump.
* **MCP App page scripts are served from the CDN via `<script type="module" src>`, not inlined
  into the HTML.** Both pages used to carry their script inline on the belief that the sandboxed
  iframe's CSP blocks every external host; it doesn't — `resourceDomains` maps to `script-src`,
  and the directive was already in use for the host's fonts. Inlining cost ~9 KB gzip on *every*
  `resources/read`; the CDN version costs that once as a shared, content-hashed chunk (plus a
  stable, revalidating entry per page) rather than a full copy per read.
* **Laminar was adopted for the upload page, then dropped two commits later.** Right call while
  the page rendered a list of pending videos with per-row JavaScript; wrong call once the page
  became strictly single-video and had nothing left to render dynamically — "worth revisiting if
  the question editor arrives," since repeated, per-locale-validated option rows are exactly what
  a framework like Laminar is for.
* **The paused/maintenance page is a Scala.js entry point, not static HTML.** Reuses `Layout`, the
  brand icon and the location's own stylesheet so it looks like the portal it stands in for. It
  talks to nothing — by design, since it's shown exactly when the backend is deliberately absent —
  and its copy lives in source rather than in the i18n database for the same reason. It ships
  inside the release bundle (not written by the pause operation itself) because it has to already
  be in place *before* a pause happens.

== Build, deploy and infrastructure

* **Single-stage Dockerfiles.** Mill builds the jar where Mill already lives; the image just
  packages it, with a dedicated `*.image` task staging the Dockerfile beside the jar so the build
  context is two files, not the whole repository. Rejected: the old multi-stage `api.Dockerfile`
  that re-resolved the entire dependency tree inside the image build on every run (and had rotted
  unnoticed — see `incidents.adoc`).
* **Migration and server start share one `CMD`.** A failed migration stops the container instead
  of starting a server against a schema it wasn't written for.
* **The MCP server migrates its own history table (`db/migration-mcp`), not the API's.** Two
  processes migrating one shared history table race on startup; `Migrate.migrateTo` takes the
  table name as a parameter specifically so the two schemas can stay apart.
* **Migration serialisation uses a lock built on rqlite itself (`Migrate.Lock`), not Flyway's own
  locking, not S3, not EFS, not etcd — for now.** Flyway's lock needs a transaction to hold it and
  rqlite had none usable for most of this project's life (see `incidents.adoc`); even with
  transactions restored, Flyway's SQLite dialect logs "does not support locking" and does nothing.
  The lock is a single `INSERT` of a fixed primary key, decided by *reading back* who landed, not
  by whether the insert threw (both "it threw" and "it affected zero rows" are indistinguishable
  from a lost race under rqlite's silent-rejection behaviour — see `incidents.adoc`). Deliberately
  no heartbeat and no takeover of an abandoned lock: a migrator that dies mid-migration leaves a
  half-applied schema *and* a failed Flyway history row that Flyway refuses to pass until a human
  repairs it, so handing the lock to a new process would not help — it would just be blocked for a
  different reason. **Rejected, explicitly, with the reasoning kept:**
** *S3 with `If-None-Match: *`, or DynamoDB conditional `PutItem`* — both legitimate CAS
   primitives (this is what OpenTofu's own S3 backend lock does), but rejected because "the
   primitive is not the weak part": rqlite's own `INSERT` already goes through Raft, giving the
   same CAS guarantee for free, and swapping stores buys no correctness while adding a dependency
   and its own IAM surface. Crucially, neither one fixes the one real weakness (the abandoned
   lock) either — a TTL-based lease just resolves the wrong problem, since a migrator that is
   merely slow and one that is dead look the same without a server-side session.
** *EFS* — its NFSv4 locks *do* release automatically on client death, which is the one property
   the current design lacks — but EFS only exists in the single-node `dev` topology; prod's Raft
   cluster runs on ephemeral storage. `FileChannel.tryLock` over NFS is also not reliable in the
   JVM.
** *etcd* — the only option on the list offering a true server-side session (a lease with
   keepalive via `jetcd`), and the one to reach for "if this bites": costs an always-on task, a
   Terraform module, and `jetcd` pulling grpc-netty into `platform/`; introduces a new single point
   of failure that blocks every deploy; and still does not solve fencing (a holder frozen by GC
   could wake after losing its lease and keep migrating, since Flyway accepts no token).
** *Removing the container entirely* — running migrations as a one-shot task per deploy instead of
   inside the serving container, with the API only checking a version — needs no lock at all
   (one migrator by construction, and ECS already detects a dead task). Left on the table,
   undone; it is the pattern `mcp.dev`/`api.dev` already use locally (migrate, then serve, as
   separate steps), and the deployed path is the one that diverged from it.
** When to revisit the S3/DynamoDB option specifically: if the lock is ever needed *before* the
   database exists, or when the database itself is unreachable — today, if the database can't be
   reached, migrating is moot anyway.
* **The real OpenTofu configuration is applied against LocalStack for `mcp.test`, replacing a
  219-line hand-built `awslocal` fixture.** The fixture agreed with the deployed topology only for
  as long as someone kept it agreeing, and had already drifted (`modules/alb` had grown rules the
  fixture didn't know about). `environment = "local"` is accordingly a real environment in the
  configuration, not a test-only shim.
* **The LocalStack state directory and the LocalStack container must be born together, and this
  is enforced, not just documented.** The state lives in `.devenv/state/localstack/tofu/<container-id>/`
  (`localStackStateDir`), keyed on the running container's id and outside every task's `dest` — a
  Mill task's `dest` is wiped on re-evaluation, which would discard the Tofu state while the container
  still held every resource it describes. A new container discards the state of every earlier one;
  `resetLocalStack` stops LocalStack and removes its state when the two have come apart. It started as
  a `Task(persistent = true)`, then moved to `out/localstack/`, where `mill clean` could still discard
  it while the container lived; outside `out/` that divergence is gone.
* **`backend.tf` is deliberately not staged into the LocalStack-targeted copy of the
  configuration.** It declares an S3 backend whose bucket the same configuration creates — a
  chicken-and-egg locally — so the local run falls back to Tofu's default local state file.
* **IAM is enforced locally in *soft* mode** (`ENFORCE_IAM=1`, `IAM_SOFT_MODE=1`): every AWS call
  from the test suite is evaluated against the real policy and logged, never denied. Hard mode is
  measured, not guessed, to be unreachable: LocalStack's own IAM-coverage page lists which services
  have enforcement coverage for service-specific condition keys, and ECS is not one of them, while
  this policy gates ECS service calls on `ecs:cluster` and `iam:PassRole` on
  `iam:PassedToService` — confirmed with LocalStack's own `simulate-principal-policy`, which flips
  each from `implicitDeny` to `allowed` purely by supplying the condition key, with an unconditioned
  action in the same policy (`ecs:RegisterTaskDefinition`) allowed either way as a control.
  Dropping the conditions to make hard mode pass was rejected as "weakening a production policy to
  suit a local tool." `CAPTAL_IAM_SOFT=0` exists to retry hard mode once LocalStack's coverage
  catches up. Soft mode alone is not the check — `DeployE2ESpec` reads the denial log back and
  fails on anything outside a named `KnownEmulationGaps` set, and asserts that a deliberately
  withheld permission (`s3:ListBuckets`, or similar) *is* denied, so the check cannot pass
  vacuously by evaluating nothing (see `incidents.adoc`).
* **Infrastructure provisioning was first declared explicitly out of scope for an MCP tool**,
  because the MCP server runs *inside* the VPC the base infrastructure creates — a tool that
  created the VPC would have to run before there was anywhere to run it — and because Terraform's
  value is the state and the plan, which imperative SDK calls have neither of. Per-location deploy
  (register task definition, create/update service, target group, listener rule) was identified at
  the same time as the part that *should* become a tool, since it is incremental on top of a base
  that already exists — and it did, as `deploy_location`/`pause_location`/`resume_location`/
  `destroy_location`.
* **`terraform/` was brought in as a git subtree of the formerly-separate
  `whitelabel-captal-infrastructure` repository**, because `mcp.test` applies this configuration
  against LocalStack, so a checkout of the portal alone was not enough to test the portal. The
  override `terraformDir` still exists for pointing at a working copy elsewhere while editing it.
  Its own nine commits are **not** part of `main`'s linear ancestry — the commit message for the
  move states plainly that preserving them was the cost a subtree *merge* would have added, and
  that cost was not paid — but they remain reachable from the tag `backup/pre-flatten-rewrite`
  (verify with `git log backup/pre-flatten-rewrite`). See `history.adoc`.
* **`modules/vpc` (private subnets, NAT gateway, EIP) was deleted in favour of the account's
  default VPC.** `enable_nat_gateway` defaulted to false and no environment ever overrode it, so
  every task already ran in a public subnet with its own address, isolated by security group
  alone — the private half existed and was paid for (~USD 32/month per availability zone) by
  nobody. What's given up: the private subnet as a second isolation layer behind the security
  groups; a rule written with a CIDR source rather than a group source is now exposed the moment
  it applies. **This decision has not yet been applied to the deployed `dev` environment** — see
  `pending.adoc` for the resulting plan drift.
* **`mcp/` is grouped by MCP's own protocol vocabulary** (`tools/`, `apps/`, `protocol/`,
  `access/`, `resources/`, `aws/`), not by product domain (`video/`, `survey/`, `location/`),
  because cross-entity reads (`EntityResources`, `Readiness`) would otherwise have to live in five
  domain packages at once. `aws/` stays inside `mcp/` rather than moving to `platform/`: the SDK
  adapters are concrete case classes taking clients by constructor, not ports, so relocating them
  would decouple nothing while dragging the ECS/ELBv2/CloudFront SDKs into a module everything else
  depends on. One package-cycle constraint decided a placement: `Prompts` was slated for
  `protocol/` but calls `LocationTools`/`Readiness`/`AssetStore`, while `Readiness` (in
  `resources/`) imports from `protocol/` — a `protocol → resources → protocol` cycle that Scala
  compiles happily and that would make the package boundary meaningless, so `Prompts` sits in
  `tools/` with what it calls instead.
* **`infra/` was renamed to `platform/`.** It held `services/`, `session/`, the Quill schema and
  the repositories — "the application's own machinery, not infrastructure" — while sitting next to
  an actual infrastructure repository, which made the word mean two different things depending on
  which directory you were in.

== The Mill build

Build files: `build.mill` at the root, one `package.mill` per module, and the helpers in
`mill-build/src/millbuild/`. Each entry names the definition it concerns. Failures that led to a
rule are in `incidents.adoc`, section "The Mill build".

* **One `package.mill` per module; `build.mill` keeps only what no single module owns.** It holds
  the `rqlite` image object, the cross-compiled `core-js` and `messages-js` modules, and `ci.run`.
  Each module's file declares its own dependencies, Scala version and tests.
* **Only `mcp` is on Scala 3.10.0; the rest of the build stays on 3.8.0 (`BaseModule` in
  `mill-build/src/millbuild/Modules.scala`).** Scala 3 reads TASTy only from the same or an older
  compiler, so a 3.10 module may depend on 3.8.0 modules but not the reverse. `zio-http-mcp` 0.10.0
  ships TASTy 28.10, which a 3.9 compiler refuses ("expected stable TASTy from 28.0 to 28.9"); its
  predecessors needed 3.9.0 (for 0.8.3) and 3.8.4. Moving the whole build to 3.10 was rejected: it
  breaks Quill (next entry), and `api` writes far more SQL than the backoffice does.
* **Quill 4.8.6 on 3.10 needs `QuillArrow`.** Scala 3.10 made `->` an inline extension method, and
  Quill's parser matches the `ArrowAssoc.->` call that no longer appears in the tree, so every
  `update(_.column -> lift(value))` breaks. Quill 4.8.6 is the last release and predates 3.10, so
  this is permanent. `mcp` compiles because `whitelabel.captal.mcp.QuillArrow` puts the call back.
  Any module moved to 3.10 hits the same failure. Open gap: `pending.adoc`, "Other modules stay on
  Scala 3.8.0".
* **zio-http versions are split by classpath.** `mcp` takes `platform`'s zio-http 3.0.1 up to 3.11.3,
  which `zio-http-mcp` requires; `api` still resolves 3.0.1. `platform`'s `UnifiClient` is the only
  file compiled against zio-http, and the backoffice never loads it because it never authorizes
  guests. Open gap: `pending.adoc`, "The backoffice cannot talk to UniFi yet".
* **`mcp` has its own scalafix config** (`mcp/.scalafix.conf`): scalafix refuses `removeUnused` on
  3.10. `ScalaTests` is its own `ScalafixModule` and does not inherit it, so `mcp.test` sets it too.
* **`izumi-reflect` is forced to 3.0.10 over the 3.0.9 the tree resolves** (`mcp/package.mill`). It is
  on Scala 3.10's pre-upgrade list. Its breakage is invisible at compile time: it supplies `Tag`, so a
  mismatch surfaces as a `ZLayer` that cannot find a service at runtime. The rest of that list is
  either already current (zio 2.1.26, pulled in by 0.10.0) or absent (zio-blocks, neotype).
* **ZIO is 2.1.26 across the build** (2026-10-31). It was 2.1.14 everywhere but `mcp.test`, which
  took 2.1.26 to match what `zio-http-mcp` pulls in. zio-grpc 0.6.4, which the change data capture
  relay and its subscribers speak, requires 2.1.26 too, so every module moved to it rather than
  carry two versions of the runtime.
* **`zio-http-mcp` versions and what they bought.** 0.8.3 added MCP Apps: `ResourceContents` gained
  the `_meta` that carries the CSP, without which the upload page's PUT is refused as `blocked:csp`;
  `McpApps` replaced a hand-rolled `_meta` decorator. 0.10.0 added `TaskExecution`: the tool declares
  its policy and the server decides. `Required` answers `-32021` to a client that cannot poll, instead
  of running synchronously and being cut off by a transport timeout. It also brings `skills/list` and
  `skills/get`; `read_skill` stays anyway, because a primitive existing is not a host handing it to the
  model (see the "Wire format" and "MCP" entries above).
* **`netty-nio-client` is excluded from the AWS SDK clients.** `mcp` builds only synchronous clients
  (S3, CloudFront, ECS, ELBv2, CloudWatch Logs, S3 presigner). The async client would add a second
  HTTP stack beside zio-http's. The failure it prevents is in `incidents.adoc`, "Auth / protocol
  plumbing".
* **`scalajs-dom` is declared directly in `client`.** The MCP App pages use nothing but the DOM. Left
  to Laminar's dependency graph, a Laminar bump could move them without naming them.
* **Vite is pinned and installed beside the task, not in the repository.** `client.jsTools` installs
  `vite@6.0.7` and `terser@5.37.0` with `--no-save` into the task's own directory. The Rollup-over-
  esbuild measurements (1,854 and 7,621 bytes) are in the "Client and bundle" entry above.
* **ESModule output is required for per-route imports.** `NoModule` emits one module and refuses
  `js.dynamicImport` outright. Scala.js runs the Closure Compiler only for a single module: under
  CommonJS a multi-module build errors, under ESModule it skips silently. Hence the Vite bundling
  step, which Rollup scope-hoists and terser mangles (`client/package.mill`, `moduleKind`).
* **`get_css_schema` reads the portal's own stylesheet** (`defaultStyles` in `mcp/package.mill`,
  `client/assets/styles.css`). A hand-kept variable list drifts silently: an operator themes a variable
  nothing honours any more and sees no change.
* **`read_skill`'s index is generated at build time** (`resources` in `mcp/package.mill`), from the
  skill directories. `read_skill` advertises the catalogue in its description, so an index that
  disagreed with the directory would name a skill the model cannot read, or hide one that exists.
* **One constant for the rqlite engine** (`rqliteVersion` in `mill-build/src/millbuild/Rqlite.scala`).
  Every suite container and the end-to-end task definition use it, and production runs that version,
  so moving it means moving the driver too. The test container was 8.36.2 while production ran 10.6.1;
  see "rqlite / JDBC driver silence" in `incidents.adoc`.
* **The rqlite image is built by Mill** (`rqlite.image` in `build.mill`), from
  `docker/rqlite.Dockerfile` and `docker/rqlite-entrypoint.sh`. It was pushed by hand, with its tag in
  each `terraform.tfvars`, so a checkout could not reproduce the image its own configuration deploys.
  `rqliteImageTag` reads the tag from `environments/<env>/terraform.tfvars`, so the tag pushed and the
  tag pulled cannot drift apart.
* **The driver is `rqlite-jdbc` 10.5.2.1 and must pair with the server.** Since rqlite 10.6.0 a failed
  statement carries SQLite result codes, and only this driver decodes them. An error can therefore be
  identified by code rather than by matching its text. Production had drifted to rqlite 10.6.1 while
  the build said 9.1.2 and the test fixture ran 8.36.2: three combinations, none of them the one the
  driver targets.
* **Module versions come from git-cliff with `--context`, not `--bumped-version`**
  (`Released.releaseVersion` in `mill-build/src/millbuild/Modules.scala`). The user-facing rules are in
  `development.adoc`, section "Versions". The failure behind the flag is in `incidents.adoc`.
* **The paths that count toward a version are the source folders too** (`Released`). A Scala.js
  module such as `core-js` has no folder of its own; its sources are `core`'s. `api` and `mcp` add
  their Dockerfiles, and `mcp` also its stylesheet, because both go into the image or the jar, so a
  change to either is a change to the service.
* **Outside LocalStack a version is published once** (`publishImages`). A tag already in its registry
  is that release, built from the commit it was cut from, and is left alone. Locally every build
  replaces the tag, because the local tag is the version being worked towards.
* **A reused tag is invisible to ECS, so locations are restarted** (`rollLocations`). When the digest
  behind the API tag has changed but the tag has not, services already on it are force-redeployed.
  A paused location keeps its task count, so it runs the new image when resumed.
* **The configuration is applied on every release and is never versioned** (`ci.run`). Only the images
  and the client carry versions. The registries are applied first (`-target=module.ecr`, the rqlite
  repository) because a service cannot pull an image that is not yet pushed; then a full plan.
* **Client releases are archived, and each location gets a copy** (`publishClient`). The bundle goes to
  `releases/client/<version>`, then to `bundle/`; rolling back is copying an earlier release back. Each
  location receives `bundle/` except `maintenance.html`, and except its own `brand-icon.svg` when that
  differs from the bundle's. A paused location keeps its maintenance page as `_paused/<slug>/site.html`,
  which resume restores. One CloudFront invalidation of `/*` follows.
* **A release to LocalStack is not a release, so nothing is tagged.** `ci.run` against LocalStack
  skips the tags, and `mcp.dev` runs the same first four steps without waiting for locations to settle.
* **`publishUiScripts` publishes chunks before entries, and never deletes old chunks.** An entry
  published before its chunk is a 404 on `import`, which shows up as a page that loads and does
  nothing. Entries are revalidated, because the server renders their URL as a constant and cannot know
  their content, and a 304 is about 200 bytes against the 9 KB they replace. Chunks carry a content
  hash and are cached for a year. Old chunks stay: a browser mid-session can hold an entry that imports
  a hash this deploy replaced, and CloudFront may serve a previous entry until `s-maxage` runs out.
  Collect them by age, never on deploy. Entries are served with `Access-Control-Allow-Origin: *`, not the
  sandbox origin: a module script is fetched in CORS mode, these files carry no credentials, and the
  sandbox origin is derived from the server's own URL, so pinning it would add a way to break without
  adding protection.
* **`fetchpriority="low"` on the preload hints** (`preloadLinks` in
  `mill-build/src/millbuild/Bundle.scala`). Measured in a throttled browser against the built page: the
  hints move discovery off the critical path, and the app mounts 143 ms sooner at 100 ms RTT and 315 ms
  sooner at 300 ms. Without priority they also start 167 KB of JavaScript ahead of the brand loader,
  which moved first paint back by 88 ms. With `fetchpriority="low"` first paint is 264 ms against 260
  ms without hints, and the mount stays early. That holds at 10 Mbps and stops holding below about
  2 Mbps (`pending.adoc`). The walk is transitive, because a chunk importing another chunk would only
  move the late discovery one level down. Dynamic `import()` is excluded: `localImport` matches only
  quoted specifiers (see the "modulepreload" entry under "Client and bundle").
* **Local S3 copies run inside LocalStack's container** (`s3Copy`). `aws` is not on the PATH Mill
  gives subprocesses, so a dev loop that needed it would work only on machines that happen to have it.
  `docker exec` cannot read a host file, so the file is first copied in with `docker cp`.
* **Cache-Control is explicit: one day, not heuristic freshness** (`publishBundle`). Left unset,
  browsers use roughly a tenth of an object's age, so the staleness window grows the longer a location
  goes without a deploy, and nothing bounds it. HTML is the exception: which HTML file the edge serves
  is decided per request, so a browser that does not ask cannot be told it changed. `s-maxage` gives
  CloudFront 24 hours, and the invalidation every deploy issues clears that copy.
* **Build state lives beside devenv's, not in `Task.dest` or `out/`** (`localStackStateDir`). Mill
  wipes a task's `dest` on re-evaluation and lets a task write only to its own `dest`, so the apply
  runs with the filesystem checker disabled. Not under `out/`: `mill clean` and a second
  `MILL_OUTPUT_DIR` would each start from an empty state against a LocalStack that holds everything.
  It is `.devenv/state/localstack/tofu/`, next to the devenv process that runs that LocalStack.
* **Cache keys include the thing they describe** (`rqliteStamp`, `e2eStamp`, `localStackStamp`,
  `tofuConfig` in `mcp/package.mill`). A recreated container has the same URL, so the container id is
  part of the key; the LocalStack licence is part of its key too, because a cached read of `Task.env`
  replays the first run's value. The stamps are `Task.Input`, which re-runs every invocation.
  `tofuConfig` hashes the `.tf` and `.tfvars` files, because `Task.Sources` cannot cover a
  `CAPTAL_TERRAFORM_DIR` override.
* **Suites that share a schema get their own container, and the end-to-end spec its own database**
  (`api.test`, `mcp.test` in their `package.mill` files). A suite on a shared schema clears another's
  rows. Advertisers and the three identification surveys are deployment-wide, so `get_location_readiness`
  on a shared database counts what every other spec wrote. Migrations run once per container, through
  `Migrate` and `McpMigrate`, never through a Flyway built in the test (see "Concurrent migrations" in
  `incidents.adoc`).
* **Test fixtures stand in for configuration deliberately** (`forkEnv` in `mcp/package.mill`).
  `PUBLIC_BASE_URL` is `https://portal.test`. `UNIFI_PROXY_URL` stands in for the Tailscale proxy output
  the local configuration does not have. The end-to-end spec asserts that a deployed task carries it,
  and an unset value could not tell a forwarded value from a missing one. `CLOUDFRONT_DISTRIBUTION_ID`
  comes from the real output of the applied configuration; it used to be made up, needed only because
  `AssetStore.layer` requires the name. The database is created and migrated outside any deploy,
  because `DB_URL` is a value the server knows in advance and injects into every task definition it
  registers.
* **The MCP App protocol strings are asserted against the shipped artifact** (`resources` in
  `mcp.test`). `UploadUiSpec` checks `ui/initialize`, `tools/call` and `ui/message` against the bundle
  carried as a test resource, not against the server's resources. A production jar holding a copy would
  put the two out of step. These strings fail silently: a bad envelope is ignored by the host, and a
  missing `ui/message` leaves the agent waiting for a confirmation that already happened.
* **LocalStack is pinned to one version for both editions.** `localStackVersion` is `2026.9.1`, read as
  `localstack/localstack-pro` with a licence and `localstack/localstack` without, so a developer with a
  licence and one without run the same LocalStack. The version is a date now: LocalStack refuses a
  licence on images older than the one it requires (see "The Mill build" in `incidents.adoc`).
* **Licensed services are listed explicitly** (`licensedServices` in
  `mill-build/src/millbuild/LocalStack.scala`). `ecs` and `elbv2` are available from the Base plan:
  57 of 77 ECS operations and 38 of 51 ELBv2 operations, including every call this repository makes.
  `ec2` is for the fixture, since a VPC, subnets and a security group must exist before a load
  balancer or an awsvpc service accepts them. `efs` backs the single-node rqlite, `secretsmanager`
  holds the admin token, `servicediscovery` is the namespace rqlite is reached through, and `ecr` is
  where the images come from. `route53` is never called directly, but
  `servicediscovery.CreatePrivateDnsNamespace` refuses without it, because a private namespace is a
  hosted zone. Without a licence only `s3` is started.
* **Local dev tooling has its own choices.** `--tunnel` uses Cloudflare quick tunnels, because they need
  no account and no configuration (`mill-build/src/millbuild/Tunnels.scala`); a tunnel's URL is kept for
  as long as its process runs, which is why a running tunnel is reused rather than reopened. With a
  tunnel the admin token is the same fixed `dev-token` (2026-10-30): a token random on every run
  forced the connector to be registered again on every restart, even with the tunnel's address kept.
  Accepted knowingly — the server is public and the token is in the repository — for a dev-only server
  holding dev data; a token derived by HMAC from a secret in `.env` and the tunnel's host was proposed
  and deferred. Without a tunnel it is the fixed
  `dev-token`, which is copied by hand into `.mcp.json`, and a token that changed every run would be
  copied wrong more often than it would be secure. Two tunnels, for the server and for LocalStack,
  because the MCP App pages render on the host's public origin and load scripts from, and upload to,
  LocalStack directly. Scripts are read from the bucket rather than the distribution, because LocalStack's
  gateway refuses a distribution request carrying an `Origin` it does not know, and a page in a host's
  frame always sends one.
* **`ReleaseTarget` is read from the environment, not from a file** (`mill-build/src/millbuild/Release.scala`).
  `CAPTAL_ENV` names the environment; `AWS_ENDPOINT_URL` set means LocalStack, and the region falls back
  from `AWS_REGION` to `AWS_DEFAULT_REGION` to `us-east-1`. Outside LocalStack, `ci.run` runs under the
  CodeBuild role, which needs Docker in privileged mode, `tofu`, `git-cliff`, the `aws` CLI, a clone with
  its tags, and permission to push tags.
* **`messages` depends on `core`, never the reverse.** `ApiError` is an HTTP error vocabulary
  (`{"error": …, "data": …}`), and `core` must not know one. The types lived in `core.codecs` for part
  of the refactor, which is why the direction was checked. `-Xmax-inlines:64` is needed for the
  derivation (see `incidents.adoc`, "The Mill build").
* **The Scala.js entry points are a single `client` linker run** (`client/package.mill`). The portal,
  the maintenance page and the MCP App pages share one run, which removes a Vite configuration and lets
  the paused page reuse the portal's `Layout`. The measured cost is in the "Client and bundle" entry
  above.
* **The build is split by module, with its helpers in the meta-build** (2026-10-29). A `package.mill`
  per module folder, so each module's build sits with its code; helpers and shared traits in
  `mill-build/src/millbuild/*.scala`, which is where Mill's own repository keeps them and which Mill
  compiles with no `mill-build/build.mill`. Rejected: helper `*.mill` files next to `build.mill` (they
  crowd the repository root), and a helper folder with its own `package.mill` (that makes it a module,
  `build.<folder>`). `core-js` and `messages-js` stay in `build.mill`: they have no folder, and moving
  them under `core`/`messages` would rename them on the command line.

== Long-running local processes

* **They run under devenv's process manager, started and stopped by Mill** (`devenv.nix`,
  `mill-build/src/millbuild/Processes.scala`). The problem: `mcp.dev` ended in a blocking call, so for as
  long as the server ran it held Mill 1.1.2's daemon-wide lock and every other `mill` command waited.
  Mill commands now prepare a process — compile, apply, write its command and environment under
  `.devenv/state/processes/<name>/` — have devenv (re)start it, wait for it to serve, and return. The
  user still runs only Mill: CodeBuild runs `mill ci.run` without devenv, and wrapping every Mill
  command in a devenv task would lose `__` selectors, `show`, `-w` and Mill's caching.
* **Not Mill workers, measured on 1.1.2, 1.3.1 and 2.0.0-M2.** A `Task.Worker` is closed whenever the
  build's compiled classes change, any edit to any task included (`MillBuildBootstrap.scala`, 1.1.2,
  lines 307-341; measured with a worker whose `close()` logs). Its `dest` is wiped whenever it is
  re-created, in a new daemon too, because `Worker` fixes `persistent = false`
  (`GroupExecution.scala:313` in 1.1.2, `:441` in 1.3.1). The docs' "Workers can also make use of
  their `Task.dest` folder as a cache that persists" does not hold: Mill's own compression-cache
  example, run as written with `--no-daemon`, recompresses instead of reading "from disk" on all
  three versions. The daemon exits after 30 minutes without a client (`mill.server_timeout`), os-lib
  kills what it spawned on exit, and from 1.3 the daemon closes every worker on exit too. A worker
  that owned LocalStack would have taken it down on every build edit and every idle half hour. A
  `persistent` worker is possible only by subclassing `Task.Worker` and memoizing it with
  `cachedTask` by hand, outside the macro — `Task(persistent = true).Worker` does not exist.
* **OpenTofu stays in Mill.** An apply ends, it is part of the release CodeBuild runs without devenv,
  and it is interleaved with tasks Mill owns: the image tags are the versions git-cliff computes, and
  the registries are applied, the images pushed into them, then the rest.
* **A process is alive when the pid its launcher recorded is, not when devenv says so.** devenv 2.1.2
  keeps reporting `exited` after `devenv processes restart` until the restarted process first passes its
  readiness check, and forever without one; `devenv processes start` on an exited process does nothing.
  The launcher in `devenv.nix` writes `$$` before it `exec`s, so the pid is the command's own.
* **Only a new command or environment restarts a process.** Comparing the written files decides it;
  the readiness check is excluded, because restarting LocalStack for a new check discards every
  resource the configuration made.
* **The LocalStack licence reaches the container by name only.** The manager is started with the
  task's environment plus `LOCALSTACK_AUTH_TOKEN` (`.env` names it `LOCALSTACK_TOKEN`), processes inherit
  it, and the container gets `-e LOCALSTACK_AUTH_TOKEN` with no value — the token is in no file and on
  no command line. A manager started without it runs LocalStack unlicensed until it is restarted.
* **Kept as containers rather than devenv services.** LocalStack, the test databases and the tunnels
  are what the build already ran; devenv only supervises them. LocalStack's own persistence
  (`PERSISTENCE=1`, Base or Ultimate plan) would let a recreated container keep its resources; the plan
  this project's licence is on was not checked.

== Comments vs. documentation

* **A comment answers "what does this do and what breaks if you touch it"; `docs/context/`
  answers "why this way and not the other."** The test for which one a paragraph belongs in: if it
  survives someone changing the decision, it's a comment; if it stops making sense, it was
  documentation. Stated reason this split exists at all: "this repo comments heavily for a good
  reason, almost everything here fails silently, but comments that argue a decision with
  measurements grow until they bury the code." `platform/Migrate.scala` went from 130 comment
  lines to 51 against the same 143 lines of code once its argument moved here.

== Client loading UI — rejected alternatives

Written up here because the architecture doc (xref:../client.adoc[]) describes only what shipped,
not what was tried first. The
current mechanism: a permanent `.nav-loader` overlay (never unmounted) plus per-view `Layout`
loading state, with a `breathe` opacity pulse (`0.65↔1`, 1.4 s, no scale change — specifically
requested) while loading and a one-shot `brandGlowFlash` `drop-shadow` on completion.

* **A spinning ring (`ring-arc` + `ringSpin`) was the original approach, and was dropped.** Its
  arc has a visible *direction* at any instant, so two ring elements in different DOM nodes
  (initial page loader → nav overlay → view) showed different phases on handoff, producing a
  visible jump. A `syncSpin` fix — copying `currentTime` between nodes via the Web Animations API —
  was tried and found fragile (needed a "donor" arc always present; failed differently on mobile
  Firefox) before the team switched to a non-directional animation (`breathe`) instead of patching
  synchronisation further.
* **SVG `<mask>`-based ripples, animated per-circle, were tried and dropped** because doing it
  properly meant duplicating the brand icon's own SVG paths in Scala — but the icon is
  per-tenant-configurable (each location uploads its own SVG via `set_location_icon`), so nothing
  about its paths can be hardcoded.
* **A generic CSS `mask-image: url("brand-icon.svg")` ripple approach was tried next and also
  dropped**, for two reasons: the `mask-image` URL in an external stylesheet resolves against the
  stylesheet's own path, not against the page's `<base href="/<slug>/">`, so it had to move into
  an inline `<style>`; and Firefox did not render the layered, masked composite consistently.
* **A "jar with waves" / rain visual was mocked up as a richer alternative and never built** — the
  team judged `breathe` sufficient and prioritised fixing the real `<video>` double-fetch bug
  instead (see `incidents.adoc`). The mockups were ephemeral scratch files and no longer exist.
* **Among glow implementations, CSS `filter: drop-shadow(...)` via `@keyframes` won on
  cross-browser grounds**, not aesthetics: an SVG `<filter>` (`feGaussianBlur` + `feColorMatrix` +
  `feMerge`) rendered correctly in Chromium but not consistently in Firefox when combined with SMIL
  animation; stacking 3–4 copies of the icon with increasing stroke-width and decreasing opacity
  produced visible concentric rings rather than a soft glow. The plain CSS `drop-shadow` keyframe
  is what Firefox renders correctly, and it is what shipped.
