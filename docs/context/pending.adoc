= Pending work

Work that is known, decided or diagnosed but not finished. Each entry says what is true now, what
is wrong with it, and what settling it would involve. Nothing here is speculative — every claim was
verified against the configuration or the code at the path given.

== rqlite: production selects FARGATE_SPOT

`terraform/modules/rqlite/main.tf`, in `aws_ecs_service.rqlite`:

[source,hcl]
----
capacity_provider = local.single_node ? "FARGATE" : "FARGATE_SPOT"
----

`single_node` is `var.desired_count <= 1`. `environments/prod/terraform.tfvars` sets
`rqlite_desired_count = 3`, so production resolves to Spot and dev — one node — resolves to
on-demand. The branch with less redundancy has the more reliable compute.

The comment justifies it as tolerating "individual node loss", which Raft and the S3 backup do
cover. Spot reclamation is not individual: AWS reclaims on capacity pressure in a pool, so three
Spot tasks share the signal. With quorum 2 of 3, losing two at once stops the cluster — no leader,
no writes. Storage is ephemeral, so each lost node returns empty and rebuilds rather than catching
up from its own log.

Not yet applied to production: the deployed state predates this configuration. A `tofu apply` moves
it onto Spot.

To settle: decide the cost question. Three on-demand removes it; two on-demand and one Spot keeps
quorum through a single reclamation.

== rqlite: continue_on_failure turns data loss into a healthy boot

`docker/rqlite-entrypoint.sh` writes one backup config used for both `-auto-backup` and
`-auto-restore`, with `"continue_on_failure": true`. The comment justifies it for a missing backup
on first boot, which is a development concern; the entrypoint does not distinguish environments.

In production that means: if all three nodes are replaced together and the S3 backup cannot be
downloaded — object deleted, permission broken, bucket misconfigured — the cluster does not fail.
It boots empty, answers its health check, and the load balancer marks it good. A portal then serves
with no surveys, no locations and no users.

`false` is the correct value for production: the task should die rather than serve an empty
database.

`backup_interval` defaults to `1m` (`terraform/modules/rqlite/variables.tf`) and neither dev nor
prod overrides it, so one minute of writes is the RPO on total cluster loss.

== The VPC change is configured but not applied

Commit `49eed79` deleted `terraform/modules/vpc` (164 lines across three files) and rewrote
`main.tf` to consume the account's default VPC through a data source. The reasoning is sound — the
module was building private subnets, route tables, an EIP and a NAT gateway that nothing used, at
roughly USD 32/month per availability zone, because `enable_nat_gateway` defaulted to false and no
environment set it.

It was never applied. Deployed dev lives in the VPC the old module created; the configuration now
resolves a different VPC id. A `tofu plan` against dev reports:

----
Plan: 33 to add, 8 to change, 48 to destroy.
----

Twenty of those are replacements cascading from one line:

----
~ vpc_id = "vpc-06aaccfb0c4d74832" -> "vpc-0f401994632773082"  # forces replacement
----

Six resources carry `vpc_id` in their identity (the security groups for ecs_tasks, alb, dispatcher,
rqlite and tailscale_proxy, plus the service discovery namespace); the rest follow from a changed
`security_group_id`, `namespace_id` or `zone_id`. The remaining 28 destroys are resources the
configuration no longer declares — the `releases` bucket, the `captal-provision` and
`captal-locations` ECR repositories, the `derived` lifecycle policies — which is the cleanup from
commit `53a5e94`.

Consequence to know: applying this to a live environment replaces its network-attached resources. A
destroy-and-rebuild is fine; an in-place upgrade is not.

What the change gave up, per the comment on the data source: the private-subnet option. Every ECS
task now runs in a public subnet with its own address, isolated by security group alone. A rule with
a CIDR source rather than a group source is exposed the moment it applies.

== Destroying an environment does not come clean

Verified in `terraform/`:

* No `force_destroy` on any of the four buckets — `s3-backend/terraform_state`,
  `rqlite/rqlite_backup`, `cli-releases/releases`, `cloudfront/assets`. A destroy fails on any that
  holds objects.
* Three have versioning enabled, so `aws s3 rm --recursive` is not enough: object *versions* and
  delete markers have to go too, via `list-object-versions` and `delete-objects`.
* `modules/s3-backend` carries `prevent_destroy = true` on the state bucket. Tofu refuses it, which
  is correct while that bucket holds the state being used.
* `modules/ecr` declares no `force_delete`, so a repository holding images fails.
* Per-location target groups and listener rules are created by `DeployTargets.ensureTargetGroup`
  with the AWS SDK, not by tofu. They are absent from state and survive a destroy, pointing at an
  ALB that no longer exists.

`aws_s3_bucket.releases` holds CLI releases — content, not replaceable infrastructure. Anything in
it that exists nowhere else should be copied out before a destroy.

== ensureTargetGroup never corrects an existing target group

`mcp/src/whitelabel/captal/mcp/aws/Deploy.scala`. `healthCheckPath(slug)` is `/$slug/api/health`
and is passed only to `createTargetGroup`:

[source,scala]
----
find.flatMap:
  case Some(arn) => ZIO.succeed(arn)   // exists: returned untouched
  case None      => createTargetGroup(... .healthCheckPath(targets.healthCheckPath(slug)) ...)
----

Nothing in `mcp/` calls `modifyTargetGroup`. A target group created with a different path keeps it,
silently. That matters because the portal no longer serves `/api/health` unprefixed — see the slug
prefix entry in `decisions.adoc` — so a group still probing the unprefixed path marks every task
unhealthy.

The ALB module's own default target group uses `var.health_check_path`, default `/api/health`, and
no environment overrides it. Two target groups with two different paths, only one of which the
server answers.

== The slug prefix has no test coverage

`ApiBase` puts the location slug into each `Endpoint`'s `RoutePattern`. `TestLayers` provides
`ApiBase.none`, so the suite only ever exercises the unprefixed form. The prefixed form was verified
by starting the dev server and asking for both paths; nothing in CI would catch a regression.

Covering it means either a suite that builds the routes with a slug-bearing `ApiBase`, or accepting
that this stays a manual check and saying so where someone will read it.

== The browser's decoders are only checked on the JVM

`WireContractSuite`, `ClientDecodeSuite` and `WireCheck` read responses with the browser's circe
decoders compiled for the JVM. The browser runs them compiled to JavaScript, and Scala.js differs at
some edges: `Long`, number formatting, `java.time` through `scala-java-time`. A response that passes
on the JVM and fails in the browser reaches the guest as a client error report, with its wait.

Covering it means running the contract's values through the decoders on Scala.js: a test module for
`client`, or for `messages-js`, which needs a JavaScript runtime in the build.

== Nothing pins the images prod would run

`prod/terraform.tfvars` names `rqlite_image_tag = "1.0.8"`, as `local` does (2026-10-31), but no
release has run against AWS: what prod's rqlite runs is whatever was last applied by hand, likely the
variable's old default `1.0.0`, which captures no changes at all. `image_tag`, `mcp_image_tag` and
`cdc_image_tag` are the modules' versions, which `ci.run` passes; no `api/v*`, `mcp/v*` or `cdc/v*`
tag exists, and every image in a deployed environment was pushed by hand. The first `ci.run`
against prod replaces every rqlite node: check the backup bucket holds a recent version first.

== First paint on slow links waits on brand-icon.svg

At 1.6 Mbps first paint is 980 ms with or without the preload hints. It tracks `brand-icon.svg`, which
finishes at 965 ms: the loader has no text, so the first contentful paint is that 730-byte image. It
needs a round trip of its own and queues behind the bundle on a saturated pipe. It was already 756 ms
before the hints; they exposed it rather than causing it. The fix makes first paint depend on the
document alone: the icon inline as a data URI, the loader's rules in a `<style>`, and `styles.css` out
of the render-blocking path. First paint would then be one round trip, better than it has ever been.
Not done, because the venue connections are not 1.6 Mbps and at their speeds there is nothing left to
win. Revisit if the connections change. Measured against the hints in `preloadLinks`
(`mill-build/src/millbuild/Bundle.scala`); see "Client and bundle" in `decisions.adoc`.

== The backoffice cannot talk to UniFi yet

`mcp` resolves zio-http 3.11.3, which `zio-http-mcp` requires, while `platform`'s `UnifiClient` is
compiled against 3.0.1. The backoffice never loads that class today because it never authorizes guests.
Calling a UniFi controller from it needs the two versions aligned first, or it fails at runtime with a
`NoSuchMethodError` rather than at compile time. See `decisions.adoc`, "The Mill build".

== Other modules stay on Scala 3.8.0

Only `mcp` is on Scala 3.10.0. Quill 4.8.6 is the last release and predates 3.10, so every module moved
there would need a `QuillArrow`-style shim on each `update` assignment; `mcp` has one (see
`decisions.adoc`, "The Mill build"). Revisit when Quill ships a release for 3.10, or when the repositories
stop depending on it.

== The dev servers run on the build's own output

`mcp.dev` and `api.dev` start `java -cp <runClasspath>`, whose entries are folders under `out/`. A
compile while a server runs — `api.dev` recompiling `core` while the backoffice serves — rewrites
classes under a running JVM, and `mill clean` deletes them. Planned: Mill 1.3, whose locks are per
task rather than daemon-wide, and devenv running the servers through a Mill command instead of the
bare classpath. Whether 1.3 keeps a running command's read locks on its upstream tasks, which is what
would stop that recompile, has not been checked.

== The editor's build import starts the local fixtures

Metals, through Mill's BSP server, evaluates the test modules' `forkEnv`, and `mcp.test`'s depends on
`localStackStamp` and `localStackInfra`: an import after a build edit starts the test databases and
LocalStack and applies the local configuration (see `incidents.adoc`, "Long-running local
processes"). The setup would have to move out of `forkEnv` into the test commands themselves.
