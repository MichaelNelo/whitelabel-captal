= Plan: the relay hands its fan-out to SNS and SQS
:toc:
:toclevels: 2

A plan agreed in conversation on 2026-11-13 and revised on 2026-11-22, once its first step — checking
the documentation — had been done (<<verified>>). The change data capture relay stops keeping change
sets: it publishes each one to an SNS topic per table it touches, and every task that reads them has
an SQS queue of its own subscribed to the topics it reads. The relay becomes stateless, so it deploys
overlapped, and the gap of one to two minutes on every relay deploy goes away. Pick it up from
<<migration>>, step 2.

== The problem

The relay (`cdc`) receives rqlite's change data capture over HTTP and fans it out to its subscribers
over a gRPC stream, keeping the last `CDC_BUFFER` (1000) change sets in memory for those that
reconnect (xref:../cdc.adoc[Change data capture relay]). Because that history lives in one process:

* It deploys stop-then-start (`deployment_minimum_healthy_percent = 0`, `modules/cdc/main.tf:138`).
  Two relays at once would split rqlite's posts: a subscriber that connected to the new one while
  rqlite still posted to the old misses those change sets with no `Gap`, since its instance never
  changed. DNS cannot coordinate the switch — `cdc.<namespace>` lists both tasks during an overlap,
  ECS registers a task while it is still `ACTIVATING`, and an open connection never resolves again.
* So every relay deploy leaves one to two minutes with no live feed. rqlite retries its posts, and
  every subscriber gets a `Gap` from the new instance and rebuilds what it derives from the
  database. Nothing is lost unnoticed; nothing arrives live either, and every subscriber does the
  rebuild.

What was considered on the way here, and why it was not taken:

[cols="1,3"]
|===
| Option | Why not

| An ALB in front of the relay
| It moves no open stream (a deregistering target's connections end, and the client reconnects
  anyway); its idle timeout ignores HTTP/2 PINGs, cutting quiet subscriptions every 60 s to 4,000 s;
  gRPC needs an HTTPS listener; and it would round-robin rqlite's posts between two relays,
  splitting them.

| Fan-in in the follower
| Every subscriber follows every relay address, with a cursor per relay and duplicates dropped by a
  set of seen indexes. Works, but keeps the history in relay memory and puts the complexity in every
  subscriber.

| Explicit handoff between relays
| The old relay, on SIGTERM, hands its buffer, its last index and its instance id to the new one
  (which starts on standby), answers rqlite with `307` to the new one, and closes its streams. Works,
  given what rqlite does (below), but it is a protocol of our own to keep correct, and the `Gap` and
  instance-lineage machinery stays.

| RabbitMQ
| Moves the problem to the broker, whose own redeploy needs a quorum-queue cluster — on Fargate a
  second rqlite to operate — or Amazon MQ's three brokers.

| NATS JetStream
| Solves the relay's redeploy (the relay becomes a stateless bridge, consumers resume by themselves),
  but NATS is then the stateful service: one node is down while it restarts, and no downtime needs a
  three-node R3 cluster, since Raft needs a majority (two of three) to keep serving.

| Kinesis
| Managed, but its push (enhanced fan-out) admits few consumers per stream and shared reads are
  limited per shard: it does not fit one consumer per location. (Limits from memory, not re-checked.)

| API Gateway or a Lambda instead of the relay
| No process of our own at all, but rqlite cannot sign AWS requests, so the endpoint has to be a
  private API (an interface VPC endpoint, about USD 7.20 a month per AZ) or a public URL with a
  secret in it. Keeping a relay inside the VPC keeps rqlite's endpoint and its security group as
  they are, for about USD 7–9 a month.

| Redpanda Connect, Hookdeck, Svix
| A configured bridge instead of our relay (still a process), or a SaaS that takes the data out of
  AWS and needs a public endpoint per subscriber.
|===

== What rqlite does

Read from rqlite 10.6.1's documentation and, where the documentation is silent, its source
(`cdc/service.go`, `cdc/sink.go`, `cdc/config.go`); the design depends on these:

* One POST in flight: only the leader sends, from one loop that does not move on until the batch is
  sent or dropped. Within one leader, batches go out in Raft index order.
* Success is HTTP 200 or 202 only (`sink.go`); anything else is retried. 307 and 308 are followed
  with the POST kept; 301–303 are refused.
* With our configuration (`transmit_retry_policy: 1`, exponential, `transmit_max_retries: 10`,
  `transmit_max_backoff` 60 s; minimum backoff unset, so 1 s) a batch is tried 11 times over about
  362 s and then *dropped*, the high watermark moving past it — not in the documentation.
* A batch holds up to 10 index groups, sent after at most 200 ms (`DefaultMaxBatchSz`,
  `DefaultMaxBatchDelay`). Each POST times out after `transmit_timeout`, 5 s by default.
* A leader change can resend batches the old leader had sent, and can deliver out of order; the
  documentation asks handlers to be idempotent and to tolerate it.
* rqlite caches no DNS itself. Whether it reuses connections is not settled by its code.
* The CDC configuration is read once at startup, per node; there is no SIGHUP or HTTP route to
  change it. Changing the table filter means restarting rqlite, which the user accepted: the new
  cluster takes no writes until the previous one is down.

platform version `1.4.0`, an environment variable named `ECS_CONTAINER_METADATA_URI_V4` is injected
into each container in a task", on by default, and `${ECS_CONTAINER_METADATA_URI_V4}/task` answers
`TaskARN`, `Family`, `Cluster` and, for a task of a service, `ServiceName`
(https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4-fargate.html[endpoint
v4 on Fargate],
https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-metadata-endpoint-v4-fargate-response.html[its
response]). No service here sets a platform version, so each runs on `LATEST`. LocalStack's ECS
does not inject it: a task it ran had `AWS_ENDPOINT_URL`, `LOCALSTACK_HOSTNAME` and

queue's name takes a random id, and nothing depends on the task's own (<<one-queue-per-task>>).

What an orphan costs — the queue of a task killed without SIGTERM, which nothing removes: queues do
not expire (`DeleteQueue` says nothing of idle queues; only an old SDK page "reserves the right" to

https://aws.amazon.com/sns/pricing/[SNS pricing]). Whether each delivery counts as an SQS request is
not settled; counted as one, an orphan of the backoffice costs about USD 0.01 a month at today's two
locations and 0.48 at twenty, and one of a location nearly nothing, errors being rare.

== The design

----
                         captal-<env>-cdc-video_playbacks ─┬─► queue of backoffice task A
rqlite ─POST─► relay ─►                                    └─► queue of backoffice task B (in a deploy)
   (one in flight)  (stateless)
                         captal-<env>-cdc-errors ──────────┬─► queue of <slug-1>'s task
                                                           └─► queue of <slug-2>'s task …
             one standard topic per table, one queue per task, no filter policies
----

=== The relay

For each change set in rqlite's post:

* publish it to `captal-<env>-cdc-<table>` for every table it touches — once per table, so a change
  set touching two tables reaches both topics whole;
* with the trace context as message attributes (`traceparent`, `tracestate`), so a change's trace
  still reaches every subscriber;
* answer rqlite 200 only once SNS has accepted every publish of the post; if it did not, answer 503
  and rqlite retries the post.

The topics are standard: no subscriber needs the order between change sets, nor to be spared a
repeated one (<<the-subscribers>>), and a FIFO topic admits 100 subscriptions, too few for one per
task. A table rqlite publishes and no topic exists for is a defect, logged and answered 503.

The relay keeps nothing: no buffer, no `Gap`, no instance id, no gRPC. It deploys overlapped — a
container health check on `/health`, `deployment_minimum_healthy_percent = 100` and
`deployment_maximum_percent = 200`, and a `stopTimeout` long enough to finish a post in flight. One
task is enough: if it dies, rqlite retries for about six minutes while ECS starts another.

A batch rqlite drops after those six minutes is lost to every subscriber, and nothing tells them:
there is no `Gap`. Each finds out only when it next starts and rebuilds. Today's relay answers that
with a `Gap` from the instance that replaced it.

=== Why both SNS and SQS

[cols="1,2,2"]
|===
| | Does | Lacks

| SQS alone
| A durable queue: keeps messages until someone processes and deletes them
| Each message is consumed by one reader. Fanning out to every task means the relay sending to every
  queue: knowing them, keeping the list current as tasks come and go, and retrying when three of five
  sends succeeded — reimplementing SNS.

| SNS alone
| Fan-out: publish once, delivered to every subscription
| Keeps nothing per subscriber: an HTTP subscriber that is away is retried for a while and then
  dropped, and every task would need an HTTPS endpoint.

| SNS then SQS
| SNS fans out once; each task has its own queue, which keeps what is pending and lets it go at its
  own pace
|
|===

[[one-queue-per-task]]
=== One queue per task, one topic per table

A queue is one reader's cursor: readers sharing a queue split its messages between them. An ECS
deploy runs the outgoing task beside the incoming one — 100/200, the default for the backoffice
(`modules/mcp` sets none) and explicit for a location (`Deploy.scala`, `deploymentConfiguration`) —
for as long as the incoming one takes to pass its checks and the outgoing one to drain. A playback
that starts then, whose message the outgoing task takes, would be timed in the memory of a process
about to stop, after the incoming one had already read the database. So every task has a queue of
its own, and each gets every message of the topics it reads.

The table is the topic, not a filter policy on one topic: a task's subscription is new on every
start, and a new filter policy takes up to 15 minutes to apply, delivering who knows what meanwhile.
A task reading two tables subscribes its queue to both topics. Publishing a new table adds it to
rqlite's filter and adds its topic.

A queue's name is `captal-<env>-feed-<service>-<random id>`, the service being `mcp` or a location's
slug, which can never be `mcp`: the name only has to be unique, and LocalStack gives a task no id of
its own. The `feed` segment keeps the permissions on these queues apart from every other queue
under `captal-<env>-`. A name has at most 80 characters, so a long slug is shortened with a digest, as
`DeployTargets.targetGroupName` does; the id is 32 hexadecimal characters, so a location's queues are
told from those of a slug that extends it (`x` and `x-y`) by the whole name, not the prefix.

[[the-subscribers]]
=== The subscribers

[cols="1,1,1,3"]
|===
| Subscriber | Topic | Retention | Does

| Every task of a location's API (`RecoveryFeed`)
| `cdc-errors`
| 60 s
| Each `INSERT` wakes every page waiting on this task, which checks its offer again against `errors`
  and hears of it only if it changed. A message is a doorbell, not data: consumed and forgotten. One
  older than a minute serves no page — a page connecting later checks as it connects — and one
  repeated or out of order checks to the same answer, since a shortening is recorded once
  (`OpenOffer.current`).

| Every task of the backoffice (`VideoFileCollector`, `PlaybackExpiry`)
| `cdc-video_playbacks`
| one hour
| An `INSERT` of an open row starts its playback's timer; an `UPDATE` setting `ended_at`, or a
  `DELETE`, cancels it; any change asks for a collection pass. A repeated `INSERT` finds its timer
  running (the map of timers), an old one finds its playback closed (`OpenPlaybacksQuery`, read
  before sleeping), and either schedules nothing.
|===

A timer lives in the memory of the task that started it, and the database says which timers there
should be: one per open playback, with its deadline. So each backoffice task rebuilds its timers from
the database as it starts, and the queue tells it what happens after; recording which timers run
would record a process's memory, false as soon as the process dies.

[[startup]]
=== Each task subscribes itself

A task declares the topics it reads, next to the code that reads them, as `ChangeFeedFollower` does
today with `since`. As it starts:

. it creates its queue, standard, with its retention, a visibility timeout of a few seconds and its
  kind's dead-letter queue for messages it cannot process — `captal-<env>-mcp-dead-letter` for the
  backoffice's tasks, `captal-<env>-locations-dead-letter` for every location's, the locations not
  being OpenTofu's to create — and the queue policy letting its topics send to it;
. it subscribes the queue to each topic, with raw delivery;
. it publishes to each topic a marker carrying its queue's id, and drains its queue until the marker
  arrives: the subscription delivers. Whatever arrives before the marker is deleted unprocessed.
  Every other task gets the marker too and discards it, as anything that is not an rqlite change set;
. it rebuilds from the database;
. it consumes: long polling of up to 20 s, batches of up to 10, `DeleteMessageBatch` after
  processing.

What the drain discards is old: a message received before the marker was published before then, so
its change was committed before the rebuild, which reads it. That holds whatever order a standard
topic delivers in, since it is the receipt that comes before the marker, and it needs no clock. Every
change committed after the rebuild is published after the marker came back, once the subscription
delivers, so it is in the queue. Nothing is purged: purging takes up to a minute and may delete what
arrives after it was asked, and a new queue starts empty anyway.

The queue, the subscription and the consumer are resources of the task's scope, acquired in that
order, so its finalizers stop the consumer, unsubscribe and delete the queue, in the reverse order.
They run on SIGTERM: `ZIOAppDefault` registers a JVM shutdown hook that interrupts the main fiber and
waits for its finalizers (`ZIOAppPlatformSpecific.main`, zio 2.1.26), which ECS bounds by sending
SIGKILL 30 s later. The JVM receives SIGTERM itself: each image runs `CMD ["java", "-jar", …]`, and
the base image's entrypoint, `/__cacert_entrypoint.sh`, ends in `exec "$@"`, so `java` is PID 1. A
task killed without SIGTERM — SIGKILL, memory exhausted — leaves its queue and subscription, and
nothing removes them: each costs cents a month (<<verified>>), and they are removed by hand.
`destroy_location` removes every queue and subscription of the location, by its prefix, since no
task of a service that is gone has one alive.

The task role needs, scoped by name: on its queues, create, set and get attributes, receive, delete
messages and delete the queue — `captal-<env>-feed-mcp-*` for the backoffice's role, and
`captal-<env>-feed-*` with every SQS action on `-feed-mcp-*` denied for the role every location
shares; on its topics, `sns:Subscribe` only with `sns:Protocol = sqs` and `sns:Endpoint` one of those
queues, `sns:Unsubscribe` and `sns:Publish`, for the marker. A task keeps the subscription's ARN `Subscribe` answers, so it lists nothing. No condition
key names the subscription `sns:Unsubscribe` removes, so a task could remove another's subscription to
the same topic; a marker or a forged message published by a task only makes the others check against
the database. The backoffice's role also needs, for `destroy_location`, `sqs:ListQueues`,
`sns:ListSubscriptionsByTopic`, `sns:Unsubscribe` and `sqs:DeleteQueue` on the locations' queues. The
relay's role needs `sns:Publish` on every `cdc` topic.

=== Push and pull, plainly

The subscribers read SQS by long polling: a request the server holds open until a message arrives or
20 s pass, returning up to 10, after which the subscriber asks again and deletes what it processed.
It is a pull. Delivery is as immediate as the gRPC stream's — the request is already waiting when the
message arrives — and in both cases the subscriber opens the connection; what differs is that it asks
again after each batch, and each request is billed.

simulator, or the first apply to AWS, is what settles them.

  touches; 200 to rqlite only once SNS accepted every publish; the gRPC fan-out as today, so current
  subscribers notice nothing.
. *Subscribers move to SQS one at a time*, each task subscribing itself as above.
  * The backoffice: an SQS consumer producing the same `Event.Changed(index, json, context)` as
    today, without `Gap`, so `VideoFileCollector` changes only its source and rebuilds its timers as
    it starts.
  * Every location: `RecoveryFeed` reads its task's queue. Existing locations subscribe themselves
    when `ci.run` moves them onto the new image; `destroy_location` removes what their tasks left.
. *gRPC is retired*: the relay stops serving it; the `cdc.protocol` module (`ChangeFeedFollower`,
  `cdc.proto`), the buffer, the `Gap`, `CDC_BUFFER`, the gRPC port and its security group rule go.
. *The relay deploys overlapped*: the container health check, 100/200, the `stopTimeout`. ARM is
  optional and needs the image built for arm64.
. *Documentation*: rewrite `cdc.adoc`, update `infrastructure.adoc`, record in `decisions.adoc` why
  SNS and SQS, why a queue per task and a topic per table, and what was set aside (the table above),

== What it changes elsewhere

* xref:admin-core-plan.adoc[The admin core plan]: the progress of a deploy run can reach its page the
  same way — publish `mcp_deploy_runs` through CDC to the backoffice's tasks — once this is done;
  option A there stops being blocked on the relay.
* The out-of-order delivery a leader change can cause, which the relay today drops silently when an
  index arrives below the last it published, reaches the subscribers, as do repeats; both are
  idempotent, so they apply whatever arrives in whatever order.
