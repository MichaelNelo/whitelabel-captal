= Plan: tools and endpoints from flows and queries
:toc:
:toclevels: 2

A plan agreed in conversation on 2026-11-15. Its tools are done (<<done-tools>>); its endpoints wait
for the next rework of the API's routes. Every backoffice tool and every API route that
runs one command or one query does the same few things around it; this turns them into one extension
for tools and one for typed endpoints, so a tool or a route says only how its input becomes the
command and how the result becomes its answer.

== The problem

Once every tool is a command or a query (xref:admin-core-plan.adoc#decided-2026-11-15[decided
there]), a tool that runs a command does, in order: parse its input and build the command, with the
instant and any new id it needs; publish the `OperatorContext` (the calling token, and the means to
ask the operator); run the flow; turn a refusal into what the operator reads; shape the answer. Only
the first and the last differ from one tool to the next. A tool that runs a query does the same
without the context and the flow. An API route does the same with the guest's session instead of the
operator, and with cookies, headers and status codes around its body.

== Tools

Extensions on `McpTool`, chained after its description and scopes, which read the flow or the query
from the environment, where the layers put them:

[source,scala]
----
extension (tool: McpTool)
  /** The input becomes the command, the flow runs it as the calling operator, a refusal becomes what
    * the operator reads, the result becomes the answer.
    */
  def runs[In: Schema, C, Res, Out: Schema](command: (In, Fresh) => ZIO[Any, AppError, C])(
      answer: (In, Res) => ZIO[Any, String, Out]): McpToolHandlerR[OperatorContext & Flow.Aux[Task, C, Res]]

  def reads[In: Schema, Q, Res, Out: Schema](query: In => Either[AppError, Q])(
      answer: (In, Res) => Out): McpToolHandlerR[Query.Aux[Task, Q, Res]]

McpTool("set_fingerprint_required").description("…").requireScopes(Auth.LocationWrite)
  .runs((in: FingerprintRequest, fresh) => …)((in, _) => …)
----

`Fresh` is the instant and the new ids, generated by the extension, since `core` takes them in the
command. What a refusal reads as becomes a typeclass, `Describe[E]`, one per error domain, where
`LocationCommands.describe` is today.

Both the factory and the answer are effects, because some tools read before the command —
`confirm_video_upload` takes the file's length from S3 — and some add to the answer something that is
not state — a signed upload URL.

What does not fit: the tools whose refusal leads to a question and another command — deploy, pause,
resume and destroy, through `PreviousOperationUnfinished` and `OperationInProgress` — either take an
optional `onRefusal` or stay written by hand. There are four.

== API routes

The same as an extension on the typed `Endpoint`. A route's endpoint already declares everything its
response carries: `/api/status`'s `.out[StatusResponse].outHeader(HeaderCodec.setCookie.optional)`
makes its output `(StatusResponse, Option[Header.SetCookie])`. So the answer returns exactly the
endpoint's declared output, cookies and headers included, and the compiler holds it to all of it; the
factory takes its declared input — cookies, headers, path — the same way.

[source,scala]
----
extension [P, In, Out, A <: AuthType](endpoint: Endpoint[P, In, ApiError, Out, A])
  def runs[R, C, Res](flow: Flow.Aux[Task, C, Res])(
      command: In => ZIO[R, ApiError, C])(
      answer: (In, Res) => ZIO[R, ApiError, Out]): Route[R, Nothing] =
    endpoint.implement: in =>
      for
        cmd <- command(in)
        res <- flow.execute(cmd).mapError(ApiError.fromThrowable)
        out <- answer(in, res)
      yield out

status.runs(enterPortalFlow)(toEnterPortalCommand)((_, entered) =>
  ZIO.succeed((statusOf(entered), Some(cookieConfig.asSetCookie(entered.sessionId.asString)))))
----

Both are effects there too: a route reads or publishes things around the command — the session the
cookie names into `SessionContext`, the phase check of `SessionEndpoint.authorise`.

== Order

. The tools' extensions, once the admin core plan has every tool as a command or a query; the
  location tools first.
. The endpoints' extension, the next time the API's routes are reworked: there are few of them, and
  each has more of its own around the command than a tool does.

== Done on 2026-11-17: the tools

`Adapters` in `mcp/tools/` has `runs`, `runsEither` and `reads`, and every tool that runs one
command or one query is built with them; compiled, and not yet run through `mcp.test` or the E2E,
which wait on LocalStack's license. What it became, against the sketch above, each change agreed in
conversation:

* *No `Fresh`.* The factory is an effect: it reads the instant from `Clock` and makes its ids with
  each type's own `generate`, so there is nothing to hand it.
* *No `Describe[E]`.* What a refusal reads as is one exhaustive function, `Refusals.describe`,
  matching every case of `AppError` and describing each domain once. The typeclass's one advantage,
  overriding by scope, is a parameter instead (`runs(command, describe)`), which only the survey
  question pairs pass, to name the other tool. `cats.Show` and ZIO Prelude's `Debug` were weighed
  and left: what is described is one type, `AppError`, for one audience, and a `Show` instance would
  claim to be every audience's textual form.
* *The error type is `AppError`*, since flows and queries already fix it in `core`. What fails while
  the input is read — a MAC, a rule's value — is the tool's and fails with its text.
* *`runsEither`* takes a factory that picks one of two commands answered alike, for the four
  `set_*_active` tools.
* *Queries are found in the environment*, built once in `Queries`, as the flows are; `reads` takes
  its answer as an effect too, since `resume_video_upload` signs a URL in it.
* *The result's type is named on the answer's parameter*, which is how the flow or the query is
  found: a generic `Tag` of `Flow.Aux[Task, C, Res]` was checked to match the one a layer registers
  under a concrete alias.
* *What the creating commands answer grew*: the answer sees only the input and the result, so a
  command that makes ids answers them (see the admin core plan's seventh step).

Written by hand still, as the code says why: the four operation tools, whose refusals lead to a
question and another command; `configure_unifi`, which signs its ticket with the calling token; the
token tools, outside `core`; and the static ones.
