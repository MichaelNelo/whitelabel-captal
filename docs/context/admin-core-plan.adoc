= Plan: the administrative side in core
:toc:
:toclevels: 2

A plan agreed in conversation on 2026-11-13, revised on 2026-11-14, with its first two steps done on
2026-11-15 (see <<order-of-work>> for what they became) and the rest refined the same day
(<<decided-2026-11-15>>). It moves the
backoffice's business rules into `core`, models a location as an entity whose state is in its type and
each operation on it as a run of its own, run by a saga, and then moves `/api/status`'s logic into a
command on that model. One question stays open that blocks part of it: the availability of the change
data capture relay. Pick it up from <<order-of-work>>.

Status when written: access points (migration `V34__access_points.sql`, `access_points` table, the AP
check at `/api/status`, `update_access_point` and `remove_access_point`) and the split of
`/api/status`'s failures (`InvalidClient`, `UnknownAccessPoint`, the missing fingerprint a guest
leaves through) were pushed to `main` and not yet released. Everything below comes after them.

== Why

`core` models the guest's side only. Its 16 commands (`Start`, `AnswerEmail`, `StartPlayback`,
`Finish`, `ExpireAccess`, `RequestRecovery`, …) walk a guest through the flow; `survey`, `video` and
`user` are modelled as the guest meets them — answering, validating an answer, which video is next —
not as an operator authors them.

The administrative side has no model. The backoffice's tools write rows with Quill directly — 46
write sites across 10 files under `mcp/src/.../tools` and `apps` — and each handler holds its own
rules: the slug's shape in `LocationTools.validateSlug`, the MAC and the one-running-location-per-AP
rule in `UiRoutes.refuseRunningElsewhere`, the video states in `VideoTools`. The backoffice imports a
handful of types from `core` (`Mac`, `VideoType`, `Playback`, the i18n schema) and nothing else.

What that costs:

* Those rules are only exercised against rqlite and LocalStack, which is why `mcp.test` is rarely run.
  In `core` they would be pure tests.
* A rule has more than one home. The AP rule is applied by three tools and assumed by the portal
  dispatcher; an AP's validity is checked in the backoffice and again in the API.
* Nothing records who changed what. The guest's side emits events that `EventLogHandler` writes to
  `event_log`; the administrative side would get the same audit trail for free.

== Principles

Stated by the user, and binding:

* `core` stays as pure as possible and talks to platform and infrastructure through events. A tool
  never goes into `core`; only the logic it uses does. Whatever ends up as an impure change becomes an
  event.
* The shape is the existing one: a command carries the instant (`occurredAt`) and any new id; a
  handler is a `Handler.Aux[F, Cmd, Result]` that reads through repository traits in
  `core.infrastructure` and answers an `Op[Event, Error, A]`; `platform`'s handlers persist the
  events (transactional) or call out (post-commit).
* A tool becomes an adapter: parse the input, build the command, run the flow, shape the answer — or
  the elicitation.

== The model

Sketch, to be refined when it is written:

----
core/
  location/
    Slug.scala          opaque Slug: lowercase kebab-case, not blank
    Location.scala      LocationId, Location[S <: State](id, slug, name, settings, state)
                        Settings(durationMinutes, redirectUrl, unifiEnabled, fingerprintRequired)
    State.scala         Created
                        | Deployed(by: RunId, accessPoints: NonEmptyList[AccessPoint])
                        | Paused(by: RunId) | Destroyed(by: RunId)
    AccessPoint.scala   AccessPoint(mac: Mac, controller: Controller)
                        Controller(host: Host, port: Port, siteId: SiteId, token: Secret)
    ops.scala           the transitions, one extension per state they leave (see the state machine)
    Readiness.scala     Facts → steps(facts)

                        AccessPointRegistered, AccessPointUpdated, AccessPointRemoved,
                        LocationDeployed(run), LocationPaused(run), LocationResumed(run),

    Error.scala         InvalidSlug, SlugTaken, InvalidMac, ControllerIncomplete(field),
                        TokenRequired, AccessPointHeld(mac, by), NoAccessPoint,
                        LastAccessPoint(mac), NotAllowedFrom(state, op),

                        PreviousOperationUnfinished(run, op, pending)
  operation/
    Run.scala           RunId, Operation: Deploy | Pause | Resume | Destroy
                        Run[S <: RunState](id, location, operation, steps, state)
                        RunState: Started(heartbeat) | Completed(at) | Failed(step, failure)
                        Step, and each operation's steps in order
                        StepFailure → explain(step, failure): LifecycleError
    ops.scala           Run[Started].completed, Run[Started].failed
    Event.scala         OperationStarted(run, op, steps), OperationCompleted(run),
                        OperationFailed(run, step, error)
  application/commands/
    CreateLocation, ChangeSettings, RegisterAccessPoint, UpdateAccessPoint, RemoveAccessPoint,
    StartOperation(op), CompleteOperation(run, outcome)
  infrastructure/
    LocationRepository[F]       findCreated(id), findDeployed(id), findPaused(id), findDestroyed(id),
                                stateOf(id), slugTaken(slug)
    AccessPointRepository[F]    of(location): List[AccessPoint], holders(mac): List[(Slug, State)]
    RunRepository[F]            findStarted(location), findFailed(location)   (steps done, heartbeat)
----

* A location is an entity as `Device[S]` is: its state is in its type, and each transition is an
  extension on the states it leaves, so a transition from the wrong state does not compile. A run is
  an entity of its own, the same way.
* A handler asks the repository for the entity in the state its command needs — `findDeployed`,
  `findStarted` — as `DeviceRepository.findAccepted` and `findNotAccepted` do: the query's `WHERE`
  narrows the type, and `None` means it is not in that state. Not a `Location[State]` matched by type:
  the type parameter is erased, so `case l: Location[State.Deployed]` tells nothing apart. The handler
  then matches on the `Option`s, as `AcceptTermsHandler` does. `stateOf(id)` answers the state's name
  alone, for `NotAllowedFrom` to say which state the operation was asked from.
* The controller's token travels inside commands and events. `Secret` renders redacted, and
  `EventLogHandler`, which builds each event's JSON by hand, leaves it out — as must any log line.
* Administrative flows have no guest session: they need a flow constructor without
  `SessionContext`.
* `core` is also compiled to Scala.js (`core-js`) for the portal. The linker should drop what the
  portal never references; measure the bundle when the first types land, as was done for the ZPure
  experiment, and move the administrative model to a module of its own if it grows.

== A location's lifecycle

=== What a deploy is

`deploy_location` stands a location up: it copies `bundle/` under `/<slug>/`, creates the log group,
the target group and the ALB rule, registers a task definition (the release's image, read from
`API_IMAGE`, and the environment: `LOCATION_SLUG`, the database, CDC, OTEL, the UniFi proxy), and
creates or updates the service. It is needed once per location.

Its other historical uses are gone or going: a newly published bundle reaches every location through
`ci.run`'s `publishClient`, paused ones included (their new `index.html` goes to
`_paused/<slug>/site.html`, `Release.scala:524-570`); a new image reaches every service through
`rollLocations`, which keeps a paused one paused (`Release.scala:435`); and with access points the
UniFi settings are read per event, so nothing location-specific is read at task start any more. So
versions are the release's business, never the deploy's, and a deploy of a deployed location has
nothing legitimate to do — re-running it today only replaces the task, minutes of draining for
nothing. The log group and target group are created once and removed by a destroy; they are not
reconciled.

A reconciling planner (desired state against actual, a resource graph applied in dependency order
going up and in reverse going down) was considered and dropped for this reason: the resources it
would reconcile never change after creation.

=== The state machine

----
Created ───deploy──► Deployed ──pause──► Paused
                      ▲    ▲               │
Destroyed ──deploy────┘    └────resume─────┘
Deployed | Paused ──destroy──► Destroyed
----

Each state names an action that succeeded, and points to the run that did it. A location changes
state only when an operation completes: an operation in progress is its run's state, not the
location's, since until it completes nothing has happened to the location; and a run that fails
leaves the location where it was, which is what happened. There is no `Deploying` or `Pausing`.

`Destroyed` is not an end. A destroy removes what the location has in AWS and touches nothing in the
database — the row, its translations, surveys and videos stay, and `list_locations` still reports
it — and a deploy stands it up again, from `Destroyed` as from `Created`. The two stay apart for the
history: a destroy may have deleted the location's S3 objects, so its videos need uploading again.
Deleting a location's row is not planned: sessions, users, answers and `event_log` point to it, and
what becomes of them would have to be decided first.

`by` is a run's id, not the run: a location reaches a state only when the run completes, so the run
it names is always a completed one, and there is no state of it to find out. Holding the run itself
would load it with every location, on every `/api/status`.

Only `Deployed` holds the access points, since it is where they are used: `EnterPortalCommand` checks
the redirect's AP against them, and a deployed location with none would refuse every guest. The
transitions into it take them as an argument, read by the handler (`AccessPointRepository.of`), as
`acceptTerms` takes the terms in force; with none they fail with `NoAccessPoint`. `Paused` does not
hold them: a resume reads them again and asks for one again, which covers access points changed while
paused. Removing the last access point of a `Deployed` location is refused (`LastAccessPoint`); in
any other state a location takes and loses them freely. Registering one asks `holders(mac)` for the
one deployed location per AP rule, and the location's own access points for whether it already has
that MAC, which it then updates rather than adds: uniqueness per location and MAC is checked before
writing, not left to the table's `UNIQUE`. A new row's id is a random UUID; only `V34`'s copy from
`locations` wrote `<location id>/<mac>`.

The transitions, one extension per state they leave:

[source,scala]
----
extension (l: Location[State.Created | State.Destroyed])
  def deployed(run: RunId, accessPoints: List[AccessPoint], now: Instant)
      : Op[Event, E, Location[State.Deployed]]
extension (l: Location[State.Deployed])
  def paused(run: RunId, now: Instant): Op[Event, E, Location[State.Paused]]
extension (l: Location[State.Paused])
  def resumed(run: RunId, accessPoints: List[AccessPoint], now: Instant)
      : Op[Event, E, Location[State.Deployed]]
extension (l: Location[State.Deployed | State.Paused])
  def destroyed(run: RunId, now: Instant): Op[Event, E, Location[State.Destroyed]]
----

`StartOperation` takes the location in the state the operation leaves — a deploy needs a
`Location[Created | Destroyed]` — and asks for its run in progress or failed (`findStarted`,
`findFailed`):

* asked to deploy a location that is `Deployed`: nothing to do, no event;
* the location is in a state the operation does not leave (resume only from `Paused`):
  `NotAllowedFrom`;
* its latest run is `Started` with a fresh heartbeat: `OperationInProgress`;
* its latest run is `Failed`, or `Started` with a stale heartbeat: `PreviousOperationUnfinished` with
  the steps still pending — the tool turns it into an elicitation ("the pause stopped at «scale to
  zero»; finish it first?");
* otherwise: check the operation's conditions (terms of service; for a deploy or a resume, one access
  point at least, and none of them in another `Deployed` location) and emit `OperationStarted` with a
  new `Run[Started]` and every step of the operation, or only the pending ones when it finishes an
  unfinished run. The location does not change.

`CompleteOperation(run, outcome)` loads the run, which knows its operation, and the location, still
in the state the operation leaves, since the lock lets no other operation in between. On success it
applies the transition (`deployed`, `paused`, …) and completes the run; on failure only the run
changes, to `Failed`.

Each operation has a fixed list of steps owned by `core`. Their order is a domain rule: a pause swaps
the edge to the maintenance page and waits for it before the ALB answers "paused" and the service
scales to zero, since an API that refuses behind a page that still offers the flow strands the
guest; a resume goes the other way. That ordering was never exercised by a test; in `core` it would
be, against a fake port.

Failures: the port that runs a step reports a structured `StepFailure` (timed out, rejected, missing),
never an AWS string, and `core`'s `explain(step, failure)` turns it into a `LifecycleError` the page
can show (`ServiceNeverStarted(revision)`, `EdgeStillServing(invalidation)`, `TasksStillStopping`).
Today those messages are strings built in `Deploy.scala` and `DeployTools`.

Drift — a resource changed by hand in the AWS console — is out of the model; an explicit repair
operation can be added if it is ever needed.

[[Concurrency]]
=== Concurrency

As sketched here; the lock itself moved to Redis once the fourth step was built (see that step under
<<order-of-work>>).

rqlite has no `SELECT … FOR UPDATE`. The lock is the location's run pointer, taken by a conditional
write the leader serializes: `UPDATE locations SET current_run = :new WHERE id = :id AND current_run
IS :seen`, one affected row to win, and a read afterwards to confirm who holds it — the `Migrate.Lock`
idiom (xref:../database.adoc[Database], "the insert is a bid; a follow-up SELECT is the answer"). It
is held while the run it points to is running with a fresh heartbeat, released by `CompleteOperation`,
and an abandoned one is taken over through `PreviousOperationUnfinished`.

The loser learns it when `platform` persists `OperationStarted` and the conditional write affects no
row (`TransitionTaken`), or earlier when `core` already sees a live run (`OperationInProgress`). Both
end in one answer from the tool: re-read the location and elicit "a pause of `prueba` is in progress
(step 3 of 5, started by `operator-x` two minutes ago) — see its progress?". Yes returns the same view
the starting tool returned, on the same run id; no returns a short message naming the run; a host
that cannot ask gets the error with the run id and `get_deploy_status`, as `destroy_location` already
does when `ctx.elicit` fails.

=== The saga

----
StartOperation ──► OperationStarted(run, op, steps)
                     ├─ transactional handler: persist the run, take the lock (current_run)
                     └─ post-commit handler: enqueue RunOperation(run)        ← data only
OperationRunner (a fiber) ◄── consumes the queue
   runs the steps through the AWS port, records progress and heartbeat on the run
   └─► runs the CompleteOperation flow ──► LocationDeployed (…Paused, …) + OperationCompleted
                                          | OperationFailed
----

A handler does not run a flow directly. The flow needs the handler chain to dispatch its events, so a
handler in that chain needing the flow is a cycle in the ZIO layers; a post-commit handler runs inside
the request, so waiting on AWS would hold the tool call for minutes; and data in a queue can be rebuilt
from the database. This is the existing `JobQueue` / `JobRunner` pattern: `UnifiAccessHandler`
enqueues `ScheduledAt(expiresAt, ExpireAccess(sessionId))` and `JobRunner` runs the `ExpireAccess`
flow.

Completion events are only persisted and logged; no handler starts an operation on them, so the saga
cannot chain itself. A run interrupted by a backoffice restart is not resumed on startup: its heartbeat
goes stale and the next request elicits whether to finish it. Rehydrating runs on startup, as
`JobRunner` does with expirations, is the alternative if the operator should not have to.

=== Database

`locations` gains `state` (`created`, `deployed`, `paused`, `destroyed`) and `current_run`, the lock.
(`state` came with the first step, beside `state_run`, the run that left it so; `current_run` is
still owed.)
With the paused state there, the portal dispatcher can read it in the query that finds the location
and stop reading S3 — removing the S3 gateway endpoint and the `s3:ListBucket` permission
`modules/portal-dispatcher` was given for it. `_paused/<slug>/site.html` stays, only for the resume
to restore the page. `mcp_deploy_runs` is the run's row: its state, its heartbeat and each step's
state; `core` reads it through `RunRepository` to compute pending steps.

The legacy UniFi columns `V34` left on `locations` (`unifi_ap_mac`, `unifi_host`, `unifi_port`,
`unifi_site_id`, `unifi_api_token`) are dropped once no dispatcher or API on the previous release
reads them, together with the dispatcher's fallback query.

[[slug-and-aws-names]]
=== The slug and the names in AWS

`Slug` holds the slug's shape alone: lowercase kebab-case, not blank. No length: the 25 characters
`LocationTools.validateSlug` allows today come from `Deploy.targetGroupName`, `captal-<slug>`, which
AWS caps at 32. That limit stays with the adapter that meets it: the target group is named
`captal-<slug>` while that fits, and `captal-<short hash of the slug>` past it, with the slug in a
tag, so no existing location's name changes. The ECS service (255) and the log group (512) take any
slug. The reserved names — `bundle`, `ui`, `releases`, `mcp`, prefixes every location shares in the
assets bucket and at the distribution — are refused by the backoffice's `create_location`, not by
`core`.

== Open: progress to the page, and the relay's availability

How the run page learns of each step is undecided, and depends on the relay. Today `RunRoutes` reads
the run's row every second and sends the whole run as a server-sent event when it changed
(`RunRoutes.scala:55`). Polling was kept there without the choice being put to the user — the fourth
time in this project — and the user asked for push. The options, as put:

[cols="1,2,2,2"]
|===
| | A. Push through CDC | B. In-memory push | C. Poll the row (today)

| How
| rqlite posts `mcp_deploy_runs` changes to the relay; every backoffice replica already follows it
  (`VideoFileCollector`); a `RunFeed`, like the API's `RecoveryFeed`, publishes them to a `Hub`, and
  the SSE route subscribes for its run
| The runner publishes to a `Hub` in its own process
| Read the row every second

| Several replicas
| Yes
| No: an SSE connection on the other task (a backoffice deploy runs two) hears nothing, unless it
  falls back to reading the row
| Yes

| Late or reconnecting page
| The current row first, then live changes; a `Gap` re-reads the row
| Same, within one process
| Yes

| Cost
| Changing `rqlite_cdc_table_filter` changes rqlite's task definition and replaces every node — a
  single deliberate operation with the S3 backup verified first, worth doing once with this plan's
  migrations
| None in infrastructure
| One query a second per open page, up to a second late
|===

A was recommended, and was blocked on the relay's availability. That is now planned separately —
the relay publishes to SNS and every subscriber reads its own SQS queue
(xref:relay-sns-sqs-plan.adoc[the relay plan]) — and with it, A means publishing `mcp_deploy_runs`
to the backoffice's queue. What follows is the analysis that led there:

The relay is one Fargate task deployed stop-then-start (`deployment_minimum_healthy_percent = 0`,
`modules/cdc/main.tf:134`), because each relay keeps its change sets in its own memory. Two at once
would split rqlite's posts: a subscriber that connected to the new one while rqlite still posted to
the old misses those change sets with no `Gap`, since its instance never changed. DNS cannot
coordinate the switch: `cdc.<namespace>` is a Cloud Map MULTIVALUE A record that lists both tasks
during an overlap, ECS registers a task while it is still `ACTIVATING`, the VPC resolver caches for
the 10-second TTL and the JVM for about 30 seconds, and an open connection — rqlite's keep-alive HTTP
connection, a subscriber's stream — never resolves again. So each relay deploy leaves one to two
minutes with no live feed: rqlite retries its posts (exponential, 10 retries, backoff up to 60 s,
`docker/rqlite-entrypoint.sh`), subscribers reconnect every 2 seconds and get a `Gap` from the new
instance, and nothing is lost unnoticed. ECS stops the old task only once the new counts as healthy,
which without a container health check is 40 seconds after `RUNNING`, whether or not it listens.

Options discussed, none chosen:

* *Fan-in in the follower.* `ChangeFeedFollower` follows every address `cdc.<namespace>` resolves to,
  re-resolving every few seconds, one stream per relay; a new relay is asked for its whole buffer
  (its indexes say nothing about another's), and duplicates are dropped with a bounded set of seen
  indexes rather than "above the last", since streams interleave. With a container health check and
  a 100/200 deployment, overlap becomes safe and two relays could run permanently. Changes the
  follower only.
* *Explicit handoff.* The relay registers itself in Cloud Map instead of ECS doing it. On SIGTERM the
  old one refuses rqlite's posts with 503 (rqlite retries), ends the streams and deregisters; the new
  one registers only when no other is registered. Never two in DNS, and a gap of seconds since the new
  one is already warm. Needs Cloud Map permissions for the relay, and a liveness check for an old one
  that crashed without deregistering.
* *SNS FIFO and SQS FIFO.* The relay publishes each change set to a topic, with the Raft index as
  `MessageDeduplicationId`; each subscriber — the backoffice, every location — has its own durable
  queue. The relay becomes stateless and can overlap or run twice. Costs a queue and a subscription
  per location, created and removed by the deploy and destroy operations, and the gRPC contract goes
  away. SQS is consumed by long polling: it is a pull, which has to be said plainly when choosing it.

Rejected: an ALB in front of the relay (it moves no open stream — a deregistering target's connections
end and the client reconnects anyway; its idle timeout ignores HTTP/2 PINGs, so quiet subscriptions
are cut every 60 s to 4,000 s; gRPC needs an HTTPS listener; and it would round-robin rqlite's posts
between two relays, splitting them); RabbitMQ (it moves the problem to the broker, whose own
replacement needs a quorum-queue cluster that on Fargate is a second rqlite to operate, or Amazon MQ's
three brokers).

=== Every tool a command or a query

As far as possible, each tool is one command or one query; the tool parses, runs it and shapes the
answer. A query is what `core.application.queries.Query[F, Q]` already declares — `execute(query):
F[Either[Error, Result]]`, a `Query.Aux` like `Handler.Aux` — with its input and output defined in
`core` and kept anemic: plain data, not entities, no methods. It is implemented in `platform` as an
object with an `apply` factory returning the `Query.Aux`, the way a command's flow is built, and run
by the tool directly: no `Flow`, no events, no transaction. `AssetStore` moves from the backoffice to
`platform`, so the queries that read S3 live there too. Where a query needs a rule — readiness's next
steps — the rule is a pure function in `core` that the implementation calls to fill the output.

=== The operator's context, and flows in layers

The backoffice's flows are composed once, in layers, as the API's are — `LocationCommands.run`, which
builds its chain per call for the actor, goes. What changes per call travels in an `OperatorContext`
in `platform`, the way `SessionContext` carries a guest's session: a `FiberRef` holding the `actor`
(the operator token's id, what `event_log.actor` records) and `ask`, the means to put a yes-or-no
question to the operator. A tool publishes it around the flow it runs (`locally`); the runner
publishes the run's `started_by` and no `ask`. `EventLogHandler.forOperator(operators)` reads the
actor when it runs instead of taking it when it is built, and a flow run with no context fails
(`OperatorContext.NotSet`), as `SessionContext.NotSet` does.

`ask` is a function, not the MCP context, because the handlers live in `platform`, which knows no
MCP.

=== Elicitations

A saga is no more than a handler that runs another flow. A handler can ask the operator through
`OperatorContext.ask`, provided it runs after the commit — never inside the transaction, which would
stay open while a person answers — and in a flow a tool runs, since only a tool call has an operator
on the other end. Of the three elicitations there are:

* *Delete the S3 objects on a destroy*: asked by the tool before the command — `AssetsOf`, the
  question, then `StartOperation(Destroy(deleteAssets))` — and not by a handler after it, which would
  ask with the lock taken and the run not yet queued, long enough for its heartbeat to go stale.
  Only a yes deletes; a host that cannot ask keeps the objects.
* *An operation left unfinished* (`PreviousOperationUnfinished`) and *one in progress*
  (`OperationInProgress`, or `TransitionTaken` for a lost race): refusals, which emit no event and so
  reach no handler. The tool asks — "the pause stopped at «scale to zero»; finish it first?", "see its
  progress?" — and runs `StartOperation(op, finishing = run)` or the `RunStatus` query. Finishing runs
  that operation, not the one first asked for, which is asked again once it completes: the saga does
  not chain.

=== Running an operation

Two commands, since the domain's decisions are at the ends: `StartOperation` decides whether the
operation may start and which steps it takes, `CompleteOperation` applies the transition on success
or records the failure, explained (`explain(step, failure)`). The steps in between are I/O on AWS
with nothing to decide — their order is a domain rule, `Operation.steps`, and no more — so they are
not commands:

----
tool ─► StartOperation ─► OperationStarted ─► (after the commit) the run is queued
runner ◄─ the run
   execute(run, steps)   ← core: the pending steps in order through the port, stopping at the first failure
      each step: OperationSteps.run (AWS) · RunProgress marks it on the run's row
   ─► CompleteOperation(run, outcome) ─► LocationPaused (…) + OperationCompleted | OperationFailed
----

`OperationSteps[F]` and `RunProgress[F]` are ports in `core`; the backoffice implements the first
with `InfraStore` and `AssetStore`, `platform` the second, writing each step's state and the
heartbeat on `mcp_deploy_runs` directly, as `Runs.Progress` does today: neither is a fact of the
domain. `execute` is small, but it puts the order under test against a fake port. The queue and the
runner follow `JobQueue` and `JobRunner`: the handler only queues data, the runner runs the flow, so
the layers have no cycle and a tool call never waits on AWS. A run interrupted by a restart is not
re-queued on startup; it is finished through the elicitation above.

Finishing an interrupted run runs again the step it died in, which AWS may have completed before the
process died, so every step has to be safe to run twice. Pausing's page swap was not — run again, it
saved the maintenance page over the location's own — and was made idempotent on 2026-11-15.
