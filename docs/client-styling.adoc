= Client styling
:toc:
:toclevels: 2

One file, `client/assets/styles.css`, styles the whole guest portal: every view in
xref:client.adoc[Client] renders against it, and a location themes itself by overriding a subset of
its custom properties. The MCP-UI apps (`mcpui/UploadApp.scala`, `mcpui/unifi/UnifiApp.scala`) are
styled differently — by the MCP host, through `Bridge.applyHostStyles` — and are out of scope here;
see xref:client.adoc[Client].

== Per-location theming

The portal's two HTML templates load two stylesheets, in order:

[source,html]
----
<link rel="stylesheet" href="{{CSS_PATH}}">
<link rel="stylesheet" href="./custom-styles.css.gz" onerror="this.remove()">
----

`{{CSS_PATH}}` is the bundle's own `styles.css` — the file this document describes. The second link
is a per-location object that, when present, is loaded strictly after the first; because both
declare the same `:root` selector at equal specificity, the later declaration wins property by
property. A location's stylesheet therefore only needs to redeclare the properties it wants
changed — anything it omits keeps the bundle's default. `onerror="this.remove()"` is what makes a
location with no customisation correct: the object does not exist, the link fails to load, and the
tag removes itself rather than sitting there as a stylesheet reference to nothing.

`custom-styles.css.gz` is always gzipped and always `text/css`, written by the MCP backoffice's
`AssetTools.setStyles` → `AssetStore.put` (`mcp/src/whitelabel/captal/mcp/aws/Assets.scala`), which
also sets `Content-Encoding: gzip` and the same `Cache-Control: public, max-age=86400` the portal
bundle carries, and invalidates the one CloudFront key the write touched so the change is visible
without waiting out that cache. The brand icon (`brand-icon.svg`, referenced by `BrandLoader` and by
the static markup in both HTML templates) follows the same store but is not a CSS property at all —
`set_location_icon` replaces the file outright, after `AssetTools.validateSvg` rejects anything
carrying a `<script>` or an `on*` handler, since the icon is served from the portal's own origin and
would execute there.

An operator discovers the themeable surface and writes it through three MCP tools —
`get_css_schema`, `get_location_styles`/`set_location_styles`, `get_location_icon`/
`set_location_icon` — documented in xref:mcp.adoc[MCP backoffice]. `get_css_schema` is not a
hand-kept list: it is `CssSchema` parsing this file's own `:root` block at startup, so it cannot name
a variable this stylesheet no longer declares, and a variable this file grows without an entry in
`CssSchema.Purposes` shows up with an empty purpose rather than not at all — the signal that
something new needs explaining. `set_location_styles` replaces the whole stored file on each call;
it is not a patch, and reading back with `get_location_styles` first is how an operator edits rather
than overwrites.

== Custom properties

The `:root` block groups its declarations under banner comments, which is also how `CssSchema` reads
its groups. Purposes below are `get_css_schema`'s own prose where the stylesheet has an entry for
it; the type scale, the spacing scale and `--radius-sm`/`--radius-md`/`--radius-lg` have none today
— the live tool answers an empty purpose for those — so the column instead gives what the size and
its call sites show.

[[Layout architecture]]
== Layout architecture

Every view composes against one shared shell, built once by `Layout` (`client/src/whitelabel/captal/client/views/Layout.scala`) and reused by every route:

[source,scala]
----
def apply(
    content: HtmlElement,
    footer: HtmlElement,
    isLoading: Signal[Boolean] = Signal.fromValue(false)): HtmlElement
----

[source]
----
.app-layout
├── .layout-content
│   └── .layout-view (.loading-state | .loaded-state)
│       ├── .view-icon
│       │   └── .brand-icon (img, via BrandLoader)
│       └── .view-content (.hidden | .visible)
│           └── [the view's own content]
└── .layout-footer (.hidden | .visible)
    └── [the view's own footer]
----

`.view-icon` is rendered once and never swapped — only the parent's `loading-state`/`loaded-state`
class changes — which is what lets the brand icon travel from "centred in the viewport" to "sitting
above the content" as one continuous element rather than two elements handed off. `.layout-view` and
`.view-content` track `isLoading` directly; `.layout-footer` tracks the same signal one level up.
`onMountCallback` on the outer `.app-layout` div also turns `AppState.isNavigating` off — see
*Navigation integrity* in xref:client.adoc[Client] for the Scala-side protocol this participates in.

[cols="1,4"]
|===
|Class |Behaviour

|`.layout-view.loading-state`
|`position: fixed; inset: 0`, flex-centred: the icon sits in the middle of the viewport, independent
of where the view will eventually render.

|`.layout-view.loaded-state`
|Normal flow. `.view-icon` here plays `slideFromCenter`, delayed by `--loader-handoff`, which is
what produces the rise.

|`.view-content.hidden`
|`opacity: 0`, `translateY(20px)`, `position: absolute`, `visibility: hidden` — out of flow as well
as invisible, so it cannot hold space open under the centred loader.

|`.view-content.visible`
|`opacity: 1`, no transform, with `transition-delay: var(--loader-handoff)` so the fade waits for
the icon's rise to finish before the content follows it.

|`.layout-footer.hidden` / `.layout-footer.visible`
|Same opacity/translateY pair as the content. Its *entrance* animation, though, is keyed off the
content rather than off its own loading flag: `.app-layout:has(.view-content.visible) .layout-footer`
fires `--animate-fade-in-4`. The footer's own `hidden`/`visible` classes still gate layout (display,
pointer-events) and the base transition.
|===

Only the first four direct children of `.view-content` get a staggered entrance —
`.view-content.visible > :nth-child(1..4)` map to `--animate-fade-in-1`..`-4`, each delayed by
`--loader-handoff` plus a fixed offset. `--animate-fade-in-5` exists as a property but no selector in
this stylesheet reaches a fifth child today; a view whose content has five or more top-level
children will have its later ones appear without a stagger unless a new rule is added for them.

=== Pre-mount and navigation overlays

Two more full-viewport elements sit outside `Layout` entirely, for the two gaps `Layout` itself
cannot cover:

[cols="1,4"]
|===
|Element |Covers

|`.initial-loader`
|Static markup in both HTML templates (`index.html.template`, `maintenance.html.template`),
outside `#app`. It is the only thing on screen while the JS bundle and the first view's chunk come
down, and it is removed outright by `Layout.adopt` the moment the first `Layout` mounts — not by a
timer. `.initial-loader.is-fading` is declared, pairing with `brandGlowFlash` on the brand icon, but
nothing in the client sets that class today; the removal is immediate rather than animated.

|`.nav-loader`
|A permanent overlay in `App.app` (never unmounted — see xref:client.adoc[Client]'s *Navigation
integrity*), visibility toggled by `.is-visible`, bound to `AppState.isNavigating`. Its background
repeats the body's gradient, so once visible it opaquely covers the outgoing view while the
destination route's chunk loads and its `Layout` mounts underneath.
|===

`.route-slot` (`display: contents`) is the third piece of that same mechanism: `Router.lazily` wraps
every dynamically-imported view in a div so Laminar's `child <--` binding has a stable parent, and
`display: contents` is what keeps that wrapper out of the box tree so `.app-layout` stays the direct
flex child of `.app-root` — otherwise the extra box would break the centring and `min-height` the
root depends on.

=== The brand icon's own animation

`.brand-icon` breathes continuously while loading (`animation: breathe 1.4s ease-in-out infinite`,
oscillating opacity between `.65` and `1`). Because `breathe` is symmetric — its `0%` and `100%` are
identical — two copies of the icon that mount out of phase (the static `.initial-loader` one and the
first Laminar-rendered one) converge on the same resting appearance with no synchronisation between
them. On the `loading-state → loaded-state` handoff the icon plays `brandGlowFlash` (a white
drop-shadow pulse, `forwards` so the filter returns to `none` once it ends) and `slideFromCenter`,
which lands the icon at the exact point the static loader held it — computed from `--icon-size-lg`,
`--space-lg` and `--space-2xl` against `50dvh` (with a `50vh` fallback for pre-2022 browsers),
because the loader is `position: fixed; inset: 0` and centres on the *current* viewport, and mobile
`vh` resolves against the viewport with the browser chrome hidden while `dvh` follows what is
actually visible.

`.brand-ring`, the wrapper `BrandLoader` still emits, is a historical name: the ring it was named for
was replaced by `breathe` on the icon itself, and the CSS that drew it is gone along with the
`@keyframes ringOut` it used — `ringOut` remains declared in the stylesheet but no rule references
it. `--brand-icon-url` is the same story one layer up: a masked, multi-layer icon was tried, is fully
gone, and left no property behind — the icon today is a plain `<img>`.

== State-class pattern

`Layout`'s `loading-state`/`loaded-state` and `hidden`/`visible` pairing is not special to the shell:
individual views repeat the same shape in their own markup for state that `Layout` does not own —
`WelcomeView`'s `.welcome-text-content.hidden`/`.visible`, `IdentificationQuestionView`'s
`.question-content.question-loading`/`.question-loaded` and its own
`.question-text-content.hidden`/`.visible` nested inside, each wired to that view's own loading
signal rather than `Layout`'s. The convention held across the stylesheet is: a `-loading`/`-loaded`
(or bare `loading-state`/`loaded-state`) modifier drives layout and the icon's position, a nested
`hidden`/`visible` modifier drives the content fade, and the fade is delayed by `--loader-handoff` so
it never races the icon.
