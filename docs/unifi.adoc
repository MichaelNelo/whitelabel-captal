= UniFi integration
:toc:
:toclevels: 2

The venue's UniFi controller hands a guest device to this system through its captive portal, and
when the guest finishes the portal flow the system authorizes that device on the controller for a
bounded time and revokes it when the time is up. This document covers the whole path: the query
parameters the controller sends, the access point check that admits a guest, the event that
triggers the authorize call, the Integration v1 API contract, the configuration — each access
point's controller and the location's own settings — and the network route from a Fargate task to a
controller on a customer LAN.

== Where it lives

The integration is not a module. Its moving parts are spread across four of them:

[cols="2,3"]
|===
| File | What it is

| `platform/src/whitelabel/captal/platform/UnifiClient.scala`
| The HTTP client. One trait, two operations (`authorizeGuest`, `revokeGuestAccess`), both built
  from the same two-step Integration v1 flow. Also the trust-all/proxy `Client` layer.

| `platform/src/whitelabel/captal/platform/UnifiAccess.scala`
| The controller access for one access point: `UnifiAccess.of(ap, durationMinutes)` takes an
  `AccessPointRow`'s host, token, port and site id and its location's access duration.

| `platform/src/whitelabel/captal/platform/services/LocationService.scala`
| The reads by location id and AP MAC: `hasAccessPoint`, which `/api/status` checks a redirect
  with, and `unifiFor`, which builds an AP's `UnifiAccess` when an event needs it.

| `platform/src/whitelabel/captal/platform/eventhandlers/UnifiAccessHandler.scala`
| The post-commit event adapter. Resolves the controller of the session's access point on every
  event, maps `AccessGranted` to authorize and `AccessExpired` to revoke, and on a successful
  authorize writes `Phase.Authorized` plus `accessExpiresAt` and enqueues the expiry job.

| `api/src/whitelabel/captal/api/routes/SurveyRoutes.scala`
| `requireAccessPoint`: the check that turns away a redirect through an access point that is not
  the location's.

| `platform/src/whitelabel/captal/platform/session/JobScheduler.scala`
| `JobQueue` and `JobRunner`: where the expiry deadline is parked and the fibers that fire it. See
  xref:platform.adoc[Platform].

| `mcp/src/whitelabel/captal/mcp/tools/UnifiTools.scala`
| The backoffice tools `configure_unifi`, `get_unifi_config`, `set_unifi_enabled`,
  `update_unifi_settings`, `update_access_point` and `remove_access_point`.

| `mcp/src/whitelabel/captal/mcp/apps/UnifiUi.scala`
| The server-rendered MCP App that collects the credentials, with
  `mcp/src/whitelabel/captal/mcp/apps/UiRoutes.scala` as the endpoint it posts to and
  `client/src/whitelabel/captal/mcpui/unifi/UnifiApp.scala` as its Scala.js behaviour.

| `api/test/src/whitelabel/captal/api/TestUnifiClient.scala`
| The test double that stands in for the transport.

| `platform/resources/db/migration/V16…V19`, `V24`, `V34`
| The `unifi_*` columns on `locations`, `sessions.access_expires_at`, and the `access_points`
  table.

| `terraform/modules/{tailscale-proxy,global-accelerator,portal-dispatcher}`
| The network path: the proxy out to the customer LAN, the static IPv4 the controller points at,
  and the Lambda that turns an AP MAC into a portal slug.
|===

== End-to-end flow

[source]
----
 1. Guest associates to the venue's guest SSID; the controller blocks its traffic.
 2. Controller redirects the device to the external portal server, carrying the session's
    parameters as a query string.
 3. (Deployed only) the Global Accelerator IP → ALB → portal-dispatcher Lambda resolves the
    location slug from the `ap` parameter — the running location that has that access point — and
    302s to the portal, preserving the query string.
 4. The SPA loads, reads the query parameters and forwards them as `X-*` headers on
    `GET /api/status`, which checks that `X-Ap-Mac` is one of the location's access points and
    creates the session row, its `ap_mac` included.
      └─ any other AP, or none → `ApiError.UnknownAccessPoint`; no session, and the error page
               offers no retry.
 5. The guest completes the flow (email → profiling → video → advertiser survey).
 6. The last answer leaves the session in `Phase.Ready`; the client routes to `/ready`.
 7. `ReadyView` mounts and issues `POST /api/finish`, which runs `FinishCommand` and emits
    `UserEvent.UserFinishedProcess` and `AccessEvent.AccessGranted`. A guest who left through an
    error reaches `/ready` from `Phase.Recovered` instead, and `finish` emits `AccessGranted` alone.
 8. The transaction commits. Post-commit, `UnifiAccessHandler` reads the controller of the
    session's access point and calls `UnifiClient.authorizeGuest` with the session's `clientMac`.
      ├─ 2xx → `SessionService.setAuthorized(sessionId, expiresAt)` (phase `Authorized`,
      │        `accessExpiresAt = occurredAt + defaultDurationMinutes`) and
      │        `JobQueue.schedule(ScheduledAt(expiresAt, ExpireAccess(sessionId)))`.
      └─ failure, or no controller for the session's AP → log and return; the session stays
               `Ready`.
 9. `/api/finish` re-reads the session and answers `phase` + `secondsRemaining`.
10. At the deadline the `JobRunner` worker runs `ExpireAccessCommand`, which emits
    `AccessEvent.AccessExpired` — the session's, with or without a user.
11. In the same chain: `SessionExpirationHandler` resets the session row to `Welcome`
    (transactional), `EventLogHandler` writes an `access.expired` row, and post-commit
    `UnifiAccessHandler` reads the controller of the session's access point again and calls
    `UnifiClient.revokeGuestAccess` — which unauthorizes *and* disconnects the client.
----

=== The controller's query parameters

The controller's external-portal redirect carries the device's pre-authorization state in the URL.
`client/src/whitelabel/captal/client/Main.scala` reads five of them and forwards each as a header,
decoding the value once with `decodeURIComponent` (values arrive partially percent-encoded, and a
malformed sequence falls back to the raw string):

[cols="1,2,3"]
|===
| Query parameter | Header | Meaning

| `id` | `X-Client-Mac` | MAC of the guest device. The MAC every authorize call is made for.
| `ap` | `X-Ap-Mac` | MAC of the access point the device associated to. Has to be one of the location's access points, and says which controller authorizes the guest.
| `url` | `X-Redirect-Url` | The URL the guest originally asked for.
| `ssid` | `X-Ssid` | The guest SSID's name.
| `fingerprint` | `X-Fingerprint` | The device fingerprint the link shortener in front of the portal computes, stored on the session and the device.
|===

`client/src/whitelabel/captal/client/views/ErrorView.scala` repeats the same mapping so a retry from
the error page carries the parameters too. `GET /api/status` declares all five as optional headers
(`api/src/whitelabel/captal/api/routes/SurveyRoutes.scala`) and builds a
`CaptivePortalParams(clientMac, apMac, redirectUrl, ssid, fingerprint)` only when `X-Client-Mac`
**and** a non-empty `X-Fingerprint` are both present. Creating a session without them fails with
`ApiError.SessionMissing`; a request that already carries a session cookie ignores the parameters,
save for the access point check below. A MAC header that is not twelve hex digits counts as
missing. The values land on
`sessions.client_mac` and `ap_mac`, each its 48-bit big-endian integer (V31), `redirect_url` and
`ssid` (V11), and `fingerprint` (V14 adds it as `click_id`, V30 renames it).

=== The access point check

An API serving a location admits a redirect only through one of that location's access points,
because the AP is what names the controller: a guest who came through any other could never be
authorized. `SurveyRoutes.requireAccessPoint` runs on every `/api/status` that carries the
redirect's parameters — the pair that builds `CaptivePortalParams` — before any session is resolved
or created, and asks `LocationService.hasAccessPoint` whether the location has an access point with
the `X-Ap-Mac` it was sent. The header is read as a `Mac`, so any spelling matches.

An AP the location does not have, and a header that is missing or is not a MAC, are refused the
same way: a warning in the log and `ApiError.UnknownAccessPoint(apMac)` (400), carrying the MAC as
`Mac.show` writes it, or the raw header when it is not one. No session is created, and nothing is
recorded in `errors`: it is an expected refusal, not a fault to offer a way out of. The client's
`ErrorView` shows `error.unknownAccessPoint` for it and hides the retry button, since retrying
cannot change the AP (see xref:client.adoc[Client]).

An API serving no location (`LOCATION_SLUG` unset, as the API's tests run it) checks nothing.

== Phase semantics

Two session phases carry the whole contract, and the boundary between them is the UniFi call.

[cols="1,4"]
|===
| Phase | Meaning

| `Ready`
| The guest finished the survey flow and the system is waiting on UniFi. Normally a few
  milliseconds; indefinite if the controller is unreachable or the session's access point has no
  configuration.

| `Authorized`
| The controller accepted the authorize action and `accessExpiresAt` is populated. The transition
  is written **only** by `UnifiAccessHandler`, post-commit.
|===

The matching `User` aggregate type-states are `State.Ready`, projected from the session row by
`UserRepository.findReadyUser`, and `State.Authorized`, the result type of the `finish` op. Expiry
is not the user's: `ExpireAccessHandler` reads the session itself. See xref:core.adoc[Core].

=== Retry by design

Because the phase stays `Ready` (or `Recovered`) until the controller answers 2xx, a second
`POST /api/finish` grants access again, re-emits `AccessGranted` and retries the authorize call. The client exploits this directly: `ReadyView` calls `/api/finish` from
its `onMountCallback`, so a reload of `/ready` is a retry.

The retry is safe because the authorize action is idempotent per MAC — the controller cancels any
existing active authorization for that client, creates a new one with the new limits and resets the
guest's traffic counters.

=== What the guest sees

[cols="1,4"]
|===
| Branch | Guest experience

| Authorize succeeds
| `/api/finish` answers `phase = authorized` with `secondsRemaining`. The router switches to
  `WelcomeView`, which counts down from that number and schedules one `setTimeout` for the
  deadline. The device has internet.

| Authorize fails, times out, or the session's access point has no UniFi configuration
| `/api/finish` answers `phase = ready` and `secondsRemaining = null`. The guest stays on `/ready`
  with the spinner; no network access is granted. A reload retries.

| No `Ready` session
| `/api/finish` is rejected before the flow runs: the route authorises only `Phase.Ready` and
  answers 400 with an `ApiError`.

| Redirected through an access point that is not the location's
| `/api/status` answers `UnknownAccessPoint` and no session is created. The guest sees the error
  page with `error.unknownAccessPoint` and no retry button, before the first screen.
|===

A location that is fully translated, has videos and deploys cleanly but has no access point
therefore turns every guest away at the first page, whatever its UniFi switch says. This is what
`get_unifi_config` and the `unifiConfigured` field of the readiness resource exist to surface — see
xref:mcp.adoc[MCP backoffice].

== Scheduled revocation

On a successful authorize the handler enqueues `ScheduledAt(expiresAt, ScheduledJob.ExpireAccess(sessionId))`
on the `JobQueue`. That is the scheduler's only producer. What is enqueued is data rather than an
effect, which is what lets startup rehydration rebuild the same job by reading the `sessions` table.

`JobRunner.start` (called from `api/src/whitelabel/captal/api/Main.scala`, never by building the
layer) forks two fibers and then rehydrates:

* a scheduler fiber holding pending deadlines in a `SortedMap[Instant, List[ScheduledJob]]` and
  waiting with `inbox.take.timeout(wait)`, so a newly scheduled job with an earlier deadline
  recomputes the wait without interrupting anything;
* a worker fiber — a single one, so there is at most one in-flight request against the controller —
  that takes due jobs and runs `ExpireAccessCommand` with the session installed in the ambient
  `SessionContext`, exactly as a request would;
* rehydration from `SessionService.findPendingExpirations()`, which selects this location's sessions
  that are `Authorized` with a non-null `access_expires_at`. Deadlines already past fire
  immediately, because the computed wait is zero.

The worker swallows and logs its errors, so neither an unreachable controller nor an rqlite failure
can kill the fiber. The staleness guard is in the command handler, not the runner: a session no
longer `Authorized`, or authorized again until later, makes the command a silent no-op. Details of the scheduler are in xref:platform.adoc[Platform]; the event chain is in
xref:event-sourcing.adoc[Event sourcing].

The cut therefore happens whether or not the guest still has the portal open — nothing in the
expiry path depends on a client request.

`GET /api/status` keeps an independent expiry check as a safety net. When the session is
`Authorized` and `accessExpiresAt` is already in the past, the route calls
`SessionService.resetForExpiration` and answers `Phase.Welcome` with no `secondsRemaining`:

[source,scala]
----
isExpired = session.phase == Phase.Authorized && session.accessExpiresAt.exists(_.isBefore(now))
----

This covers the cases the in-memory scheduler cannot: a task that restarted and has not rehydrated
yet, a scheduler that is not running, and an access point with no UniFi configuration at all. Note that
this branch resets *our* session row; it issues no revoke, because no authorization was ever
recorded for it to revoke.

== The Integration v1 API

The client speaks the UniFi Network **Integration v1** API, served by the controller itself (a UCG,
UDM or other UniFi OS console). The cloud Site Manager API at `api.ui.com` is a different thing and
is not used.

=== Base URL and authentication

[source]
----
https://<host>:<port>/proxy/network/integration/v1
----

`UnifiClient.baseUrl` builds this from the access point's `host` and `port`, bracketing the host per
RFC 3986 when it contains a colon (an IPv6 or Tailscale ULA address). Every request carries a static
API key — no login, no session cookie, no CSRF token:

[source,http]
----
X-API-KEY: <token>
----

The key is created on the controller under Settings → Control Plane → Integrations → Create API Key.
A single operation (lookup plus action) is bounded by a 10-second timeout; exceeding it fails with
`UniFi <ACTION> timed out after 10s`.

=== Site discovery

The site is addressed by UUID. `GET /sites` is how that UUID is found:

[source,http]
----
GET https://<host>:443/proxy/network/integration/v1/sites
X-API-KEY: <token>
----

[source,json]
----
{"data": [{"id": "<uuid>", "internalReference": "default"}]}
----

The `id` is what goes into the access point's `unifi_site_id`. A `curl` to this endpoint needs `-k`,
because the controller's certificate is self-signed.

=== Authorize a guest

Two requests. First the client id is looked up by MAC, because the action endpoint is addressed by
client id and the system only knows the MAC:

[source,http]
----
GET https://<host>:443/proxy/network/integration/v1/sites/<siteId>/clients
      ?filter=macAddress.eq('aa:bb:cc:dd:ee:ff')
X-API-KEY: <token>
----

The filter expression is URL-encoded by the client, and the MAC is written as the controller stores
it (`Mac.show`: lower case, colon-separated). The response is the usual envelope and
the client takes the first `id` from `data`:

[source,json]
----
{"data": [{"id": "<clientId>", "macAddress": "aa:bb:cc:dd:ee:ff"}]}
----

A non-2xx status fails with `UniFi GET /clients returned <code>: <body>`; an empty `data` array
fails with `no client found for MAC <mac>`.

Then the action is posted:

[source,http]
----
POST https://<host>:443/proxy/network/integration/v1/sites/<siteId>/clients/<clientId>/actions
X-API-KEY: <token>
Content-Type: application/json
----

[source,json]
----
{
  "action": "AUTHORIZE_GUEST_ACCESS",
  "timeLimitMinutes": 1440
}
----

`timeLimitMinutes` is `UnifiAccess.defaultDurationMinutes`, the location's access duration. The schema also accepts
`dataUsageLimitMBytes`, `rxRateLimitKbps` and `txRateLimitKbps`; this client sends none of them, so
the body it emits is the discriminator plus the time limit and nothing else.

=== Revoke guest access

Same lookup, same path, same headers. The body is the discriminator alone:

[source,json]
----
{"action": "UNAUTHORIZE_GUEST_ACCESS"}
----

IMPORTANT: `AUTHORIZE_GUEST_ACCESS` and `UNAUTHORIZE_GUEST_ACCESS` are the *only* two client actions
the controller's schema admits. There is no `DISCONNECT`, `KICK` or `FORCE_RECONNECT`, and none is
needed: unauthorizing a guest client also disconnects it. The two literals are spelled once each, as
`UnifiClient.AuthorizeAction` and `UnifiClient.RevokeAction`.

A 200 response carries a required `revokedAuthorization` object (`authorizationMethod`,
`authorizedAt`, `expiresAt`, `usage`, rate limits). The client ignores the body and only checks the
status code.

== Configuration

Configuration is rows in the database, written by the MCP backoffice. There is no configuration
file. A location has any number of access points, each a row in `access_points` carrying the
controller that authorizes the guests who join through it — a venue's APs need not share a
controller — and its `locations` row carries the settings that are the location's, whichever AP a
guest came through.

=== Access points

[cols="2,2,1,1,1,4"]
|===
| Column (`access_points`) | `AccessPointRow` field | Type | Optional | Default | What it controls

| `location_id` | `locationId` | TEXT | required | — | The location the AP belongs to.
| `mac` | `mac` | TEXT | required | — | The AP's MAC, lowercase with colons as `Mac.show` writes it.
  What `/api/status` checks `X-Ap-Mac` against, what the portal dispatcher matches the `ap`
  parameter on, and what a session's `ap_mac` finds its controller by. Unique within a location.
| `unifi_host` | `unifiHost` | TEXT | required | — | Controller address on the customer LAN, without
  scheme or port. An IPv6/ULA literal is bracketed automatically.
| `unifi_api_token` | `unifiApiToken` | TEXT | required | — | The `X-API-KEY` value.
| `unifi_site_id` | `unifiSiteId` | TEXT | required | — | Site UUID in every request path. Must be
  the UUID from `GET /sites`, not a site name.
| `unifi_port` | `unifiPort` | INTEGER | optional | `443` | Controller port.
|===

`id` is a random UUID for a row the backoffice writes, and `created_at`/`updated_at` are its
stamps. The same MAC may be registered in several locations, so that one can take a venue over from
another; the backoffice keeps at most one of them running (see <<Which tool writes them>>).

=== Location settings

[cols="2,2,1,1,1,4"]
|===
| Column (`locations`) | `LocationRow` field | Type | Optional | Default | What it controls

| `unifi_duration_minutes` | `unifiDurationMinutes` | INTEGER | optional | `1440` (24 h) | The
  authorize call's `timeLimitMinutes` and the `accessExpiresAt` the session is stamped with, for
  every access point of the location.
| `unifi_redirect_url` | `unifiRedirectUrl` | TEXT | optional | dispatcher default
  `https://<cloudfront-host>/<slug>/` | Overrides where the dispatcher sends the location's guests,
  preserving the controller's query parameters. For a location running its own portal SPA behind
  this system's static IP; not where a guest goes after authorizing.
| `unifi_is_enabled` | `unifiIsEnabled` | INTEGER | optional | `1` | Whether the portal calls a
  controller at all. `0` skips both authorize and revoke, whatever else is configured, and keeps the
  access points as they are.
|===

=== How the portal reads them

"Required" means an access point is never stored without it: those columns are `NOT NULL`, and the
backoffice refuses a submission that leaves one out. An access point is therefore a whole
configuration, and `UnifiAccess.of` builds from one with nothing left to check:

[source,scala]
----
def of(ap: AccessPointRow, durationMinutes: Option[Int]): UnifiAccess = UnifiAccess(
  host = ap.unifiHost,
  apiToken = ap.unifiApiToken,
  port = ap.unifiPort.getOrElse(443),
  siteId = ap.unifiSiteId,
  defaultDurationMinutes = durationMinutes.getOrElse(1440))
----

None of this is read at startup: `CurrentLocation`, resolved once from `LOCATION_SLUG`, holds only
the served location's id and slug. The handler resolves the controller on every `AccessGranted` and `AccessExpired`, through the resolver
`Flows.unifiFor` builds — `LocationService.unifiFor(locationId, mac)` with the served location's id
and the session's `ap_mac`, which reads that location's access point with that MAC and the
location's `unifi_duration_minutes`. With no such AP, or a session without one, it answers `None`:
the handler logs `UniFi <action>: AP <mac> has no configuration for the current location —
skipping` and returns, so the session stays `Ready`. If the read fails, the handler logs the error
and skips. A change to an access point or to the duration therefore reaches the next guest that
finishes or expires, with no task restart.

`unifi_is_enabled` is read the same way, and first: before resolving the controller the handler
reads the switch from the row (`LocationService.unifiEnabled`, wired in `Flows.unifiEnabled`). With
`0` it logs `UniFi <action>: disabled for current location — skipping` and returns the same way, so
the session stays `Ready`. Turning it off or back on takes effect on the next guest that finishes
or expires. If the read itself fails, the handler logs the error and skips. An API run with no
location (`LOCATION_SLUG` unset) has no switch and no access points: its resolver answers `None` for
every session, so it authorizes nobody.

The migrations that shaped these columns: **V16** added `unifi_host`, `unifi_port`, `unifi_site`,
`unifi_use_os`, `unifi_api_token` and `unifi_duration_minutes` to `locations`. **V17** added
`sessions.access_expires_at` (TEXT, an ISO-8601 instant). **V18** moved to Integration v1 — renamed
`unifi_site` to `unifi_site_id` for the shift from name to UUID, and dropped `unifi_use_os`, which
the uniform `/proxy/network/integration/v1` path made irrelevant. **V19** renamed the standalone
`ap_mac` (V11) to `unifi_ap_mac` and added `unifi_redirect_url`. **V24** added `unifi_is_enabled`.
**V34** creates `access_points`, with an index on `mac` for the dispatcher, and copies into it each
location that had a complete configuration and an AP MAC that reads as one, as its one access point:
the MAC written as `Mac.show` would, the id `<location_id>/<mac>` and both stamps the location's
`updated_at`, since rqlite runs a statement on every node and a value that differed between them
would split the replicas. See xref:database.adoc[Database].

The columns V34 copied from — `unifi_ap_mac`, `unifi_host`, `unifi_port`, `unifi_site_id` and
`unifi_api_token` — stay on `locations` for one release: a dispatcher or an API still on the
previous release reads them until it is replaced. This release reads none of them, save the
dispatcher's fallback on a database V34 has not reached (below), and writing them changes nothing.
A later migration drops them.

=== Which tool writes them

`configure_unifi` (`UnifiTools.configure`, scope `content:write`) registers an access point, and is
the only writer of the tokens. It takes a slug and, optionally, `apMac`: no token travels through
the conversation. The tool returns a short-lived ticket, an absolute `postUrl`, the location's
access duration and redirect URL, and — when `apMac` names one of the location's access points, in
any spelling — that AP's MAC, host, port and site id, with `tokenSet: Boolean` in place of its
token; an `apMac` the location does not have is refused. Without `apMac` the page opens to register
a new one. The tool points the host at the MCP App `ui://configure-unifi`. The operator types the
settings into that page and the browser posts them directly to `POST /ui/unifi`
(`mcp/src/whitelabel/captal/mcp/apps/UiRoutes.scala`), outside the MCP protocol.

Behaviour of that write:

* The ticket is the authorization. It is signed with the calling operator token's own stored SHA-256
  hash, names one location, and expires in minutes — so revoking the token invalidates the pages it
  opened without touching anyone else's. `Access-Control-Allow-Origin: *` is safe on the route
  precisely because no cookie or ambient header grants anything there.
* One submission is one access point. Its MAC names it, read in any spelling and stored lowercase
  with colons: a MAC the location already has updates that AP, any other registers a new one. The
  MAC, `host` and `siteId` are required on every submission; `apiToken` only when that access
  point has none stored.
* A blank token means "keep the stored one", not "unset". This is how the form avoids ever
  rendering a stored token back. The other fields are written as the form sends them, which is why
  the page opens filled with what is stored.
* `port` and `durationMinutes` must parse as positive integers or the page shows an error.
* The access duration and the redirect URL on the same form are the location's, for all its access
  points, and are written with the AP.
* An access point that another running location — active, and not paused — already has is
  refused, naming that location and asking for it to be paused first: an AP takes the guests of
  one running location, which is what the portal dispatcher counts on.
* The response body names the AP and the host it configured and never the token.

`get_unifi_config` (`UnifiTools.status`, read-only) reports `configured` — whether the location has
at least one access point — and `accessPoints`, each with its `apMac`, `host`, `port`, `siteId` and
`tokenSet`, beside the location's `redirectUrl`, `durationMinutes` and `enabled`. The token value is
never returned by any tool.

`set_unifi_enabled` (`UnifiTools.setEnabled`, scope `content:write`) is the only writer of
`unifi_is_enabled`. It takes a slug and `enabled`, leaves every other column and the access points
alone, and answers with the same report as `get_unifi_config`. The readiness resource reports the
switch as `unifiEnabled`, and asks for an access point whether it is on or off, since without one
every guest is turned away at the first page.

`update_unifi_settings` (`UnifiTools.updateSettings`, scope `content:write`) changes the location's
own settings without the form: its redirect URL and access duration. Each field given replaces the
stored one and every field left out stays; an empty redirect URL removes it, and giving neither is
refused. The redirect URL has to be http or https and the duration positive. It never touches the
access points or the switch, and answers with the same report as `get_unifi_config`. The duration
is read on every authorize and the redirect URL by the dispatcher on every redirect, so a change
applies with no redeploy.

`update_access_point` (`UnifiTools.updateAccessPoint`, scope `content:write`) changes one access
point's settings that are not secret without the form: `newApMac`, for an AP that was replaced, and
its controller's `host`, `port` and `siteId`. The AP is named by `apMac`, in any spelling. Each
field given replaces the stored one and every field left out stays; giving none is refused. Host and
site id cannot be blank, the port is 1 to 65535, and a new MAC has to read as a MAC and is stored
lowercase with colons. A new MAC the location already has, or one another running location has, is
refused. It never touches the token, and answers with the same report as `get_unifi_config`. The
next authorize or revoke reads it, with no redeploy.

`remove_access_point` (`UnifiTools.removeAccessPoint`, scope `content:write`) takes an access point
off a location, with its controller's settings and token, and answers with the same report as
`get_unifi_config`. A guest who comes through it afterwards is turned away at `/api/status`. One
already authorized through it keeps the access until it runs out, and the revoke at the deadline is
skipped, since there is no controller left to ask; changing an AP's MAC does the same to the
sessions that came through the old one.

`deploy_location` and `resume_location` refuse, before they start a run, a location that shares an
access point with another running location (`UiRoutes.refuseSharedAccessPoints`): both make the
location take its access points' guests. Pausing the other location first is the way through.

=== The proxy URL

One setting is neither an access point's nor a location's: the HTTP proxy the API dials every
controller through.
`api/resources/application.conf` reads it from the environment —

[source]
----
unifi {
  proxy-url = ""
  proxy-url = ${?UNIFI_PROXY_URL}
}
----

— and `ServerSettings.unifiProxyUrl` feeds `UnifiClient.trustAllClientLayer`. Empty means a direct
connection, which only works when the API runs on the controller's own LAN (local development). An
unparseable value fails the layer at startup with `Invalid UNIFI_PROXY_URL '<raw>'`.

== Network path in deployment

A Fargate task has no route to a customer's LAN, so the deployed chain is:

[source]
----
API task (ECS Fargate)
  → HTTP CONNECT proxy  tailscale-proxy.<namespace>:1055  (Fargate, Tailscale userspace)
  → tailnet
  → Tailscale subnet router (VM on the customer's premises)
  → customer LAN
  → UniFi controller :443
----

=== The Tailscale proxy

`terraform/modules/tailscale-proxy/` runs the `tailscale/tailscale:stable` image as its own Fargate
service, registered in service discovery as `tailscale-proxy.<namespace>` (A record, TTL 10). Its
container environment is the contract:

[cols="2,3"]
|===
| Variable | Value and purpose

| `TS_USERSPACE` | `true` — Fargate does not allow `tun`/`tap` devices.
| `TS_OUTBOUND_HTTP_PROXY_LISTEN` | `0.0.0.0:1055` — the HTTP CONNECT listener the API dials.
| `TS_EXTRA_ARGS` | `--accept-routes` to pick up the on-prem router's subnet advertisements, plus
  `--advertise-routes=<vpc_cidr>` so tailnet devices can reach VPC resources. The advertised route
  must be approved once in the Tailscale admin console.
| `TS_STATE_DIR` | `/tmp/tailscale` — the Fargate filesystem is read-only outside `/tmp`.
| `TS_AUTHKEY` | From Secrets Manager. The key is minted by Terraform (reusable, ephemeral,
  preauthorized, tagged `tag:captal-proxy`), and the secret's version id is passed in as a plain
  environment variable so a rotation changes the task definition and rolls the service.
|===

Its security group accepts ingress on 1055 only from the application task security group, and allows
all egress (the Tailscale control plane, STUN and DERP relays all need it). The module's `proxy_url`
output is the value `UNIFI_PROXY_URL` expects: `http://tailscale-proxy.<namespace>:1055`.

That output reaches the API by the same route `DB_URL` does. `terraform/main.tf` passes it to the
`mcp` module, which sets `UNIFI_PROXY_URL` on the backoffice's own task; `DeployTargets` reads it at
startup, and `Deploy.registerTaskDefinition` writes it into every location's task definition beside
`LOCATION_SLUG` and `DB_URL`. With `enable_tailscale` off the variable is absent, the backoffice logs
a warning at startup, and a deployed location dials its controller directly.

`DeployE2ESpec` reads the registered task definition back from ECS and asserts the variable is there.

=== TLS

UniFi consoles serve a self-signed certificate, so the client layer trusts all certificates:

[source,scala]
----
ZClient.Config.default.copy(ssl = Some(ClientSSLConfig.Default), proxy = proxy)
----

In zio-http 3.x `ClientSSLConfig.Default` is trust-all. Transport security on this path is provided
by the Tailscale overlay, not by the TLS session: the tunnel is what authenticates the peer and
encrypts the carriage. In local development, where there is no tunnel, the call is plain trust-all
HTTPS on the LAN.

=== Static IPv4 and the portal dispatcher

The controller's External Portal Server field validates as IPv4 only — it takes no hostname — so the
portal needs a stable address rather than a CloudFront domain.

`terraform/modules/global-accelerator/` provisions a standard accelerator (`ip_address_type =
IPV4`), which yields two static anycast IPv4 addresses that survive ALB recreation. Either one goes
in the controller's External Portal Server field. The listener is TCP/80 with
`client_affinity = NONE`, and the endpoint group sends 100% of traffic to the ALB, health-checked on
`GET /` port 80 (the ALB's 301 counts as healthy).

`terraform/modules/portal-dispatcher/` is the next hop. An ALB HTTP listener rule on `/guest/s/*`
(priority 100, created by `terraform/modules/alb/` when `enable_portal_dispatcher_rule` is set)
forwards to a Lambda target group running `dispatcher.py`:

. Read the `ap` query parameter and lowercase it; a missing one is a 400. Write it as
  `access_points.mac` is written, twelve hex digits joined by colons, whatever separators it came
  with; a value that is not a MAC is left as it is.
. `SELECT l.slug, l.unifi_redirect_url FROM access_points a JOIN locations l ON l.id =
  a.location_id WHERE a.mac = '<ap>' ORDER BY l.created_at DESC` against rqlite over its HTTP API
  (`http://rqlite.<namespace>:4001`, `level=none`, 5-second timeout): every location that has that
  access point, newest first. When rqlite answers it with an `error` — a database V34 has not
  reached, with no `access_points` table — the Lambda logs it and asks the locations' own AP column
  instead, `SELECT slug, unifi_redirect_url FROM locations WHERE LOWER(unifi_ap_mac) = '<ap>' ORDER
  BY created_at DESC`. An unreachable database is a 503; no matching row is a 404 naming the AP.
. Take the newest of those locations that is not paused. Several running ones sharing an AP are
  logged, and the newest takes the guests; with every one paused, the newest, whose page is the
  maintenance page.
. 302 to its `<unifi_redirect_url><?|&><params>` when the override is set and the location is not
  paused, otherwise to `https://<CLOUDFRONT_HOST>/<slug>/?<params>`, with `Cache-Control:
  no-store`. Every query parameter the controller sent is forwarded verbatim. The override sends
  the location's guests to a portal hosted elsewhere instead of this one; it is not where a guest
  goes after authorizing.

So a location can take over an AP from another by pausing the old one: the AP's guests go to the
location that is running. The backoffice keeps it to one running location per AP — registering an AP
another running location has is refused, and so is deploying or resuming a location that shares one
— so the newest-wins rule above is for a state the backoffice does not leave.

Which locations are paused is read from the assets bucket: `pause_location` keeps the page it
replaces at `_paused/<slug>/site.html`, and `resume_location` and `deploy_location` remove it, so the
object exists exactly while the location is paused. The Lambda lists `_paused/` once per request,
and only when there is a choice to make — several locations, or an override to skip — since
otherwise every answer leads to the same page. A listing that fails is logged and reads as none
paused.

So the AP MAC is what selects the portal: one static IP serves every location, and a new location
needs only its access points registered. The whole accelerator-plus-dispatcher pair is behind
`enable_global_accelerator`, which environments that do not integrate with UniFi leave off. See
xref:infrastructure.adoc[Infrastructure].

== Known caveats

* **The site identifier is a UUID, not a name.** The API documentation writes `{siteId}`
  ambiguously, but the endpoint accepts only the UUID returned by `GET /sites`. Putting `default`
  there yields 404 on every call.
* **Self-signed TLS.** The client trusts all certificates by configuration. Outside the Tailscale
  tunnel there is no peer authentication on this connection at all.
* **A client lookup is empty until the device has associated.** `GET /clients?filter=…` only knows
  devices that are on the guest network, even pre-authorization. If the device has not associated,
  or associated to a different SSID, `data` is `[]`, the client fails with
  `no client found for MAC …`, and the handler logs an error and leaves the session in `Ready` for
  the next `POST /api/finish` to retry.
* **The filter is an exact string match.** The controller stores lowercase-with-colons, so the
  client writes the MAC with `Mac.show`; a MAC in any other spelling would find nothing. Every MAC
  the API holds is a `Mac` (`core/device/Mac.scala`), read from `X-Client-Mac` in any spelling — `:`
  or `-` or no separator, either case — and stored as its 48-bit big-endian integer.
* **API-key scope follows the admin who created it.** The token belongs to that administrator
  account; if the account is removed the token stops working. Rotation is manual — re-run
  `configure_unifi` with the new value, once for each access point on that controller, since each
  stores its own copy.
* **The legacy `/api/s/<site>/cmd/stamgr` endpoint is deprecated and unused.** Nothing in this
  system calls it, and nothing calls the legacy `stat/sta` polling endpoint either: the expiry
  deadline is this system's own, computed from `defaultDurationMinutes`, and the controller is never
  asked what it thinks a session's remaining time is.
* **Revoke failures are absorbed, not retried.** The session reset is already committed when the
  revoke runs, so the guest is back at `Welcome` either way, and the controller drops the
  authorization on its own `timeLimitMinutes`. There is no second attempt.
* **A session without a `clientMac` skips the revoke** with a warning. Sessions created before
  V31 carry none.
* **Both events in one batch resolve to authorize.** The handler matches `AccessGranted` first, so
  a batch carrying both it and `AccessExpired` takes the authorize branch only.
* **The controller is resolved when the event runs, not when the guest arrived.** A guest
  authorized through an access point that is removed, or given another MAC, before the access runs
  out keeps it until the controller's own `timeLimitMinutes`: the revoke at the deadline finds no
  controller for the session's `ap_mac` and is skipped with a warning.
* **"Configured" is one thing everywhere: at least one access point.** `get_unifi_config`'s
  `configured`, and `unifiConfigured` in `list_locations` and the readiness resource, all report
  whether the location has an access point, and an access point is stored only whole. None of them
  checks that its controller answers.

== Testing

`api/test/src/whitelabel/captal/api/TestUnifiClient.scala` is the only stand-in for the controller.
It implements `UnifiClient` and records `Call.Authorize(mac)` / `Call.Revoke(mac)` instead of
reaching the network, so the suites exercise the production `UnifiAccessHandler` with only the
transport swapped. It starts **inactive**, and while inactive every call fails — which is the
"UniFi is not answering" path, asserted directly.

`TestLayers` wires it in place of `UnifiClient.layer` and builds `UnifiAccessHandler` with a
resolver that answers one fabricated `UnifiAccess` (`host = "unifi.test"`,
`defaultDurationMinutes = 0`) for every session's AP, so the handler walks the real code path and
every authorization is due the instant it is granted. The tests' API serves no location
(`CurrentLocation.empty`), so its `/api/status` checks no access point.
`suites/AuthorizedSuite.scala` covers the four outcomes that matter: `/api/status` reporting
`Authorized` with `secondsRemaining`, the `/api/status` reset when the expiry is already past,
`/api/finish` leaving the session in `Ready` when the authorize call fails, and the full scheduler
path — authorize, then a `JobRunner`-driven expiry that resets the session, records
`access.expired` and issues the revoke, all without the client asking for anything. It also covers
the access points, against an API serving a location with `TestFixtures.seedAccessPoint`: a
redirect is admitted through one of the location's APs in any spelling, and refused with
`UnknownAccessPoint` and no session through another or none; and `Flows.unifiFor` resolves each AP
to its own controller with the location's duration, and to none for an unknown AP, a session
without one, or an API serving no location.
`suites/RecoverySuite.scala` runs the same path for a session authorized through a way out before
it had a user.
`UnifiClient.noop` is the no-op implementation for any wiring that must never reach a controller.

`UnifiClient` itself has no unit test. Its pure parts — `baseUrl` and `extractClientId` — are
public and testable, but `platform` has no test module in `build.mill` (`core`, `api` and
`mcp` do), so there is nowhere in the build for such a suite to live. See
xref:context/pending.adoc[Pending work] and xref:testing.adoc[Test strategy].
