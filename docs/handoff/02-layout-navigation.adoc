== Patrón de handoff del nav-loader

*Regla*: la vista que triggera navegación prende `AppState.setNavigating(true)`
antes de `syncWithPhase(...)`. La *nueva vista* apaga el nav-loader al mount
vía `Layout.onMount`. Ninguna vista debe llamar `setNavigating(false)` en su
código de submit.

Motivo::
  Antes se llamaba `setNavigating(true)` + `syncWithPhase(...)` + `setNavigating(false)`
  todo en el mismo tick. `syncWithPhase` cambia el signal del splitter, que
  emite el nuevo `.route-slot`. Pero el `.route-slot` aún está esperando que
  baje el chunk lazy del dynamic import. Con throttling, ese gap puede ser
  significativo — user veía la vista anterior "congelada" hasta que el
  chunk terminaba de bajar.

Implementación (`views/Layout.scala`)::
  ```scala
  def apply(...): HtmlElement = div(
    cls := "app-layout",
    onMountCallback(_ => AppState.setNavigating(false)),
    ...
  )
  ```

Callsites que se limpiaron (removimos `AppState.setNavigating(false)` post-syncWithPhase)::
  * `WelcomeView.startFlow` línea ~207
  * `IdentificationQuestionView` línea ~403
  * `AdvertiserVideoSurveyView` línea ~316
  * `AdvertiserVideoView.markAsWatched` líneas ~383, ~385
  * `ErrorView.retry` líneas ~104, ~106
  * `ReadyView.resetPhase` línea ~46

`ErrorHandler.escalate`::
  Enciende el nav-loader *antes* de `Router.navigateToError()` — el chunk
  lazy de ErrorView también tarda en bajar, y sin overlay el user ve la
  vista donde ocurrió el error hasta que Error monte. Layout.onMount de
  Error lo apaga solo.
  ```scala
  def escalate(error: ApiError): Unit =
    AppState.setNavigating(true)
    AppState.setError(Some(error))
    Router.navigateToError()
  ```

== `Router.syncWithPhase` con dedup

Bug previo::
  `ReadyView.callFinish` polling: cuando UniFi no autoriza, el server
  responde `phase=Ready` → `syncWithPhase(Ready)` → `router.pushState(Page.Ready)`.
  Waypoint's `currentPageSignal` re-emite en cada `pushState` incluso si la
  page es la misma. La SplitRender emitía de vuelta el mismo HtmlElement,
  Laminar dedupificaba por ref y no hacía nada... pero según los tests, el
  ciclo se disparaba de otra forma. En cualquier caso: infinite loop de
  `/api/finish`.

Fix (`Router.scala:126`)::
  ```scala
  def syncWithPhase(phase: Phase): Unit =
    val targetPage = phaseToPage(phase)
    if router.currentPageSignal.now() != targetPage then
      router.pushState(targetPage)
  ```

== `.route-slot` con `display: contents`

`Router.lazily(...)` envuelve cada dynamic import en un `div` (necesita
un parent estable para el `child <-- EventStream.fromJsPromise(...)`). Ese
div queda entre `.app-root` (flex, justify-content: center) y `.app-layout`
del Layout de la vista (con `max-width: content-max-width`). Rompía el
centrado y el `min-height: 100%`.

Fix::
  El wrapper tiene `class="route-slot"` con:
  ```
  .route-slot { display: contents; }
  ```
  → transparente al layout tree. `.app-layout` queda como si fuera child
  directo de `.app-root`.

== Estructura de `App.app`

```scala
val app: HtmlElement = div(
  cls := "app-root",
  child <-- Router.splitter.signal,   // view actual
  navigationLoader)                   // overlay permanente

private def navigationLoader: HtmlElement = div(
  cls                := "nav-loader",
  cls("is-visible") <-- AppState.isNavigating,
  BrandLoader())
```

Motivo (importante)::
  `navigationLoader` es *permanente* — nunca se desmonta. Alternativa
  anterior era swap via `child <--` (loading vs view). Eso hacía que:
  * El BrandLoader del nav-loader se re-creara cada vez que `isNavigating`
    toggle → animation reset visible.
  * Historically también rompía `syncSpin` (que ya no existe).

CSS relevante::
  ```
  .nav-loader {
    position: fixed;
    inset: 0;
    display: flex; align-items: center; justify-content: center;
    background: linear-gradient(...);  /* gradient del body → opaco */
    opacity: 0;
    visibility: hidden;
    pointer-events: none;
    transition: opacity 0.15s ease-out, visibility 0s linear 0.15s;
  }
  .nav-loader.is-visible {
    opacity: 1;
    visibility: visible;
    transition: opacity 0.15s ease-out, visibility 0s linear 0s;
  }
  ```

== ErrorView

Estructura::
  Usa Layout, pero con `isLoading` compuesto:
  ```scala
  isLoading = justMounted.signal.combineWith(I18nClient.isLoaded).map:
    (just, loaded) => just || !loaded
  ```
  Force `loading-state` durante un tick con `setTimeout(0)` para que
  `slideFromCenter` (y el resto de la transición) se dispare aunque el
  user ya tenga i18n cargado. Sin esto, ErrorView aparecía en loaded-state
  directo → sin transición visual desde el nav-loader → salto abrupto.

`setTimeout(0)` vs microtask vs `requestAnimationFrame`::
  Ambos microtask y rAF corren *antes* del próximo paint. El toggle
  `loading→loaded` sucedería en el mismo frame → browser jamás pinta la
  fase `loading` → transición CSS no arranca. `setTimeout(0)` va al
  macrotask queue → drena después del paint → un frame de loading, cambio
  de clase, siguiente frame arranca la animation.

`ensureLocaleLoaded`::
  Si `!I18nClient.isLoadedNow` (típico en boot-error path donde nunca hubo
  status successful), dispara `WelcomeApi.getLocales()` y setea el primero
  con `I18nClient.setLocale(head)`. Esto asegura que los textos de la
  página de error se muestren (título/mensaje/botón retry) en vez de
  strings vacíos.
