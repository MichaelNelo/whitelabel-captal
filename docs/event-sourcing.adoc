= Event sourcing
:toc:
:toclevels: 2

Every change the portal makes to its database is caused by a domain event. Command handlers in xref:core.adoc[Core] emit events and write nothing; the handler chain in xref:platform.adoc[Platform] does all the writing, transactionally for the database and post-commit for the UniFi controller. This document is the catalogue of those events, the two chains that consume them, and the guest journey they drive.

== Shape of the model

The model is event-*driven* persistence, not an event store that state is replayed from:

* current state lives in relational tables — `sessions`, `users`, `answers`, `video_views`, `user_survey_progress`;
* an event is the only thing that causes a write to those tables during a request;
* `event_log` is an append-only audit trail. Nothing in the application reads it, and no projection is rebuilt from it;
* `core` contains no SQL and no effect type; it produces `List[Event]` and hands them over.

Three aggregates emit: `user`, `survey` (wrapping `survey.question`) and `video`. `application.Event` is the sum of the three, and the whole chain is written against it.

== From command to events

[source,scala]
----
// core/src/whitelabel/captal/core/application/Flow.scala
def execute(command: C): F[R] =
  for
    opResult <- handler.handle(command)
    result   <- MonadThrow[F].fromEither(Op.run(opResult).left.map(HandlerError(_)))
    (events, value) = result
    _ <- eventHandler.handle(events)
  yield value
----

The path of one request:

. The route resolves the session and checks the phase (`SessionEndpoint.authorise`), then publishes it into the ambient `SessionContext`. Every repository and every handler reads the session from there, which is why no command carries a session id.
. The route reads the clock once and builds the command — `occurredAt` is always supplied from outside the domain.
. The handler queries repositories and returns `F[Op[Result]]`. Nothing has been written yet.
. `Op.run` yields either a `NonEmptyChain[Error]` — which becomes `Flow.HandlerError`, then an `ApiError` (see xref:messages.adoc[Messages]) — or a pair of `List[Event]` and the result.
. The events go to the composed `EventHandler[Task, Event]`: first the transactional chain inside one database transaction, then the post-commit chain.
. The result is serialised. Some routes additionally write `sessions.phase` themselves when the response carries a fallback `NextStep` that no event implies.

A failed command emits nothing, by construction: `Op` only carries events on its success side.

== Event catalogue

=== User events

`core/src/whitelabel/captal/core/user/Event.scala`. All carry `occurredAt: Instant`.

[cols="2,3,2"]
|===
| Event | Payload | `event_log.event_type`

| `UserCreated`
| `userId`, `email`
| `user.created`

| `UserRecognized`
| `userId`, `email` — an email already answered: the session becomes that user's
| `user.recognized`

| `NewUserArrived`
| `userId`, `nextQuestion: Option[FullyQualifiedQuestionId]`
| `user.new_arrived`

| `SurveyAssigned`
| `userId`, `nextQuestion: FullyQualifiedQuestionId`
| `user.survey_assigned`

| `IdentificationCompleted`
| `userId`
| `user.identification_completed`

| `VideoAssigned`
| `userId`, `videoId`, `advertiserId: Option`, `videoType`
| `user.video_assigned`

| `VideoSurveyAssigned`
| `userId`, `advertiserId: Option`, `nextQuestion`
| `user.video_survey_assigned`

| `UserFinishedProcess`
| `userId`, `videoId: Option`, `answeredQuestionIds: List[FullyQualifiedQuestionId]` — the user went through the flow; what grants the access is `AccessGranted`, emitted with it
| `user.finished_process`
|===

`advertiserId` is `null` on `VideoAssigned` and `VideoSurveyAssigned` when the content was a promo — the venue's own video, which belongs to no advertiser. Analytics reading the log should treat the two consistently.

=== Survey and question events

`survey.Event` has a single case, `QuestionAnswered(surveyId, event: question.Event)`, so every survey event wraps one of the four question events. Each carries `userId`, `surveyId`, `questionId`, `answer: QuestionAnswer` and `occurredAt`.

[cols="2,3,2"]
|===
| Question event | Extra payload | `event_log.event_type`

| `EmailQuestionAnswered` | — | `survey.email_answered`
| `ProfilingQuestionAnswered` | — | `survey.profiling_answered`
| `LocationQuestionAnswered` | `hierarchyLevel: HierarchyLevel` | `survey.location_answered`
| `AdvertiserQuestionAnswered` | `advertiserId: Option[AdvertiserId]` | `survey.advertiser_answered`
|===

The logged `answer` is the `AnswerValue` encoded with the same circe codec the browser used to send it.

=== Device events

[cols="2,3,2"]
|===
| Event | Payload | `event_log.event_type`

| `DeviceLinked`
| `userId`, `deviceId`, `occurredAt` — a user identified on the session's device: by an email answered, or by a user the session already knew asking for the next identification question. Emitted every time, not only the first; being seen together again moves `last_seen_at`
| `device.linked`

| `TermsAccepted`
| `deviceId`, `termsId`, `occurredAt` — the device accepted the terms of service in force, version `termsId`, which `AcceptTermsHandler` read when the acceptance arrived
| `device.terms_accepted`
|===

The device itself is not an event: `SessionService.create` resolves it from the fingerprint before the session exists, and the commands that link it carry its id, taken from the session by the route.

=== Recovery events

[cols="2,3,2"]
|===
| Event | Payload | `event_log.event_type`

| `ErrorRecorded`
| `errorId`, `sessionId`, `deviceId`, the client's `report`, its `fingerprint` (`None` when the report has no frame of the bundle's own) and the `verdict` on it, `occurredAt` — an error the page says it caught
| `recovery.error_recorded`

| `RecoveryOffered`
| `errorId`, `sessionId`, `availableAt`, `occurredAt` — the session may leave through the error from `availableAt`
| `recovery.offered`

| `RecoveryShortened`
| `errorId`, `sessionId`, `availableAt`, `occurredAt` — another device reported the same error since it was offered: the wait shortens to `availableAt`, and the error is recurrent from now on. Emitted when the waiting page asks, or when the redeem finds it
| `recovery.shortened`

| `RecoveryRedeemed`
| `errorId`, `sessionId`, `occurredAt` — it left through it: the session moves to `Recovered`, where `finish` grants access
| `recovery.redeemed`
|===

A server error is not an event: the API records it where it catches the defect, with no command running (see xref:api.adoc#_error_model[Error model]).

=== Access events

[cols="2,3,2"]
|===
| Event | Payload | `event_log.event_type`

| `AccessGranted`
| `sessionId`, `userId: Option`, `occurredAt` — `finish` grants the session access, from `Ready` or from `Recovered`; emitted again on each retry until the controller confirms. With no user when the guest left through an error before giving an email
| `access.granted`

| `AccessExpired`
| `sessionId`, `userId: Option`, `occurredAt` — the session's access reached its `accessExpiresAt`. Emitted by the expiration scheduler, not by a request. The session's, not a user's: a session that left through an error before giving an email is authorized with no user
| `access.expired`
|===

=== Video events

[cols="2,3,2"]
|===
| Event | Payload | `event_log.event_type`

| `VideoVisualized`
| `sessionId`, `userId: Option`, `videoId`, `advertiserId: Option`, `videoType`, `durationWatched: Int`, `completed: Boolean`, `occurredAt`
| `video.visualized`

| `PlaybackStarted`
| `playbackId`, `sessionId`, `videoId`, `fileUrl`, `occurredAt`
| not logged

| `PlaybackEnded`
| `playbackId`, `sessionId`, `occurredAt`
| not logged
|===

These carry a session id in their own payload because the commands that emit them are built from the session rather than from an aggregate. The two playback events are recorded in `video_playbacks` by `PlaybackHandler` after the commit, not in `event_log`: a start the handler refuses — the file was replaced in between — would otherwise be logged as having happened.

== The handler chains

Two traits, two lifetimes:

[source,scala]
----
// core — the generic one, contravariant, with `andThen` sequencing via `*>`
trait EventHandler[F[_], -E]:
  def handle(events: List[E]): F[Unit]

// platform — a handler that must run inside an open transaction
trait DbEventHandler[-E]:
  def handle(events: List[E], quill: QuillSqlite): Task[Unit]
----

`DbEventHandler` has a `Monoid` instance (`combine` is `a.handle(…) *> b.handle(…)`) and the same `andThen` extension, so the chain is ordered and sequential. `TransactionalEventHandler` adapts the composed `DbEventHandler` to an `EventHandler[Task, Event]` by wrapping it in `quill.transaction`, logging and re-raising on failure — so one handler failing rolls back everything the earlier ones wrote.

Composition, from `api/src/whitelabel/captal/api/Flows.scala`:

[source,scala]
----
val dbHandler = EventLogHandler(ctx)
  .andThen(AnswerPersistenceHandler(ctx))
  .andThen(UserPersistenceHandler(ctx))
  .andThen(SessionPhaseHandler(ctx, nextAfterIdentification.phase, nextAfterVideo.phase))
  .andThen(SessionSurveyHandler(ctx))
  .andThen(SessionVideoHandler(ctx))
  .andThen(SessionExpirationHandler(ctx))
  .andThen(SurveyProgressHandler())
  .andThen(RecoveryHandler())
val transactional = TransactionalEventHandler(dbHandler, quill)
val unifiAccess = UnifiAccessHandler(
  currentLocation.unifi,
  unifiEnabled(quill, currentLocation),
  ctx,
  sessionService,
  unifiClient,
  jobQueue)
transactional.andThen(PlaybackHandler(quill)).andThen(unifiAccess)
----

Every `Flow` in the application shares this one `EventHandler[Task, Event]` instance.

=== Transactional chain

All nine run inside one transaction, in this order. All live in `platform/src/whitelabel/captal/platform/eventhandlers/`.

[cols="2,2,3"]
|===
| Handler | Reacts to | Writes

| `EventLogHandler`
| every event
| one `event_log` row per event, inserted one at a time, with the session id and the session's current `userId`

| `AnswerPersistenceHandler`
| all four `QuestionAnswered` variants
| one `answers` row per answer, in a single batch insert; `answer_value` is the circe encoding of the `AnswerValue`

| `UserPersistenceHandler`
| `UserCreated`, `UserRecognized`, `DeviceLinked`, `TermsAccepted`
| writes `devices.terms_id` and `terms_accepted_at` on `TermsAccepted`; inserts the user on `UserCreated` only — whether an email is already someone's is decided in `core`, by `AnswerEmailHandler` — then sets `sessions.user_id` and updates the ambient `SessionContext` so later handlers and the route see the id; upserts the `device_users` pair on `DeviceLinked`

| `SessionPhaseHandler`
| `RecoveryRedeemed`, `IdentificationCompleted`, any identification answer, `UserRecognized`, `VideoSurveyAssigned`, `VideoVisualized`
| `sessions.phase`. First match wins: `RecoveryRedeemed` sets `Recovered`, wherever the session was; the next two cases set the phase after identification (`AdvertiserVideo`), and so does `UserRecognized` — the email question met by a user who answered it before, which records no answer but moves on all the same. `VideoSurveyAssigned` sets `AdvertiserVideoSurvey`, `VideoVisualized` sets the configured phase after a video (also `AdvertiserVideoSurvey`). It has no case for `AccessExpired`.

| `SessionSurveyHandler`
| `SurveyAssigned`, `NewUserArrived` with a next question, `VideoSurveyAssigned`
| `sessions.current_survey_id` and `sessions.current_question_id`

| `SessionVideoHandler`
| `VideoAssigned`, `VideoVisualized`
| on assignment, `sessions.current_video_id` plus `current_advertiser_id` when there is one; on visualisation, a `video_views` row, which is also what the promo rotation counts. It never clears `current_video_id` — the advertiser-survey phase still needs it.

| `SessionExpirationHandler`
| `AccessExpired`
| one UPDATE — the same `SessionService.resetForExpirationQuery` the `/api/status` safety net runs — setting `phase = Welcome` and clearing `currentSurveyId`, `currentQuestionId`, `currentVideoId`, `currentAdvertiserId` and `accessExpiresAt`. The session keeps its `userId`, and the `users` row and the cross-location `captal_user` cookie survive.

| `SurveyProgressHandler`
| any `QuestionAnswered`
| upserts `user_survey_progress` for the `(userId, surveyId)` pair, then marks it complete when `SurveyService.isSurveyCompleteQuery` says every question is answered

| `RecoveryHandler`
| `ErrorRecorded`, `RecoveryOffered`, `RecoveryShortened`, `RecoveryRedeemed`
| inserts the client error into `errors` with its fingerprint and verdict; sets `available_at` on an offer, `available_at` and the verdict `recurrent` on a shortening, and `redeemed_at` on a redemption
|===

=== Post-commit chain

Two handlers, outside the transaction. `PlaybackHandler` records playbacks in `video_playbacks` and needs to see its own inserts, which a transaction defers (see xref:platform.adoc[Platform]). `UnifiAccessHandler` calls the controller, and an HTTP failure there must not roll back database writes.

[cols="2,3"]
|===
| Event | `UnifiAccessHandler` behaviour

| `AccessGranted`
| `AUTHORIZE_GUEST_ACCESS` for the session's `clientMac`. On success: `sessionService.setAuthorized(sessionId, occurredAt + defaultDurationMinutes)`, then `jobQueue.schedule(ScheduledAt(expiresAt, ExpireAccess(sessionId)))`. On failure: log the error and stop — the session stays at `Ready` or `Recovered`.

| `AccessExpired`
| `UNAUTHORIZE_GUEST_ACCESS`, which also disconnects the client. No session write: `SessionExpirationHandler` already reset the row inside the transaction. An empty `clientMac` is logged and skipped, as is a failure.
|===

With no UniFi configuration for the current location — dev, tests, a venue with no controller — both branches log a warning and do nothing. See xref:unifi.adoc[UniFi integration].

== event_log

Created by `platform/resources/db/migration/V8__add_event_log.sql`; every column is `TEXT`.

[cols="2,3"]
|===
| Column | Contents

| `id` | random UUID per row
| `event_type` | the dotted type from the catalogue above
| `event_data` | the event as compact JSON, built by hand per event in `EventLogHandler`
| `session_id` | the session the command ran in
| `user_id` | the session's user id at the time of the write; `NULL` before one exists
| `occurred_at` | the event's own `occurredAt`
| `created_at` | when the row was written
|===

`EventLogHandler.extractEventInfo` is total over `application.Event`, so every event emitted by every command is logged. The JSON is written field by field rather than derived, so a payload change is a change to this handler too.

== The guest journey

One pass through the portal, with the endpoint, the phase it requires, the events it emits and what they cause.

[cols="1,2,2,3"]
|===
| Step | Request | Phase required | Events and effects

| 1. Connect
| `GET /api/status` with the captive-portal headers (`X-Client-Mac`, `X-Ap-Mac`, `X-Redirect-Url`, `X-Ssid`, `X-Fingerprint`)
| any
| No events. The session row is created at `Welcome` (both `clientMac` and `fingerprint` are required, else `SessionMissing`), the session cookie is set, and the `captal_user` cookie is used to pre-attach a returning user.

| 2. Ask for a question
| `GET /api/survey/next`
| `Welcome`, `IdentificationQuestion`
| The route moves `Welcome` → `IdentificationQuestion` itself. `NewUserArrived` for a first-time visitor, or `SurveyAssigned` for a known one; `IdentificationCompleted` when the pool is exhausted. `SessionSurveyHandler` records the question.

| 3. Answer it
| `POST /api/survey/email` \| `/profiling` \| `/location`
| `IdentificationQuestion`
| `UserCreated` (email only) and `QuestionAnswered`. `answers`, `user_survey_progress` and `sessions.user_id` are written, `sessions.phase` becomes `AdvertiserVideo`, and the response is `Step(advertiser_video)`.

| 4. Ask for a video
| `GET /api/video/next`
| `AdvertiserVideo`
| `VideoAssigned`, and `sessions.current_video_id`. With no video available the response is a `Step` to `Ready` and the route writes that phase. With no identified user the command fails with `UserNotIdentified`.

| 4a. Start playing it
| `POST /api/video/playback/start`
| `AdvertiserVideo`
| `PlaybackStarted` → a `video_playbacks` row, if the URL is still the video's current file; otherwise `StaleVideoFile`, and the page asks for the video again. Sent before the player fetches anything.

| 5. Report it watched
| `POST /api/video/watched`
| `AdvertiserVideo`
| `VideoVisualized` → a `video_views` row and `sessions.phase` = `AdvertiserVideoSurvey`; `PlaybackEnded` for each of the session's open playbacks.

| —. Leave the page
| `POST /api/video/playback/end`
| any
| `PlaybackEnded` → the playback's `ended_at`, if it is this session's and still open. Sent by `sendBeacon` from `pagehide`.

| 6. Ask for the video's question
| `GET /api/survey/advertiser/next`
| `AdvertiserVideoSurvey`
| The video is taken from `sessions.current_video_id`, never from the request. `VideoSurveyAssigned` when there is a question; otherwise a `Step` to `Ready`, written by the route.

| 7. Answer it
| `POST /api/survey/advertiser`
| `AdvertiserVideoSurvey`
| `QuestionAnswered(AdvertiserQuestionAnswered)`. The route then sets `Ready` and answers a literal `Step(ready)` — one question per video.

| 8. Claim access
| `POST /api/finish`
| `Ready`
| `UserFinishedProcess` and `AccessGranted`. Post-commit, `UnifiAccessHandler` authorises on the controller; on success the session becomes `Authorized` with `accessExpiresAt` and an expiry job is scheduled. The response re-reads the session, so `phase` is `Authorized` only if the grant succeeded.

| 9. Browse
| `GET /api/status` (polled)
| any
| No events. While `Authorized`, the response carries `secondsRemaining`.

| 10. Expiry
| none — the scheduler
| `Authorized`
| `AccessExpired`. `SessionExpirationHandler` resets the session to `Welcome` in the transaction; post-commit the controller revokes and disconnects the client.
|===

Identification asks **one question per visit**: answering any identification question sets the phase to `AdvertiserVideo` straight away. The pool is ordered by `SurveyRepositoryQuill.nextIdentificationSurveyQuery` — the email survey while the user has no email, then profiling until every active profiling question is answered, then location — and already-answered questions are excluded per user. A returning guest therefore answers the next unanswered question, which is what makes the reconnection the moment more profiling data is collected.

NOTE: a deployment with no active email survey cannot identify an unidentified visitor. The repository logs a warning, `ProvideNextIdentificationSurveyHandler` takes its `unidentifiable` fallback, and the flow ends at `Ready` without granting access.

=== Leaving through an error

An error at any step before `Ready` is a way out, not a dead end: `POST /api/recovery` offers one and `POST /api/recovery/redeem` takes it. `RecoveryRedeemed` only moves the session to `Recovered`, in place of steps 1 to 7; from there step 8 is the same `POST /api/finish`, which grants access from `Recovered` with no user required — the error may have come before the guest gave an email. A server error opens at once; a client error waits the time `WaitPolicy` sets (see xref:core.adoc#_recovery[Core]). In `Ready`, `Recovered` or `Authorized` the error is in granting access itself, so the answer is `Unrecoverable` with the error's id, for staff to look up.

== Ready and Authorized

The two terminal phases are deliberately distinct, and the gap between them is where retries live.

[cols="1,3"]
|===
| Phase | Meaning

| `Ready`
| the guest has completed everything the portal asks for. No network access has been granted, and `accessExpiresAt` is unset.

| `Recovered`
| the guest left through an error. As `Ready`, with no user required.

| `Authorized`
| the UniFi controller confirmed the grant. `accessExpiresAt` is set, an expiry job exists, and `/api/status` reports `secondsRemaining`.
|===

`FinishHandler` emits `AccessGranted` — from `Ready`, with `UserFinishedProcess` before it — but it does not write the phase: only `UnifiAccessHandler`, after the transaction, moves `sessions.phase` to `Authorized` — and only on a confirmed grant.

That gives retry for free:

* UniFi fails, or is not configured → the session stays at `Ready` or `Recovered`;
* another `POST /api/finish` grants access again — from `Ready` it finds the user again through the same `findReadyUser()` — and the post-commit handler tries again;
* once the grant succeeds the phase is `Authorized`, and a further call is refused with `WrongPhase`, which the client reads as "you already have access".

=== Expiry

`ExpireAccessCommand` is the counterpart of `FinishCommand` and is executed by the scheduler in `platform/src/whitelabel/captal/platform/session/JobScheduler.scala`, never by a request.

[cols="2,3"]
|===
| Piece | Behaviour

| `JobQueue`
| producer side, an unbounded `Queue[ScheduledAt]`. Separate from the runner to keep the layer graph acyclic: `UnifiAccessHandler` is inside the event-handler layer and has to schedule, while the runner needs a `Flow` that depends on that layer.

| `JobRunner.start`
| called explicitly from `Main.run` and scoped to the application. Forks one scheduler fiber and one worker fiber, then rehydrates: `SessionService.findPendingExpirations()` re-enqueues one job per `Authorized` session with an `accessExpiresAt`, so a redeploy does not lose deadlines. Deadlines already past fire immediately.

| scheduler fiber
| keeps pending jobs in a `SortedMap[Instant, List[ScheduledJob]]` and waits with `inbox.take.timeout(wait)`, so an earlier deadline arriving simply recomputes the wait — no fiber is interrupted or recreated.

| worker fiber
| takes due jobs one at a time (concurrency of 1 against the controller), re-reads the session, populates `SessionContext` with it via `ctx.locally`, and runs the flow exactly as a request would. Errors are logged and swallowed, so neither an unreachable controller nor a database failure can kill the fiber.

| staleness
| handled in the domain, not the scheduler: `ExpireAccessHandler` is a silent no-op unless the session is `Authorized` and past its own `accessExpiresAt`. A session reset in between, or a guest who redid the flow and got re-authorized until later, leaves the old job harmless, which is why jobs are never cancelled or indexed.
|===

A second, independent safety net lives in `GET /api/status`: when the session is `Authorized` and `accessExpiresAt` is already past, the route resets the session itself and answers `Welcome`. It runs the same `resetForExpirationQuery` the event handler does, but emits no event — so a reset that happens this way reaches neither `event_log` nor the controller.

`AccessExpired` is a genuine domain event rather than bookkeeping: it is what sends the guest back through the flow, which is the business model. The reset keeps the `users` row and the `captal_user` cookie, so the next visit skips the questions already answered and asks the next one.
