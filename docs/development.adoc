= Local development
:toc:

== Prerequisites

Nix, https://devenv.sh[devenv] and direnv on the host — none of the three is managed by this
repository, and everything else is. Docker is also required directly: `rqlite` and, for the MCP
backoffice's deploy-related work, LocalStack both run as containers the build starts for you, not
as something devenv provisions.

`devenv.nix` provides the rest of the toolchain the moment the shell is entered:

[source,nix]
----
packages = [ pkgs.git pkgs.terraform pkgs.opentofu pkgs.scalafmt pkgs.scalafix pkgs.cloudflared ];
languages.scala.enable = true;
languages.scala.mill.enable = true;
----

Both `terraform` and `opentofu` are present — not a redundancy. `terraform/` is an OpenTofu
configuration, but the two tools cannot share a working directory: a state file one writes the other
refuses to open, and `.terraform.lock.hcl` records provider hashes from whichever registry wrote it.
See xref:infrastructure.adoc[Infrastructure]. `cloudflared` is what `mcp.dev` runs to open the
Cloudflare tunnel. `languages.scala.mill.enable` puts `mill` on the `PATH`; there is no launcher
script in the repository, so every command in these docs is `mill …`.

`.envrc` is not committed, and loads two things beyond the standard devenv hookup:

[source,bash]
----
export NIXPKGS_ALLOW_UNFREE=1
export LOCALSTACK_TOKEN="…"
eval "$(devenv direnvrc)"
use devenv
----

`LOCALSTACK_TOKEN` (equivalently `LOCALSTACK_AUTH_TOKEN`) is a LocalStack Pro licence. Without one,
the free tier covers only S3 — enough for most of `mcp.test` — and everything that needs ECS, ELBv2,
CloudFront, EC2, IAM, STS, EFS, Secrets Manager, Cloud Map or ECR skips itself rather than failing;
see xref:testing.adoc[Test strategy]. Treat the value itself as a credential: it is read by the build
(`Task.env`, not `System.getenv` — see <<Sharp edges>>) and must never be pasted into a log, a commit
message, or a document.

== Mill

Pinned at `1.1.2` (`.mill-version`). `.mill-jvm-opts` raises the compiler's stack to `-Xss8m`,
because one test in `mcp.test` — `DeployE2ESpec`'s `lifecycle` method, six `assertTrue` chains of
roughly forty conditions each — overflows the 1-minute default's implied stack depth with "Stack
overflow in the compiler" and nothing about the actual code; see xref:testing.adoc[Test strategy].

Every module mixes in the same two capabilities through `BaseModule` (JVM) and `BaseJSModule`
(Scala.js): `ScalafmtModule` and `ScalafixModule`. `.scalafmt.conf` pins `scalafmt` `3.10.4` against
the `scala3` dialect and aggressively removes redundant braces and parens in favour of Scala 3's
colon syntax; `.scalafix.conf` runs `OrganizeImports` and `RemoveUnused`. Three tasks matter across
every module at once, using Mill's `__` wildcard selector:

[cols="1,3"]
|===
|Command |Effect

|`mill __.compile`
|Compiles every module.

|`mill __.reformat`
|Applies `scalafmt` to every module (`__.checkFormat` checks without writing).

|`mill __.fix`
|Applies the scalafix rules to every module (`__.checkFix` checks without writing).
|===

`mcp` is the one module that diverges: it compiles against Scala `3.10.0` rather than the rest of
the tree's `3.8.0` (forced upward by `zio-http-mcp`'s published TASTy version — see
xref:mcp.adoc[MCP backoffice]) and declares its own `scalafixConfig`, because scalafix's
`RemoveUnused` refuses to run at all under 3.10. `__.fix` still reaches it correctly; it is simply
running a different, per-module configuration there.

== Running rqlite

`ensureRqlite(containerName, hostPort)` is the one function every `*.dev` and `*.test` task calls
to get a database. It checks Docker is reachable, looks for a container already running under the
given name, and compares its image against the one this build currently asks for
(`rqlite/rqlite:10.6.1`) — a name match alone is not reuse, because that is exactly how a stale
image survived three version drifts unnoticed in the past (see
xref:context/incidents.adoc[Incidents]). A container on the wrong image, or none at all, is removed
and recreated; a container already on the right image is left alone.

Three of those containers exist across the whole build, never shared between purposes:
`rqlite-test`, `rqlite-mcp-test` and `rqlite-mcp-e2e`, covered in xref:testing.adoc[Test strategy].
The database `api.dev` and `mcp.dev` run against is not one of them: it is the local
configuration's rqlite service, the same one production runs, in LocalStack — see
<<Running the stack locally>>.

== Running the stack locally

=== `mill api.dev`

[source]
----
[dev] Step 1/3: Waiting for the local configuration's rqlite...
[dev] Step 2/3: Running migrations...
[dev] Step 3/3: Starting server (location=cafe-centro)...
----

In order: waits for the local configuration's rqlite to have a leader, on the host port
`environments/local/terraform.tfvars` gives it (`rqlite_http_port`, 5001) — it exists only once
`mcp.dev` has applied that configuration, and the wait says so when it never answers;
`whitelabel.captal.platform.Migrate` against it; `copyIndex` renders `client/index.html` from the template (pointing at `fastLinkJS`'s output by
default, or at `client.bundle`'s Vite-processed output when `CLIENT_LINKER=full` — the shape
production actually serves); then the server is forked with `LOCATION_SLUG` set to the `--slug`
argument, defaulting to `cafe-centro`.

IMPORTANT: **A location row must already exist before this will boot.** `ServerSettings`/`AppLayers`
resolve `LOCATION_SLUG` against the `locations` table during layer construction and fail the whole
process with `LocationNotFound` if it is absent — see xref:api.adoc[Guest API]. Nothing in this task
writes that row. Create the location first (through the MCP backoffice's `create_location` tool —
run `mcp.dev` and drive it from a client) before running `api.dev` against a fresh database.

While `mcp.dev` runs it holds Mill's lock on `out/`, so `api.dev` beside it needs an output
directory of its own: `MILL_OUTPUT_DIR=/tmp/captal-api-out mill api.dev --slug <slug>`.

=== `mill mcp.dev`

[source]
----
[dev] Step 1/6: Ensuring LocalStack...
[dev] Step 2/6: Applying the local infrastructure...
[dev] Step 3/6: Waiting for rqlite, then running migrations...
[dev] Step 4/6: Publishing the portal, the MCP App scripts and the images...
[dev] Step 5/6: Opening the Cloudflare tunnels...
[dev] Step 6/6: Starting MCP backoffice on :8081
----

Everything the backoffice runs against is the local configuration's, applied to LocalStack: the
same OpenTofu configuration production uses, so nothing here is a resource the build made on the
side. That needs a LocalStack licence, and `mcp.dev` stops at step 2 without one.

Steps 2 and 4 are the release `ci.run` makes (see <<release>>), run with the
variables of this machine's LocalStack instead of CodeBuild's: `CAPTAL_ENV=local` and
`AWS_ENDPOINT_URL` at the container, which turns every AWS call into `awslocal` inside it.

Step 1 starts (or reuses) the `localstack-dev` container. Step 2 applies `environments/local`,
sharing `mcp.test.localStackInfra`'s state so the two cannot come apart: `init`, the image
registries alone, the rqlite image pushed into its own, then a plan of everything and that plan
applied — the rqlite service, the assets bucket with its CORS rule, the distribution, and the
cluster, subnets, listener and roles a deploy attaches to. On a fresh container this is minutes,
not seconds. The MCP service is declared too, with no tasks (`mcp_desired_count = 0`): the
backoffice is the one running here.

Step 3 waits for that rqlite service to have a leader, on the host port the local tfvars give it
(`rqlite_http_port`, 5001), then runs `whitelabel.captal.platform.Migrate` against it. The
backoffice's own `Main` runs `McpMigrate` itself as part of its boot. `api.dev` uses the same
database — deliberately, since the backoffice writes the content a location's API later reads.

Step 4 releases the build being run, on every run:

* the API and backoffice images, built by `api.image` and `mcp.image` and pushed into the
  configuration's repositories under the tags the local tfvars name (`image_tag`, `mcp_image_tag`)
  — the same tags its task definitions pull, as in production. The API's is what the server is
  given as `API_IMAGE`, so a location deployed from here runs the real API;
* every deployed location moved onto that API image. The tag is reused locally, so when the push
  changed what it points at, the location's service is told to start fresh tasks rather than given
  a new task definition;
* the client: the portal's bundle under `bundle/` and the MCP App pages' scripts under `ui/`, the
  bundle copied under every deployed location's prefix, and one invalidation.

None of it is waited for: a location taking minutes to settle should not hold up the server.

The server is then given the configuration's bucket, distribution and credentials, with
`PUBLIC_BASE_URL` set to the distribution as LocalStack serves it,
`https://<id>.cloudfront.localhost.localstack.cloud:4567`. A location deployed from here answers
there: `/<slug>/` for the portal, `/<slug>/api/*` through the load balancer to its task. Two
variables differ from production:

* `TASK_DB_URL`, the configuration's `rqlite_url` (`rqlite.captal.local`, by service discovery),
  which is how a deployed task reaches the database; the backoffice itself reaches it on
  `localhost`.
* `SCRIPT_BASE_URL`, the bucket itself rather than the distribution. LocalStack's gateway refuses a
  request to a distribution carrying an `Origin` it does not know, which a page in a host's frame
  always sends; the bucket answers with its own CORS rule instead.

LocalStack runs on port **4567**, not its default 4566, so it coexists with other projects' LocalStack
containers. It is the same port inside the container and out: `GATEWAY_LISTEN` moves the listener and
`LOCALSTACK_HOST` names it, because LocalStack writes that host into every URL it returns — an ECR
repository URI, the endpoint its own ECS tasks are given — and `awslocal` dials it from inside the
container. A URL saying 4566 would reach whichever LocalStack holds that port; one saying 4567 while
LocalStack listened on 4566 inside would reach nothing. A container started on any other port is
replaced, not reused.

Step 5 runs only with `mill mcp.dev --tunnel`. It opens two Cloudflare quick tunnels, `cloudflared
tunnel --url http://localhost:<port>`, one to the server and one to LocalStack. They need no account,
token or domain, and close when the server exits. Each address is a random
`https://<name>.trycloudflare.com` that changes every run and is known only once `cloudflared` prints
it, so the step waits for both before the server starts. Only `cloudflared`'s error lines reach the
terminal.

The server's tunnel becomes `MCP_RESOURCE_URI`: the UniFi and upload pages post to it and declare it
in their CSP. LocalStack's is there because those pages render in the operator's browser, on the
host's public origin, and a page there may not reach localhost. They load their scripts from the
bucket and PUT uploads straight to it, so the server is given LocalStack's tunnel for both:
`SCRIPT_BASE_URL` (`<tunnel>/<bucket>`) for the scripts and their place in the CSP, and
`PRESIGN_ENDPOINT_URL` for the upload URLs. `PUBLIC_BASE_URL` stays the distribution, because it is
stored in each video row and has to outlive the tunnel.

Cloudflare documents quick tunnels as not carrying Server-Sent Events. Through this one they do: a
stream sending a comment every 30 seconds stayed open well past Cloudflare's 100-second limit, which
only counts silence. Nothing guarantees it, though, and quick tunnels also cap a tunnel at 200
in-flight requests and carry no uptime guarantee.

The backoffice starts on port 8081 with a **fixed** admin token, `dev-token` — not generated, because
it is meant to be copied once into an MCP host's configuration by hand, and a token that changed
every run would be miscopied more often than it would ever be stolen. With `--tunnel` that no longer
holds. The server is public and `dev-token` is written here, so the token is random instead. Seeding
replaces the admin row in place, so `dev-token` stops working until the next run without the flag.
`--token <value>` overrides either. The task prints a ready-to-paste block, addressed to the tunnel
when there is one:

[source,json]
----
"captal": {
  "command": "npx",
  "args": ["mcp-remote", "http://localhost:8081/mcp",
           "--header", "Authorization: Bearer dev-token"]
}
----

and, if a quick probe of the `locations` table over raw HTTP finds it empty, a reminder that a
location has to be created through `create_location` before either side of the loop has anything to
serve. `mill mcp.stopLocalStack` stops the LocalStack container; `mill mcp.localStackSetup` ensures
it is up without starting the server, for working against it with another client.

The database lives in LocalStack's ECS tasks, so it goes wherever they go: recreating the container
empties it along with the bucket, and the next apply makes both again, empty.

`mill mcp.destroyLocal` is the whole teardown: every container this build starts, LocalStack's
anonymous volume, the ECS task containers LocalStack spawned for a service, and the images built
here. Reach for it over `stopLocalStack` when something is wedged — a stopped LocalStack leaves its
volume and its task containers behind, and a task still holding a published port is what makes the
next run fail on a port that looks free. It removes the local tofu state too, since with LocalStack
gone none of it describes anything, and the next run builds the container and its state together.

=== A full local loop, in order

. `mill mcp.dev` — LocalStack, the local configuration, and the backoffice.
. Point an MCP client at it (the printed config block) and create a location, its identification
surveys, a video, an advertiser and its question, and a locale bundle — see
xref:mcp.adoc[MCP backoffice] for the tool catalogue.
. Either `deploy_location`, and open `https://<id>.cloudfront.localhost.localstack.cloud:4567/<slug>/`
— the portal as production serves it — or `mill api.dev --slug <slug>` for the faster loop on
`localhost:8080`, against the same database.

== Images

`api.image`, `mcp.image` and `rqlite.image` build the deployed images — the first two from an
already-assembled jar, so nothing re-resolves the dependency tree per build. `api.image
--devEndpoints true` builds the same image with `SERVER_DEV_ENDPOINTS=true`, for exercising
`/api/dev/reset-phase` without a full deploy. `api.imagePush`, `mcp.imagePush` and `rqlite.imagePush`
tag and push one to a registry — against LocalStack, the registry `tofu apply` created for the
`local` environment, which is also where `rqlite.imagePush` runs on its own as part of that apply.
See xref:infrastructure.adoc[Infrastructure] for why these images are single-stage and why no tag
defaults to `latest`.

[[release]]
== Releasing: `mill ci.run`

What CodeBuild runs to release a build to an AWS environment, in four operations, shared with
`mcp.dev`, which runs them against LocalStack:

. **Images.** `rqlite.image`, `api.image` and `mcp.image`, built before anything else.
. **The configuration.** `tofu init` against the environment's backend
  (`environments/<env>/backend.tfvars`), the image registries applied alone, the three images
  pushed into them — Docker logged in to ECR first — then a plan of everything saved and that plan
  applied. The registries and the images go first because the task definitions name images, and an
  image has to be in its registry before a service pulls it. The API and backoffice images go up
  under `IMAGE_TAG`, passed to the plan as `image_tag` and `mcp_image_tag`; rqlite's under the
  tfvars' `rqlite_image_tag`, since the engine changes deliberately rather than per commit. The
  apply is what moves the backoffice onto its new image, and its `API_IMAGE` onto the new API, so a
  location deployed afterwards gets it too.
. **Locations.** Every location's service — the ones whose task runs a single container named
  `api`, which is how `deploy_location` registers them — gets a new revision of its task
  definition differing only in the image, and is pointed at it. Environment, roles and sizes carry
  over as the last deploy registered them, so a change to those is still a `deploy_location`. The
  service keeps its task count: a paused location stays paused and runs the new image when it is
  resumed. `ci.run` waits for every moved service to settle and fails naming the ones that did not.
. **The client.** The portal's bundle under `bundle/` and the MCP App pages' scripts under `ui/`,
  the bundle copied server-side under every deployed location's prefix — keeping a location's own
  brand icon, leaving `maintenance.html` shared, and for a paused location replacing the page its
  resume puts back rather than the maintenance page — then one invalidation of everything.

It is configured only through the environment, which the CodeBuild project injects:

[cols="1,3"]
|===
|Variable |Meaning

|`CAPTAL_ENV`
|Required. The `terraform/environments/<name>` to release to, for its tfvars and its backend.

|`IMAGE_TAG`
|The tag the API and backoffice images go up under. Defaults to the first twelve characters of
`CODEBUILD_RESOLVED_SOURCE_VERSION`, the commit CodeBuild built; against AWS, `ci.run` refuses to
run with neither. Against LocalStack, unset means the local tfvars' tags.

|`AWS_REGION`
|Defaults to `us-east-1`. The credentials are the build's role.

|`AWS_ENDPOINT_URL`
|Unset in CodeBuild. Set to this build's LocalStack, it releases there instead; see below.
|===

The build needs Docker, so the CodeBuild project has to be privileged, and `tofu` and the `aws`
CLI on its PATH. Its role applies the whole configuration, so it needs what that creates.

On a dev machine, the same release runs against LocalStack:

[source,bash]
----
CAPTAL_ENV=local AWS_ENDPOINT_URL=http://localhost:4567 mill ci.run
----

It needs no credentials: LocalStack's are fixed, the provider uses them when it is given an endpoint,
and every AWS call goes through `awslocal` inside the container. It needs the LocalStack licence
`mcp.dev` needs, starts the container as `mcp.dev` does if it is not running, and applies with the
same state, `out/localstack/<container-id>/` — so a release from here and an `mcp.dev` run never
come apart. That directory is under the workspace's `out/` whatever `MILL_OUTPUT_DIR` says, which
is what lets `ci.run` run beside a running `mcp.dev` with an output directory of its own.

== Test tasks

`mill core.test`, `mill api.test` and `mill mcp.test` are the three module-level suites;
`platform` and `messages` have none of their own and are exercised through the other two. Each test
module that depends on a Docker container checks and restarts it on every invocation rather than
trusting a cached URL, for the same reason `ensureRqlite` compares images above — an operator
removing a container between runs must be caught, not silently misread as a schema problem. The full
breakdown of what each suite covers, what needs LocalStack, and the three separate `rqlite`
containers the test tasks use is xref:testing.adoc[Test strategy]'s subject; `mill
api.test.stopRqlite` and `mill mcp.test.resetLocalStack` are the matching cleanup commands for the
test-side containers.

== Sharp edges

* **direnv has to be told to trust `.envrc` at least once.** direnv refuses to auto-load an `.envrc`
it has not been explicitly allowed to run, as a security measure — a freshly cloned checkout, or any
edit to `.envrc` itself, needs `direnv allow` run by hand in that directory before `devenv shell`'s
packages and environment variables take effect. Without it, commands that assume the devenv shell
(`mill`, `tofu`, `scalafmt`) are simply not on `PATH`, with no message pointing at `.envrc`.
* **`mill clean` breaks the LocalStack state pairing `mcp.test` depends on.** The Tofu state
directory for the `local` environment is kept alive across ordinary Mill re-evaluations specifically
so it survives alongside the LocalStack container it describes; `mill clean` discards it anyway,
leaving the container holding every resource a freshly-emptied state no longer knows about. Run
`mill mcp.test.resetLocalStack` immediately after any `mill clean`. Full mechanics in
xref:infrastructure.adoc[Infrastructure] and xref:testing.adoc[Test strategy].
* **`api.dev` needs a location row before it will start.** Covered above — worth repeating here
because the failure mode (`LocationNotFound` during layer construction, nothing binds the port) gives
no hint that the fix is "create a location first," and the task's own log output does not mention it
unless `mcp.dev` happens to be run afterward against the same database.
* **Changing `ENVIRONMENT` needs a clean rebuild of one generated file.** `client.generatedSources`
writes `BuildInfo.scala` (which drives `isDevMode`, and therefore the dev reset button in
`ReadyView`) from the `ENVIRONMENT` variable, but the task is cached against its own normal inputs,
and the environment variable is not one of them. `mill clean client.generatedSources` before
changing `ENVIRONMENT`, or the previous `BuildInfo` stays in place with the flag silently wrong. See
xref:client.adoc[Client].
* **`LOCALSTACK_TOKEN` gates more than licensing errors — it gates whether certain specs run at all.**
Its absence is not a build failure: `mcp.test`'s deploy-related specs detect the missing licence (or
the missing `ECS_CLUSTER` configuration that follows from it) and skip themselves. A change that
should have been caught by `DeployE2ESpec` can pass a full green `mcp.test` run on a machine with no
licence configured; see xref:testing.adoc[Test strategy].
