= Local development
:toc:
:toclevels: 2

== Prerequisites

Nix, https://devenv.sh[devenv] and direnv on the host — none of the three is managed by this
repository, and everything else is. Docker is also required directly: `rqlite` and, for the MCP
backoffice's deploy-related work, LocalStack both run as containers. Those containers, the dev
servers and the tunnels run under devenv's process manager, which the build starts and drives — see
<<processes>>.

`devenv.nix` provides the rest of the toolchain the moment the shell is entered:

[source,nix]
----
packages = [ pkgs.git pkgs.terraform pkgs.opentofu pkgs.scalafmt pkgs.scalafix pkgs.cloudflared pkgs.git-cliff ];
languages.scala.enable = true;
languages.scala.mill.enable = true;
----

Both `terraform` and `opentofu` are present — not a redundancy. `terraform/` is an OpenTofu
configuration, but the two tools cannot share a working directory: a state file one writes the other
refuses to open, and `.terraform.lock.hcl` records provider hashes from whichever registry wrote it.
See xref:infrastructure.adoc[Infrastructure]. `cloudflared` is what `mcp.dev` runs to open the
Cloudflare tunnel, and `git-cliff` is what computes the API's and the backoffice's versions (see
<<versions>>). Mill's daemon runs tools with the `PATH` it started with, so after a package is added
here, reload the shell and `mill shutdown`. `languages.scala.mill.enable` puts `mill` on the `PATH`;
there is no launcher script in the repository, so every command in these docs is `mill …`.

`.envrc` is not committed, and loads two things beyond the standard devenv hookup:

[source,bash]
----
export NIXPKGS_ALLOW_UNFREE=1
export LOCALSTACK_TOKEN="…"
eval "$(devenv direnvrc)"
use devenv
----

`LOCALSTACK_TOKEN` (equivalently `LOCALSTACK_AUTH_TOKEN`) is a LocalStack Pro licence. Without one,
the free tier covers only S3 — enough for most of `mcp.test` — and everything that needs ECS, ELBv2,
CloudFront, EC2, IAM, STS, EFS, Secrets Manager, Cloud Map or ECR skips itself rather than failing;
see xref:testing.adoc[Test strategy]. Treat the value itself as a credential: it is read by the build
(`Task.env`, not `System.getenv` — see <<Sharp edges>>) and must never be pasted into a log, a commit
message, or a document.

== Mill

Pinned at `1.1.2` (`.mill-version`). `.mill-jvm-opts` raises the compiler's stack to `-Xss8m`,
because one test in `mcp.test` — `DeployE2ESpec`'s `lifecycle` method, six `assertTrue` chains of
roughly forty conditions each — overflows the 1-minute default's implied stack depth with "Stack
overflow in the compiler" and nothing about the actual code; see xref:testing.adoc[Test strategy].

Every module mixes in the same two capabilities through `BaseModule` (JVM) and `BaseJSModule`
(Scala.js): `ScalafmtModule` and `ScalafixModule`. `.scalafmt.conf` pins `scalafmt` `3.10.4` against
the `scala3` dialect and aggressively removes redundant braces and parens in favour of Scala 3's
colon syntax; `.scalafix.conf` runs `OrganizeImports` and `RemoveUnused`. Three tasks matter across
every module at once, using Mill's `__` wildcard selector:

[cols="1,3"]
|===
|Command |Effect

|`mill __.compile`
|Compiles every module.

|`mill __.reformat`
|Applies `scalafmt` to every module (`__.checkFormat` checks without writing).

|`mill __.fix`
|Applies the scalafix rules to every module (`__.checkFix` checks without writing).
|===

`mcp` is the one module that diverges: it compiles against Scala `3.10.0` rather than the rest of
the tree's `3.8.0` (forced upward by `zio-http-mcp`'s published TASTy version — see
xref:mcp.adoc[MCP backoffice]) and declares its own `scalafixConfig`, because scalafix's
`RemoveUnused` refuses to run at all under 3.10. `__.fix` still reaches it correctly; it is simply
running a different, per-module configuration there.

== Running rqlite

`ensureRqlite(name, hostPort, env)` (`mill-build/src/millbuild/Rqlite.scala`) is how a test suite
gets its database: a container named `name` on `hostPort`, run as the devenv process of the same
name. A process already running the same command — the same image, `rqlite/rqlite:10.6.1`, and the
same port — is reused; anything else, or nothing at all, is (re)started, after removing any
container left under that name. Its data goes with the container.

Three of those exist across the whole build, never shared between purposes: `rqlite-test`,
`rqlite-mcp-test` and `rqlite-mcp-e2e`, covered in xref:testing.adoc[Test strategy].
The database `api.dev` and `mcp.dev` run against is not one of them: it is the local
configuration's rqlite service, the same one production runs, in LocalStack — see
<<Running the stack locally>>.

== Running the stack locally

=== `mill api.dev`

[source]
----
[dev] Step 1/2: Waiting for the local configuration's rqlite...
[dev] Step 2/2: Starting server (location=cafe-centro)...
[dev] The API serves 'cafe-centro' on :8080. Its log: `devenv processes logs api`. Stop it with `mill api.stop`.
----

In order: waits for the local configuration's rqlite to have a leader, on the host port
`environments/local/terraform.tfvars` gives it (`rqlite_http_port`, 5001) — it exists only once
`mcp.dev` has applied that configuration, and the wait says so when it never answers;
`copyIndex` renders `client/index.html` from the template (pointing at `fastLinkJS`'s output by
default, or at `client.bundle`'s Vite-processed output when `CLIENT_LINKER=full` — the shape
production actually serves); then the server is started as the devenv process `api`, with
`LOCATION_SLUG` set to the `--slug` argument, defaulting to `cafe-centro`. The server migrates the
database before anything else, as it does in its container. The task returns once the server
listens on 8080, or fails with the process's log if it exits first. A run restarts the server
on the current build; `mill api.stop` stops it.

IMPORTANT: **A location row must already exist before this will boot.** `ServerSettings`/`AppLayers`
resolve `LOCATION_SLUG` against the `locations` table during layer construction and fail the whole
process with `LocationNotFound` if it is absent — see xref:api.adoc[Guest API]. Nothing in this task
writes that row. Create the location first (through the MCP backoffice's `create_location` tool —
run `mcp.dev` and drive it from a client) before running `api.dev` against a fresh database.

It runs on the host, beside what `mcp.dev` released into LocalStack, and returns once it serves, so
it does not hold Mill while the server runs.

=== `mill mcp.dev`

[source]
----
[dev] Step 1/4: Ensuring LocalStack...
[dev] Step 2/4: Opening the Cloudflare tunnels...
[dev] Step 3/4: Releasing the images, the configuration and the client into LocalStack...
[dev] Step 4/4: Waiting for the backoffice behind the load balancer...
----

`mcp.dev` releases this build into LocalStack the way `ci.run` releases it to AWS (see <<release>>),
and returns once the backoffice serves. Nothing runs on the host: the backoffice and the change data
capture relay (see xref:cdc.adoc[Change data capture relay]) run as ECS tasks from their images,
beside rqlite and every deployed location, and find each other by service discovery as in
production. Everything is the local configuration's, applied to LocalStack: the same OpenTofu
configuration production uses. That needs a LocalStack licence, and `mcp.dev` stops at step 1
without one.

Step 1 starts (or reuses) LocalStack: the devenv process `localstack`, which runs the
`localstack-dev` container in the foreground. Its OpenTofu state is the one `ci.run` and
`mcp.test.localStackInfra` use, keyed by the container, so the three cannot come apart.

Step 3 is `ci.run`'s release (`release` in `mill-build/src/millbuild/Release.scala`), with
`CAPTAL_ENV=local` and `AWS_ENDPOINT_URL` at the container, which turns every AWS call into `awslocal`
inside it:

* the rqlite, API, backoffice and relay images, built as `captal-<name>:latest`;
* a plan of everything and that plan applied — rqlite, the relay, the backoffice, the assets bucket
  with its CORS rule, the distribution, and the cluster, subnets, listener and roles a deploy
  attaches to. The apply pushes each image whose tag changed and points its service at the digest it
  left (see <<release>>). Locally a tag is the version and a hash of the image's jar and Dockerfile,
  `1.0.0-local.3f2a9c1e`, since the version moves only with a releasing commit and every change to
  the code has to reach LocalStack; a run that changed nothing pushes and restarts nothing. rqlite's is
  the tfvars' `rqlite_image_tag` alone, here too: a new rqlite image replaces every node, and with it
  the database. On a fresh container this is minutes, not seconds;
* every deployed location moved onto the API image's digest, and not waited for;
* the client: the portal's bundle under `bundle/` and the MCP App pages' scripts under `ui/`, the
  bundle copied under every deployed location's prefix, and one invalidation.

Step 4 waits for the backoffice's service to settle and for its own `ok` from `/health` through the
load balancer, `http://captal-local.elb.localhost.localstack.cloud:4567`; LocalStack answers
`200 {}` for a target group with nobody in it, so the status alone says nothing. The backoffice
migrates the database itself as it starts, the API's schema included, so a new container needs
nothing else. `api.dev` uses the same database — deliberately, since the backoffice writes the
content a location's API later reads.

The task definitions differ from production only in the addresses `environments/local` gives them:

* `public_port = 4567`: LocalStack serves the load balancer and the distribution on its gateway
  port, so the backoffice's `MCP_RESOURCE_URI` is
  `http://captal-local.elb.localhost.localstack.cloud:4567/mcp` and its `PUBLIC_BASE_URL`
  `https://<id>.cloudfront.localhost.localstack.cloud:4567`. A location deployed from here answers
  there: `/<slug>/` for the portal, `/<slug>/api/*` through the load balancer to its task.
* `assets_endpoint_url = "http://localhost:4567"`, the bucket from the operator's browser, which
  becomes `SCRIPT_BASE_URL` (`<it>/<bucket>`) and `PRESIGN_ENDPOINT_URL`. The bucket answers a
  page in a host's frame with its own CORS rule.
* No `AWS_ENDPOINT_URL`, in any environment: LocalStack gives every task it runs its own, the address
  of its container, along with credentials of its own account. The backoffice's IAM policy is
  therefore not exercised by the task here; `DeployE2ESpec` exercises it.

LocalStack runs on port **4567**, not its default 4566, so it coexists with other projects' LocalStack
containers. It is the same port inside the container and out: `GATEWAY_LISTEN` moves the listener and
`LOCALSTACK_HOST` names it, because LocalStack writes that host into every URL it returns — an ECR
repository URI, the endpoint its own ECS tasks are given — and `awslocal` dials it from inside the
container. A URL saying 4566 would reach whichever LocalStack holds that port; one saying 4567 while
LocalStack listened on 4566 inside would reach nothing. LocalStack started with any other command —
another port, image, service list or IAM mode — is replaced, not reused.

LocalStack runs with `DISABLE_CORS_CHECKS=1`. Its gateway otherwise answers `403` to a request
carrying an `Origin` it does not know, before the request reaches a load balancer's target, which
AWS never does; and a backoffice MCP App page, in a host's sandboxed frame, always sends one — the
opaque `null` in the end-to-end features, the host's own in Claude — when it posts the UniFi form or
follows a run. The cost is LocalStack's protection against a website in the developer's browser
sending it requests.

Step 2 runs only with `mill mcp.dev --tunnel`, before the apply, which is given its addresses. It
opens two Cloudflare quick tunnels to LocalStack's port, the devenv processes `tunnel-mcp` and
`tunnel-localstack` (`cloudflared tunnel --url http://localhost:4567`). They need no account, token
or domain. `tunnel-mcp` rewrites every request's `Host` to the load balancer's
(`--http-host-header captal-local.elb.localhost.localstack.cloud`), which is how LocalStack's gateway
tells a load balancer from its own API. Each address is a random `https://<name>.trycloudflare.com`,
read from `cloudflared`'s metrics endpoint (ports 20241 and 20242) once it has one. A tunnel already
running is reused, so the addresses stay the same from one run to the next until `mill mcp.stop`; a
run without `--tunnel` stops them.

The backoffice's tunnel is applied as `mcp_public_origin`, so it becomes `MCP_RESOURCE_URI`: the
UniFi and upload pages post to it and declare it in their CSP. LocalStack's is applied as
`assets_endpoint_url`, because those pages render in the operator's browser, on the host's public
origin, where a page may not reach localhost; it becomes `SCRIPT_BASE_URL` and `PRESIGN_ENDPOINT_URL`.
`PUBLIC_BASE_URL` stays the distribution, because it is stored in each video row and has to outlive
the tunnel. A run with `--tunnel` after one without, or the other way round, changes the backoffice's
task definition, and its service rolls onto it. So does `mcp.test`, whose apply has no tunnel.

Cloudflare documents quick tunnels as not carrying Server-Sent Events. Through this one they do: a
stream sending a comment every 30 seconds stayed open well past Cloudflare's 100-second limit, which
only counts silence. Nothing guarantees it, though, and quick tunnels also cap a tunnel at 200
in-flight requests and carry no uptime guarantee.

The admin token is the one the configuration generates into Secrets Manager, as in production; the
task reads it and prints it in a ready-to-paste block, addressed to the tunnel when there is one:

[source,json]
----
"captal": {
  "command": "npx",
  "args": ["mcp-remote", "http://captal-local.elb.localhost.localstack.cloud:4567/mcp",
           "--header", "Authorization: Bearer <token>"]
}
----

It stays the same for as long as the LocalStack container does, so a connector keeps working across
runs. With `--tunnel` the backoffice is public: anyone with the tunnel's address and the token gets
in. The task also prints how to follow the backoffice's and the relay's logs, which their tasks write
to CloudWatch in LocalStack (`awslocal logs tail /ecs/captal-local-mcp --follow`), and, if a quick
probe of the `locations` table over raw HTTP finds it empty, a reminder that a location has to be
created through `create_location` before either side of the loop has anything to serve.

`mill mcp.stop` scales the backoffice and the relay to zero and stops the tunnels; the next `mcp.dev`
sets them back. `mill mcp.stopLocalStack` stops LocalStack and removes the containers it ran for ECS
tasks; `mill mcp.localStackSetup` ensures it is up without releasing anything, for working against it
with another client.

The database lives in LocalStack's ECS tasks, so it goes wherever they go: recreating the container
empties it along with the bucket, and the next apply makes both again, empty. A new LocalStack also
discards the OpenTofu state of the one before, which described resources that went with it.

`mill mcp.destroyLocal` is the whole teardown: every process devenv runs for this build, every
container it starts, the ECS task containers LocalStack spawned, the images built here, the local
tofu state, and the process files under `.devenv/state/processes/`. The next run builds the
container and its state together.

[[processes]]
=== Local processes

Everything that keeps running on the host — LocalStack, the three test databases, `api.dev`'s server
and the two tunnels — is a process of devenv's process manager, declared in `devenv.nix` and driven by the
build (`mill-build/src/millbuild/Processes.scala`). None starts with `devenv up` and none restarts on
its own. A task that needs one writes what it runs under `.devenv/state/processes/<name>/` — the
command, one argument per line; its environment, readable by the owner only; and a readiness check —
and has devenv start it, or restart it when the command or environment changed. The first one starts
the manager itself, with the task's environment, which is how the LocalStack licence reaches the
container without being written anywhere.

The manager runs apart from Mill, so these outlive the command that started them, `mill clean` and
the Mill daemon. Whether one is running is decided by the pid its launcher records next to those
files, not by the phase devenv reports.

* `devenv processes list` and `devenv processes logs <name>` show what runs and what it printed.
* Stop one with its task (`mill mcp.stop`, `mill api.stop`, `mill mcp.stopLocalStack`, the
  `stopRqlite` commands) or with `devenv processes stop <name>`.
* After editing `devenv.nix`, stop the manager so the next task starts it with the new definitions:
  stop each process, then `devenv processes down`. A bare `devenv processes down` can leave
  containers running outside its control; `mill mcp.destroyLocal` does it in that order, and removes
  everything else too.

=== A full local loop, in order

. `mill mcp.dev` — LocalStack, and this build released into it: the local configuration, the
backoffice, the relay and the client.
. Point an MCP client at it (the printed config block) and create a location, its identification
surveys, a video, an advertiser and its question, and a locale bundle — see
xref:mcp.adoc[MCP backoffice] for the tool catalogue.
. Either `deploy_location`, and open `https://<id>.cloudfront.localhost.localstack.cloud:4567/<slug>/`
— the portal as production serves it — or `mill api.dev --slug <slug>` for the faster loop on
`localhost:8080`, against the same database.

== Images

`api.image`, `mcp.image` and `rqlite.image` build the deployed images — the first two from an
already-assembled jar, so nothing re-resolves the dependency tree per build. `api.image
--devEndpoints true` builds the same image with `SERVER_DEV_ENDPOINTS=true`, for exercising
`/api/dev/reset-phase` without a full deploy. `api.imagePush`, `mcp.imagePush` and `rqlite.imagePush`
tag and push one to a registry — against LocalStack, the registry `tofu apply` created for the
`local` environment, which is also where `rqlite.imagePush` runs on its own as part of that apply.
See xref:infrastructure.adoc[Infrastructure] for why these images are single-stage and why no tag
defaults to `latest`.

[[release]]
== Releasing: `mill ci.run`

What CodeBuild runs to release a build to an AWS environment, in five operations. `mcp.dev` runs
the first four against LocalStack:

. **Images.** `rqlite.image`, `api.image`, `mcp.image` and `cdc.image`, built before anything else, as
  `captal-<name>:latest`.
. **The configuration.** `tofu init` against the environment's backend
  (`environments/<env>/backend.tfvars`), then a plan of everything saved and that plan applied. The
  API, backoffice and relay versions (see <<versions>>) are passed to it as `image_tag`,
  `mcp_image_tag` and `cdc_image_tag`; rqlite's is the tfvars' `rqlite_image_tag`, since the engine
  changes deliberately rather than per commit. `terraform/modules/images` pushes each image when its
  tag changes — the tag is what its `terraform_data` keeps in the state — after its registry exists
  and before any service is pointed at it; then reads the digest the push left, and every task
  definition names its image by that digest. A version is published once: against AWS, a tag already
  in its registry is that release and is not pushed again, which is also how a module whose version
  did not move goes out unchanged. The apply is what moves the backoffice onto its new image, and its
  `API_IMAGE` onto the new API, so a location deployed afterwards gets it too. It needs Docker, the
  images built and, against AWS, the `aws` CLI for the ECR login, wherever it runs: a `tofu apply`
  run by hand without them fails at the push, before any service changes.
. **Locations.** Every location's service — the ones whose task runs a single container named
  `api`, which is how `deploy_location` registers them — not already on the API image's digest and
  following the relay gets a new revision of its task definition differing only in the image and
  `CDC_FEED_ADDRESS` (the configuration's `cdc_feed_address` output), and is pointed at it. The rest
  of its environment, roles and sizes carry over as the last deploy registered them, so a change to
  those is still a `deploy_location`. The
  service keeps its task count: a paused location stays paused and runs the new image when it is
  resumed. `ci.run` waits for every moved service to settle and fails naming the ones that did not.
. **The client.** Under its version, published once, as the images are: if the bucket keeps it
  already, every location has it and nothing is done. Otherwise the portal's bundle goes up under
  `bundle/` and is kept under `releases/client/<version>/`, the MCP App pages' scripts under `ui/`,
  and the bundle is copied server-side under every deployed location's prefix — keeping a
  location's own brand icon, leaving `maintenance.html` shared, and for a paused location replacing
  the page its resume puts back rather than the maintenance page — then one invalidation of
  everything.
. **Tags.** Every version that moved is tagged on the commit released, and the tag pushed, which
  is where the next release counts from.

The configuration goes out on every run, versions moved or not: it is not versioned, and `ci.run`
is what applies it.

Putting an earlier client back is the same copy from its release, by hand, then a release of the
locations as `ci.run` makes it — the next release that moves the client's version replaces it:

[source,bash]
----
aws s3 cp --recursive s3://<bucket>/releases/client/<version>/ s3://<bucket>/bundle/
# then, per location, the copy step 4 makes, and one invalidation
----

It is configured only through the environment, which the CodeBuild project injects:

[cols="1,3"]
|===
|Variable |Meaning

|`CAPTAL_ENV`
|Required. The `terraform/environments/<name>` to release to, for its tfvars and its backend.

|`AWS_REGION`
|Defaults to `us-east-1`. The credentials are the build's role.

|`AWS_ENDPOINT_URL`
|Unset in CodeBuild. Set to this build's LocalStack, it releases there instead; see below.
|===

The build needs Docker, so the CodeBuild project has to be privileged, and `tofu`, `git-cliff` and
the `aws` CLI on its PATH. Its role applies the whole configuration, so it needs what that creates.
Its source has to be a clone with the history and the tags — CodePipeline's default artifact is a
zip without `.git`, and with no tags every version would be the `initial_tag` again — and it needs
permission to push tags.

On a dev machine, the same release runs against LocalStack:

[source,bash]
----
CAPTAL_ENV=local AWS_ENDPOINT_URL=http://localhost:4567 mill ci.run
----

It needs no credentials: LocalStack's are fixed, the provider uses them when it is given an endpoint,
and every AWS call goes through `awslocal` inside the container. It needs the LocalStack licence
`mcp.dev` needs, starts LocalStack as `mcp.dev` does if it is not running, and applies with the
same state, `.devenv/state/localstack/tofu/<container-id>/` — so a release from here and an
`mcp.dev` run never come apart. It tags nothing: a release to LocalStack is not a release.

[[versions]]
=== Versions

The API, the backoffice, the change data capture relay and the client are versioned apart, each by
its git tags — `api/v1.3.0`, `mcp/v0.4.0`, `cdc/v1.0.0`, `client/v2.1.0` — and its next version is
computed, not chosen:
https://git-cliff.org[git-cliff] reads the conventional commits since the module's last tag and
bumps it. `feat:` bumps the minor, `fix:` and `perf:` the patch, `!` after the type the major, and
the rest (`docs`, `refactor`, `tests`, `chore`, `build`, `lint`) nothing. `mill show
api.releaseVersion` prints the tag the next release goes out under and the last one, which are the
same when nothing since moves it. The client carries its own as `BuildInfo.version`.

Only commits touching the module count: its own folder and its source folders, those of the
modules it depends on (`core`, `messages`, `platform` and `cdc.protocol` for the API;
`cdc.protocol` for the relay and the backoffice; `core` and `messages`, through
`core-js` and `messages-js`, for the client), and the files it lists as `versionFiles` — the
Dockerfile of an image, and the portal stylesheet the backoffice carries. Source folders as well as
module folders because `core-js` and `messages-js` have none of their own: their sources are
`core`'s and `messages`'. The build passes those paths from its own module graph, so a module that
starts depending on another counts that one's commits without anyone listing it. A module's own
`package.mill` is in its folder and counts; `build.mill` and `mill-build/` are not among them: most
commits touching them change other modules, so a change there that only alters how a module is built
needs a `fix:` in the module itself, or it is not released.

The rules are each module's `cliff.toml` — `api/cliff.toml`, `mcp/cliff.toml`, `cdc/cliff.toml`,
`client/cliff.toml` — including its tag pattern and the `initial_tag` released before any tag
exists. Two things there are written around
git-cliff rather than with it, both checked on 2.13 (what devenv installs) and 2.14:

* the types that do not bump are *skipped* commit parsers, not `[bump] no_increment_regex`, which
  2.13 ignores — a `docs:` commit would bump the patch;
* the build reads `--bump --unreleased --context` rather than `--bumped-version`, which computes
  from every commit, ignoring the paths.

== Test tasks

`mill core.test`, `mill api.test` and `mill mcp.test` are the three module-level suites;
`platform` and `messages` have none of their own and are exercised through the other two. Each test
module that depends on a container checks it on every invocation, through a `Task.Input`, and starts
it again when it is not running, rather than trusting a cached URL: a container removed between runs
must be caught, not silently misread as a schema problem. The full breakdown of what each suite
covers, what needs LocalStack, and the three separate `rqlite` containers the test tasks use is
xref:testing.adoc[Test strategy]'s subject; `mill api.test.stopRqlite`, `mill mcp.test.stopRqlite`
and `mill mcp.test.resetLocalStack` are the matching cleanup commands.

== Sharp edges

* **direnv has to be told to trust `.envrc` at least once.** direnv refuses to auto-load an `.envrc`
it has not been explicitly allowed to run, as a security measure — a freshly cloned checkout, or any
edit to `.envrc` itself, needs `direnv allow` run by hand in that directory before `devenv shell`'s
packages and environment variables take effect. Without it, commands that assume the devenv shell
(`mill`, `tofu`, `scalafmt`) are simply not on `PATH`, with no message pointing at `.envrc`.
* **`api.dev` needs a location row before it will start.** Covered above — worth repeating here
because the failure is `LocationNotFound` during layer construction, deep in the process log the task
prints, with no hint that the fix is "create a location first".
* **The editor runs the test fixtures.** Metals imports the build through Mill's BSP server, with its
own output folder (`.bsp/out`), and on an import it evaluates the test modules' `forkEnv` — which
starts the test databases and LocalStack and applies the local configuration. Expect them to start
after an edit to the build, without a `mill` command.
* **Changing `ENVIRONMENT` needs a clean rebuild of one generated file.** `client.generatedSources`
writes `BuildInfo.scala` (which drives `isDevMode`, and therefore the dev reset button in
`ReadyView`) from the `ENVIRONMENT` variable, but the task is cached against its own normal inputs,
and the environment variable is not one of them. `mill clean client.generatedSources` before
changing `ENVIRONMENT`, or the previous `BuildInfo` stays in place with the flag silently wrong. See
xref:client.adoc[Client].
* **`LOCALSTACK_TOKEN` gates more than licensing errors — it gates whether certain specs run at all.**
Its absence is not a build failure: `mcp.test`'s deploy-related specs detect the missing licence (or
the missing `ECS_CLUSTER` configuration that follows from it) and skip themselves. A change that
should have been caught by `DeployE2ESpec` can pass a full green `mcp.test` run on a machine with no
licence configured; see xref:testing.adoc[Test strategy].
