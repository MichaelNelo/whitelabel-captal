= Change data capture relay
:toc:
:toclevels: 2

The `cdc` module is a service of its own between rqlite's change data capture and the services that
react to changes in the database. rqlite's leader posts every change set it commits to the relay
over HTTP; the relay publishes each to the SNS topic of every table it touches; and every task that
follows a table reads it on an SQS queue of its own, subscribed to that topic.

[source]
----
rqlite leader ──POST /cdc──▶ relay ──▶ <prefix>-cdc-video_playbacks ──▶ queue of each backoffice task
                                   └─▶ <prefix>-cdc-errors ──────────▶ queue of each location's task
----

== Why a relay, and why topics and queues

rqlite takes one change data capture configuration per node: one `endpoint`, one `table_filter`.
A second service that wants the same changes cannot be added to rqlite; it has to be added
downstream of whatever rqlite posts to. The relay is that place, and the only one: it keeps nothing,
so it can be replaced, and two can run at once while it is. rqlite cannot sign AWS requests, so it
cannot publish to SNS itself.

SNS fans each change set out once to every subscription; SQS keeps what each task has not read yet,
and lets it read at its own pace. A queue per task rather than per service, because tasks sharing a
queue would split its messages, and a deploy runs the outgoing task beside the incoming one. A topic
per table rather than one topic with a filter policy per subscription, because a task subscribes as
it starts and a new filter policy takes up to 15 minutes to apply. The topics and queues are
standard: no subscriber needs the order or the deduplication, and a FIFO topic admits 100
subscriptions. Why this and not the other options considered is in
xref:context/decisions.adoc[Decisions] and xref:context/relay-sns-sqs-plan.adoc[the relay plan].

== Modules

`cdc`:: The relay: `Relay`, `Topics` (SNS), `RelayRoutes` (HTTP) and `Main`.

`cdc.feed`:: `ChangeFeedQueue`, what a subscriber uses to read a table on a queue of its task's own.
The API and the backoffice depend on it, and on nothing of the relay's.

== The relay

`POST /cdc` takes rqlite's post, `{"node_id": "...", "payload": [...]}`. Each entry of `payload`
with an `index` is a change set, `{"index": n, "events": [{"op": "INSERT", "table": "...",
"before": {...}, "after": {...}}]}`, and the tables its events name are the topics it goes to. The
relay does not reinterpret rows; a subscriber reads the tables and columns it cares about from the
JSON, as it would from rqlite. `index` is the change set's Raft log index.

It keeps nothing. Every change set of every post is published, in index order within the post: a
retry's, one a leader change resends, and one that arrives below another. rqlite delivers at least
once and, after a leader change, out of order; each subscriber absorbs both, reading what it acts on
from the database.

It answers `200` once every change set of the post is published to its topics, and for a body that
is not rqlite's, whose refusal would only make rqlite retry it. When a topic refuses a publish it
answers `503`: rqlite takes only `200` and `202` as delivered, and posts it again, for about six
minutes before it drops it (see xref:infrastructure.adoc[Infrastructure]). `Topics` publishes with
`PublishBatch`, per topic, at most ten change sets and 200 KiB a batch, each message the change set
as rqlite wrote it, with two message attributes: `index`, a `Number`, and the post's trace context
(`traceparent`, `tracestate`). A subscriber's queue reads the index from the attribute, so it never
parses a message to know it is a change set.

`GET /health` answers `ok`. Nothing is authenticated: the relay's security group admits rqlite on
the HTTP port and nothing else.

== Following a table

`ChangeFeedQueue.follow(settings, service, tables, retention)` is a `ZStream` of
`Changed(index, json, context)` and `Gap` that never fails and never ends. `context` is the trace the
relay received the change set in, which each post from rqlite starts (`cdc ingest`) and which every
subscriber continues as it handles the change set, so one trace shows every subscriber a change
reached; see xref:tracing.adoc[Tracing].

. It creates a standard queue, `<CDC_QUEUE_PREFIX>-<service>-<32 hexadecimal characters>` (the
  service shortened with a digest where the name would pass SQS's 80 characters), with `retention`,
  a visibility timeout of five seconds and, with `CDC_DEAD_LETTER_ARN`, that queue as its dead-letter
  queue after five receipts; and a policy letting the tables' topics send to it, by `aws:SourceArn`.
. It subscribes it to each table's topic, `<CDC_TOPIC_PREFIX><table>`, with raw delivery.
. It publishes to each topic a marker, `{"marker":"<queue name>"}`, and drains the queue until every
  one has come back, within a minute: the subscription delivers.
. It emits a `Gap`, and from then on every change set its long polls receive (20 seconds, ten at a
  time), deleting each batch as it receives it.

A `Gap` means change sets may have been missed: a subscriber that keeps state derived from changes
rebuilds it from the database when it gets one, and carries on. What the drain discards was received
before the marker, so it was committed before the marker came back and before that rebuild, which
reads it. That holds whatever order a standard topic delivers in, and needs no clock. The other
tasks' markers carry no `index` attribute and are passed over. The queue is never purged, since a
purge takes up to a minute and may delete what arrives after it.

The queue and the subscriptions belong to the stream's scope: unsubscribed and deleted as it
closes, which on SIGTERM is the shutdown hook `ZIOAppDefault` registers. A task killed otherwise
leaves them; `ChangeFeedQueue.removeLeft` removes every queue of a service's tasks and every
subscription to one, for when none of them runs, which `destroy_location` does for the location it
destroys. Whatever stops a queue is logged, and the stream makes another, with another `Gap`, two
seconds later.

What no subscriber hears of is a post rqlite drops after its six minutes of retries: nothing tells
it. Each finds out only when it next starts, and rebuilds.

== Subscribers

[cols="1,3"]
|===
| Subscriber | What it does with a change set

| Backoffice (`mcp`)
| `VideoFileCollector` reads `video_playbacks` events: an `INSERT` of an open row starts a
  `PlaybackExpiry` timer, an `UPDATE` that sets `ended_at` or a `DELETE` cancels it, and every
  change set of that table asks for a collection pass; one of any other table does nothing. A `Gap`
  resyncs the timers with the open playbacks in the database and asks for a pass. Its queue is the
  `mcp` service's, on `video_playbacks`, kept an hour. See xref:mcp.adoc#replaced-files[Replaced files].

| Every location's API (`api`)
| `RecoveryFeed` reads `errors` events: an `INSERT` with a fingerprint, read from `after`, is
  published to every waiting page's stream, which checks again whether its wait shortened. A `Gap`
  is published too. Its queue is named after the location's slug (`LOCATION_SLUG`), on `errors`,
  kept a minute: a page connecting later checks as it connects, so an older message tells nobody
  anything. `deploy_location` forwards the backoffice's `CDC_TOPIC_PREFIX` and `CDC_QUEUE_PREFIX`,
  and the locations' dead-letter queue as `CDC_DEAD_LETTER_ARN`, and `ci.run` sets the three on every
  location it moves. See xref:api.adoc#recovery-stream[the waiting page's stream].
|===

Without `CDC_TOPIC_PREFIX` and `CDC_QUEUE_PREFIX` a subscriber logs a warning and follows nothing,
and the backoffice only runs the passes and timers of startup and replacements. A change set
repeated or out of order changes nothing: a timer reads its deadline from the database, and a page
checks its offer against it.

Which tables reach the relay is rqlite's `table_filter`: the root variable `cdc_tables`,
`["video_playbacks", "errors"]`, written as `^(video_playbacks|errors)$`, which reaches the
entrypoint as `RQLITE_CDC_TABLE_FILTER`; the same list names the topics. Changing it changes
rqlite's task definition, which replaces every node.

== Configuration

[cols="1,1,3"]
|===
| Variable | Default | Meaning

| `CDC_PORT` | `8090` | HTTP port rqlite posts to. The image sets `8080`, the `container_port` every
  service uses.
| `CDC_TOPIC_PREFIX` | required | A table's topic's ARN but for the table's name,
  `arn:aws:sns:<region>:<account>:<prefix>-cdc-`. The relay does not start without it.
|===

A subscriber reads `CDC_TOPIC_PREFIX` too, `CDC_QUEUE_PREFIX`, `<prefix>-feed`, which its queue is
named under, and `CDC_DEAD_LETTER_ARN`, its kind's dead-letter queue (see
xref:infrastructure.adoc#service-names[Infrastructure] for the queues' permissions).

== Deployment

`terraform/modules/cdc`: one Fargate task with no load balancer, named `cdc.<namespace>` (see
xref:infrastructure.adoc#service-names[Service names]), with its own security group, the topics and
a task role allowed to publish to them. It deploys overlapped (`100`/`200`): the new task starts,
the old one stops once the container health check, `curl -sf http://localhost:<port>/health`, finds
the new one healthy. Both behind the name meanwhile is harmless, since either publishes whatever
rqlite posts to it, and a post cut short as the old one stops is posted again. The module outputs
`ingest_url`, which the root passes to rqlite as its `cdc_endpoint`, `topic_arns` and
`topic_prefix`. See xref:infrastructure.adoc[Infrastructure].

Locally it runs the same way, as a task in LocalStack that `mill mcp.dev` releases, and rqlite
reaches it as `cdc.captal.local`. See xref:development.adoc[Local development].

The relay is released like the other images: `docker/cdc.Dockerfile`, the `captal-cdc` ECR
repository, its version from `cdc/cliff.toml` and `cdc/v*` tags, passed to the configuration as
`cdc_image_tag`. See xref:development.adoc#versions[Versions].

== Tests

`cdc/test`, `RelaySpec`: a post's change sets published in index order with its trace, a change set
sent again published again, a post the topics refuse failing, bodies that are not rqlite's, the
tables a change set names, and how `Topics` batches and attributes them. `cdc/feed/test`,
`ChangeFeedQueueSpec`: the queues' names, a long slug's included, and telling one slug's queues from
those of a slug that extends it. Run with `mill cdc.test` and `mill cdc.feed.test`; neither needs a
container. The end-to-end scenarios tagged `@change-feed` run both subscribers against LocalStack
(see xref:testing.adoc#end-to-end[the end-to-end features]).
